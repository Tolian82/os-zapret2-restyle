# os-zapret2-restyle — текущее состояние v0.5.x

**`v0.5.2_120` — диагностика штатной страницы «Передача голоса» сверяет реально установленные STUN/IPSET файлы с запечатанным общим runtime.** Раньше `voice_live_inspect.inspect_common_runtime` разрешал `ready`, когда `voice-plan.json`, `dvtws.args`, процессы и IPFW были корректны, даже если активный `traffic.conf` или `managed/ipset-{service}.txt` изменился после применения. Теперь read-only проверка common owner требует точного совпадения файлов `voice-plan.json`, `dvtws.args`, `traffic.conf`, управляемых IPSET включённых Voice-служб и управляемых IPSET, по которым обычный STUN «Стратегий» прошёл проверку при stage (включая службы с выключенной галочкой Voice). Списки берутся только из запечатанного `source.ipset_sha256` / `source.ordinary_scope_ipset_sha256`, посторонние пути не принимаются. При расхождении статус становится `unverified-release`, `engine_verified=false`, без автоматического перезапуска или изменения IPFW. Существующий regression расширен на валидное состояние, подменённые Voice/ordinary IPSET и traffic/argv, исчезнувший IPSET. ТЗ/frontend, штатный Apply, процессы и IPFW не изменены; живой FreeBSD STUN/MEDIA/CALL по-прежнему требует испытаний, релиза нет.

**`v0.5.2_119` — исправлена неоднозначность native L3 selector при совместном STUN Voice/Strategies.** При проверке конфликта `voice_traffic_merge.profile_scope` ранее немедленно считал профиль IPv6-only после первого `--filter-l3=ipv6`, не проверяя последующие дублирующие `--filter-l3=ipv4`; в зависимости от поведения dvtws2 это могло ошибочно разрешить пересекающийся с Voice IPv4 STUN. Теперь повторная проверка перед общим Apply явно отказывает при нескольких/неизвестных/дублируемых семействах L3 в STUN-профиле, разрешает единственный `ipv6` только как IPv6-only и продолжает проверять пересечения для единственного `ipv4` либо `ipv4,ipv6`. Сохранены один общий dvtws2, неизменный профиль «Стратегий», штатная IPFW/Config-архитектура и frontend/ТЗ. Добавлен целевой regression с IPv6-only, dual-stack, повторными IPv6+IPv4 и некорректными L3 селекторами. Никакой дополнительной инфраструктуры. Требуются реальные FreeBSD STUN/MEDIA/CALL и GUI/CONFIG/BOOT испытания, релиза нет.

**`v0.5.2_118` — сохранена диагностика общего engine/IPFW при новой pinned STUN-проверке.** `_117` успешно выполнил новый сквозной тест общего runtime (Voice Telegram ON, Voice Discord OFF, ordinary STUN на Discord IPSET), но прежний `test-voice-common-runtime.py` ожидал диагностическую категорию `engine/IPFW|UDP selector` при согласованной подмене Voice UDP профиля; новая ранняя проверка корректно отклоняла подмену, но сообщала только `traffic changed after STUN staging`. Сообщение общего `voice_ipfw_adapter.py` теперь содержит `engine/IPFW` и точную причину изменения STUN traffic. Порядок проверок и fail-closed семантика не ослаблены. Остались реальные FreeBSD STUN/MEDIA/CALL и GUI/CONFIG/BOOT испытания, релиз/merge запрещены.

**`v0.5.2_117` — исправлена повторная проверка STUN-пересечений при применении общего Voice/Strategies IPFW.** В `_116` native release stage сохраняет SHA-256 управляемых IPSET, на основе которых обычный STUN допускался рядом с Voice. Однако `voice_ipfw_adapter.shared_release_manifest` до `_117` сверял только адреса *включённых Voice-профилей* и не проверял файл управляемого IPSET выключенного Voice-сервиса, используемый обычной стратегией. Перед чтением/изменением IPFW теперь сверяются все сохранённые `ordinary_scope_ipset_sha256`, а также SHA-256 всего `traffic.conf` с запечатанным `merged_sha256`; неизменность только `dvtws.args` недостаточна. Использован прежний scoped release parser и он же read-only проверяет файлы, никакого второго движка, журнала или IPFW-контроллера нет. Сквозной regression: shared candidate с Voice Telegram ON, Discord Voice OFF и обычным STUN через Discord IPSET; подтверждены корректный manifest, отказ после подмены Discord IPSET, отказ при согласованной подмене `traffic.conf` и `dvtws.args`. Frontend и ТЗ неизменны. Живой FreeBSD STUN/MEDIA/CALL и полная GUI/CONFIG/BOOT приёмка всё ещё впереди; релиза нет.

**`v0.5.2_116` — STUN обычных «Стратегий» сохраняет ссылку на проверенный управляемый IPSET даже при выключенной соответствующей галочке Voice.** В `voice_release_stage.compile_bundle` ранее первая стадия допускала scoped STUN через любой проверенный `managed/ipset-{service}.txt`, но в следующей `voice_handoff_preflight` сохранялась карта только *включённых* Voice-профилей. Теперь stage записывает SHA-256 файлов IPSET допустимых пяти сервисов; private native handoff заново читает строго эти candidate файлы из `stage.parent/managed`, сверяет каждый хеш и повторно использует ту же STUN-проверку пересечений. Подмена IPSET после компиляции отвергается, активные IPSET не читаются. Добавлен end-to-end тест: Voice Telegram ON, Voice Discord OFF, ordinary Strategies STUN по Discord IPSET и последующая подмена файла. Это исправление касается согласованности генерации/предпроверки, без изменения штатных IPFW/Apply/boot, утверждённого GUI/ТЗ и без релиза. Полная приёмка требует живого FreeBSD STUN/MEDIA/CALL.

**`v0.5.2_115` — исправлено функциональное несовпадение двух проверок STUN-сосуществования в общем Voice+Strategies release.** Первая компиляция `voice_release_stage` разрешала обычный STUN профиль «Стратегий» при доказанно непересекающихся Voice IPSET/UDP-областях; следующая штатная `voice_handoff_preflight.verify_staged_handoff()` заново вызывала `merge_profiles` **без карты IPSET**, поэтому тот же допустимый релиз отбрасывался до Apply. Перед второй проверкой теперь используются только доверенные профили *после* восстановления и полного сравнения IPFW capture, списка целей и SHA-256 managed IPSET из запечатанного stage. Добавлен сквозной regression с реальным `generator.sh`, обычным STUN `198.51.100.0/24` и Voice Telegram `91.108.0.0/16`, плюс проверка отказа при конфликтующей IPSET и подменённом плане. Не добавлены процессы, правила IPFW, новые журналы и GUI; утверждённый frontend/ТЗ без изменений. Завершение требует реального FreeBSD STUN/MEDIA/CALL, GUI/CONFIG/BOOT acceptance и controlled rollout; релиза нет.

**`v0.5.2_114` — штатный Voice GUI status API безопасно переживает отказ configd без изменения frontend.** `VoiceController::inspectAction` ранее мог выбросить необработанное исключение при недоступной read-only команде `zapret voice_inspect`, превращая обновление статуса «Передачи голоса» в HTTP 500 и не давая пользователю достоверного состояния. Расширен существующий PHP integration test: штатный подтверждённый ответ, неверный JSON, выброшенное исключение, запрет GET и отсутствие утечки внутренних полей. Приоритет дальше — реальное FreeBSD owner-live STUN/MEDIA/CALL и GUI/CONFIG/BOOT acceptance; production PoC cutover и релиз по-прежнему запрещены.

**`v0.5.2_113` — исправлена изоляция shell-регрессии настоящего `verify-cleanup`-маршрута.** В CI `_112` обнаружилось, что старый qualification test в том же `test-voice-common-apply-runtime.sh` ранее заменял `validator_validate_runtime_modes` на кандидатно-специфичную заглушку, и новый partial-cleanup fixture ошибочно наследовал её. **`v0.5.2_112` — исправлен реальный shell→Python разрыв пути partial IPFW cleanup.** После успешного CI `_111` аудит показал: `voice_ipfw_adapter.py` принимает безопасный read-only `verify-cleanup`, но производственный `backend/firewall.sh:firewall_shared_runtime()` всё ещё допускал только прежние пять действий, поэтому приватный `shared-apply-legacy-resume ID` всегда останавливался до kernel preflight. Исправлен *только общий* allowlist `firewall_shared_runtime`, без отдельного исполнителя и без расширения полномочий mutating actions: `verify-cleanup` разрешён как read-only. Сквозной существующий shell regression теперь извлекает фактическую production-функцию, проверяет точный Python argv, запрет неизвестных действий, а также фактический `apply_runtime_resume_retired_legacy_cleanup` при проверенной частичной стадии, чужом IPFW и отсутствующем dvtws2. ТЗ/frontend неизменны. Операторский режим сохраняется: без автоматического опасного IPFW повторения, production cutover/release/merge запрещены до FreeBSD STUN/MEDIA/CALL и полной приёмки.

**`v0.5.2_111` — безопасное operator-only возобновление частичного native IPFW cleanup под исходным FD9.** Для уже сохранённого `legacy-common-committing` добавлена служебная команда `shared-apply-legacy-resume ID`, отдельно от автоматического boot, обычного read-only reconcile и cold reconcile. После проверки вызывается **только прежний** `firewall_shared_runtime commit` (идемпотентная очистка подтверждённых стадий), затем два `verify-committed` и терминальный shared journal; без Config save, запуска engine и повторной установки правил. Ошибки сохраняют pending и старый backup, автоматического обхода нет. Добавлены регрессии на частичное завершение и конфликты; ТЗ/frontend неизменны, FreeBSD owner-live STUN/MEDIA/CALL и полная приёмка ещё впереди, релиза нет.

**`v0.5.2_106` — двойной read-only witness для terminal native IPFW COMMIT.** После первого подтверждения complete live common runtime перед записью terminal `committed` выполняется второе независимое `verify-committed` под тем же FD9 и Config flock. Исчезновение engine между проверками оставляет `legacy-common-committing` pending без повторного COMMIT, save или start. Существующий journal fault suite проверяет этот случай. Cold reboot при отсутствующих процессах и частичный IPFW cleanup остаются незакрыты; публичная миграция и релиз отключены.

**`v0.5.2_105` — фактическое применение read-only reconciliation при утраченном native IPFW COMMIT receipt.** Приватный forward сразу после fsync `legacy-common-committing` по-прежнему вызывает **не более одного** штатного `apply_runtime_commit`. Теперь, если дочерний native исполнитель ответил ошибкой, потерял проверенный receipt или завершился по timeout, исходный Python FD9/Config-lock владелец НЕ повторяет kernel/Config/engine операции, а в этой же транзакции выполняет независимую `verify-committed`. Только когда физически подтверждены один новый dvtws2+monitor, sealed release/old-backup и полное отсутствие IPFW staging, фиксируется обычный `committed`; при частичном cleanup/чужом runtime остаётся durable `legacy-common-committing` и блокировка, без ложного успеха. Тот же read-only путь `_104` применяется к уже существующему прерванному intent. Сквозной существующий Python-тест расширен до 9 комбинаций (уже pending, потеря receipt, timeout × полный/частичный/чужой live-state), проверяет максимум один COMMIT и отсутствие повторного запуска/Config-save. **Не реализована cold power-loss recovery**, отдельный private route/GUI не открыт. ТЗ/front-end прежние, без релиза.

**`v0.5.2_104` — безопасное read-only завершение прерванного IPFW COMMIT живого общего владельца.** Доработана прежняя приватная `commit_native_common_after_legacy_config_save`: когда единый WAL уже содержит `legacy-common-committing`, повторное обращение под исходным FD9 и **актуальным** заблокированным Config inode **никогда** не вызывает `apply_runtime_commit`, `Config::save`, `activate` или rollback. Вместо этого оно повторно сверяет sealed старый Config/runtime backup и journal, затем вызывает только существующий `verify-committed`: проверку установленного native release, единственного dvtws2+monitor и итогового IPFW **без staging-таблиц**. При полном совпадении ранее потерянный final receipt можно завершить записью обычного `committed`; при остаточных таблицах, отсутствии процесса или иной неопределённости `legacy-common-committing` остаётся заблокированным без мутаций. В существующем Python suite добавлены отдельные случаи удачного read-only reconciliation, частичного IPFW и недоступного нового engine; повторное завершение отвергается. **Граница:** это reconciliation только пока verified common runtime жив; cold reboot и частичная очистка по-прежнему требуют отдельного безопасного механизма. Не подключено к CLI/configd/GUI, публичная миграция/релиз закрыты, ТЗ и frontend неизменны.

**`v0.5.2_103` — проверка legacy lifecycle после terminal native COMMIT.** CI `_102` подтвердил, что новая native IPFW COMMIT-последовательность доходит до финального общего journal owner. Два прежних ожидания в `test-shared-apply-operation.py` ошибочно предполагали `safe_to_mutate=True` для **устаревшего legacy lifecycle** при фазе `committed`. По действующему `voice_cutover_guard.check_pending` этот lifecycle ОБЯЗАН оставаться заблокированным с причиной `shared-runtime-owned`, иначе после reboot может появиться второй dvtws2. Исправлены только два ожидания: у legacy `blocked`, а у owner-scoped native Apply `safe_to_mutate=True`. Production-код `_101` и макет IPFW `_102` не менялись. Следующий этап — разобрать crash recovery фазы `legacy-common-committing` и завершить FreeBSD проверку STUN/MEDIA/CALL до включения публичной миграции.

**`v0.5.2_102` — точная регрессия post-COMMIT IPFW stage в существующем shell-тесте.** CI `_101` указал на тестовый макет `firewall_shared_runtime verify`: вопреки реальному `voice_ipfw_adapter.shared_firewall_action(verify)`, он принимал `FW_STAGE=1` после native COMMIT, поэтому отказной сценарий не срабатывал. В `scripts/test-voice-common-apply-runtime.sh` существующий mock `verify` теперь отказывает при любой оставшейся staging-таблице. Публичный legacy cutover, recovery после частичного cleanup и live STUN/MEDIA/CALL по-прежнему закрыты.

**`v0.5.2_101` — штатный IPFW COMMIT в приватном общем legacy→common backend.** После подтверждённой записи Config (`legacy-config-saved`) исходный Python-владелец удерживает FD9 и **новую** блокировку Config, снова проверяет sealed previous Config/runtime и запущенный `dvtws2`/supervisor со *staged* IPFW, затем в едином журнале fsync-публикует `legacy-common-committing` **до** любого удаления таблиц. Далее через прежний `zapret_service.sh` вызывается **существующий** `apply_runtime_commit`, который выполняет штатный `firewall_shared_runtime commit` и полную проверку без staging; новый read-only `apply_runtime_verify_retired_legacy_committed` отдельно доказывает установленный release, единственный engine/supervisor, старую резервную копию и отсутствие staging/чужих IPFW. CLI `finish-activating` закрывает только указанную фазу после повторных проверок, не подменяя семантику `finish-activated`. Тесты проверяют маршрут и отказ на partial/foreign tree, drift Config, чужом IPFW и failed atomic install. Случаи, когда старое дерево перемещено, а новое **не** установлено полностью, пока blocked; owner-live не подтверждён.

**`_51`:** прежде `atomic_install_tree` удалял существующие `.stage.$$` и `.old.$$` перед каждой установкой; при столкновении PID после сбоя это могло уничтожить старую копию runtime. Теперь сохранение неизвестных staged/parked деревьев обязательно: проверка до copy/rename и отказ при существующем файле/симлинке. Также запрещён `mv` в уже занятый backup `name-date-PID`. Regression на реальном helper проверяет три отказа и неизменность активного runtime. Автоматическое восстановление *частичного* `activating` ещё не реализовано; owner-live не подтверждён.

**`_50`:** ограниченное восстановление фазы `activated` после холодного прерывания до Config save: предыдущий committed common owner, saved Config, оба sealed bundle, полное установленное дерево, отсутствие engine/supervisor/orphan-процессов и пустой scoped IPFW проверяются под FD9. При точном совпадении установленного нового release штатный `atomic_install_tree` возвращает предыдущий release, сохраняет неудачный кандидат и после повторной проверки переводит тот же журнал в `restored`. Если предыдущий release уже на месте, повторный вызов не переносит файлы. Чужое/частичное состояние остаётся заблокированным. Linux CI проверяет код; FreeBSD owner-live ещё не принят.

**`_49`:** для прерванной `activating` с **предыдущим committed общим владельцем** добавлен fail-closed recovery только при полном совпадении active runtime с его sealed release, native saved Config и отсутствии живых/незарегистрированных процессов dvtws2 и owned IPFW. Единственный durable journal переводится в `restored`, затем штатный boot использует previous. Partial mutation, отсутствие previous, `activated` не восстанавливаются автоматически. В CI зафиксирована неизменяемая граница истории PR по SHA `a7682c46` (конец `_47`): все заголовки и ревизии начиная с `_48` строго проверяются, история до границы не переписывается. Linux/CI проверки и FreeBSD owner-live различаются.

**`_48`:** рабочий откат общего runtime исправлен: `atomic_restore_tree` парковит временный кандидат под PID `$$`; расширен регрессионный сценарий old literal `$`/foreign PID. Повреждённые вставки в активных документах исправлены. Recovery `activating`/`activated`, running-legacy handoff и owner-live ещё не завершены.

**v0.5.2_38–_39:** root PHP staging и native Config worker теперь самостоятельно проверяют оригинальный FD9: inode, владение root, удерживаемый flock. Не появляется новый lock, Config writer или WAL. Linux тест проверяет заблокированный FD9, свободный, чужой и symlink. Полный CI на `_37` завершился PASS для Voice candidates, но Project не прошёл позднюю Strategy Lab matrix из-за устаревшей метки пакета `_28` в PROJECT_STATE; `_39` синхронизирует primary metadata и добавляет ранний тест, чтобы предотвратить повторение. FreeBSD owner-live, полноценное mutating-phase recovery и выпуск релиза ещё не подтверждены.

**`_40` — устранение опасного ложного rollback после native Config save.** `SharedConfigCommit::persist()` теперь классифицирует исключение на повторной блокировке Config, построении модели, чтении saved Config и последующей разблокировке как `SharedConfigSaveUncertain`, а не pre-save error. Корневой worker проверяет сериализацию и полную запись JSON receipt; ошибки после подтверждённого сохранения возвращают код 70 и оставляют журнал на проверку. Отрицательные PHP-тесты моделируют сбой relock после реального сохранения и несерилизуемое подтверждение. Автоматический откат runtime при уже записанном Config запрещён. FreeBSD owner-live квалификация всё ещё нужна.

**`v0.5.2_41` — read-only native common IPFW inspection:** существующая `voice/inspect` теперь различает legacy IPFW ledger и новый подтверждённый common owner из единого durable journal. Когда owner committed (либо у `restored` есть предыдущий committed owner), инспектор подтверждает целостность source bundle, совпадение page/dependencies/changed_fields с sealed plan и фактические kernel IPFW правила/таблицы по manifest общего release; при совпадении возвращает `state=ready`, `source=native-common`, `condition=common-ipfw-verified-only`, **`can_activate=false`**. Все pending-фазы немедленно возвращают `interrupted`, без обращения к IPFW. Чужие или частичные правила остаются blocked; если common owner отсутствует, сохраняется legacy inspection. Это статус только IPFW, НЕ подтверждение живых dvtws2, успешного STUN или звонка. GUI, ТЗ, FD9 runtime и native Config не изменены. Запрошена проверка CI ревизии `_41`, живые FreeBSD tests отдельно.

**`v0.5.2_42` — read-only свидетельства процессов общего движка и пяти Voice-профилей.** Единственный существующий endpoint `voice/inspect` после подтверждения общего sealed owner и kernel IPFW дополнительно проверяет PID `dvtws2`, PID supervisor и точное совпадение установленного `runtime-v2/voice-plan.json` и `dvtws.args` с тем же sealed release. Имена включённых профилей сопоставляются одновременно с `voice-plan.profiles`, `capture.voice` и фактическими IPFW таблицами. Для всех пяти служб возвращаются отдельные `configured`, `capture_verified`, `runtime_state`, `media_verified=false`; для всей операции — `runtime.state`, `engine_verified`, `supervisor_verified`, `source_verified`, `call_verified=false`. Это НЕ пять независимых демонов и не подтверждение прохождения STUN, медиа или звонков. Нет новых писателей, WAL или изменений GUI. После контрольных тестов требуется FreeBSD owner-live/call acceptance.

**`v0.5.2_43` — предотвращение ложного `requires-review` при обычном legacy/foreign runtime.** В общем `backend/apply_runtime.sh` read-only `apply_runtime_probe` отделён от мутирующего `apply_runtime_preflight`. Под исходным FD9, после detached Config preflight и до durable фаз `prepared/activating`, `shared_apply_execute_service` проверяет полноту candidate, engine/supervisor, соответствие common active release и фактический IPFW. Запущенная legacy-установка без `voice-plan.json`, частичный monitor и чужой kernel/IPFW отвергаются кодом 69 **без записи** новой транзакции и без firewall_prepare. Когда проверки пройдены, тот же probe повторяется внутри runtime activation после durable intent, чтобы отказать при гонке внешних изменений. В тестах отдельно проверено, что негативные случаи не вызывают `record:prepared`, `record:requires-review`, Config::save или изменение firewall. Это только безопасное предотвращение ложного зависания; автоматическая live migration legacy→common и FreeBSD owner-live ещё требуют проверки.

**`_44`–`_45`:** первоначальная попытка PID-парковки отката сохранила буквальный `$` в исходнике и тесте. `_48` исправляет имя на `$$` и доказывает, что текущая парковка конфликтует безопасно, а чужие следы не перезаписываются. Защита census процессов `dvtws2` из `_45` сохраняется.

**`_47` — тестируемый quiescent legacy→common migration.** Добавлен интеграционный shell-сценарий на существующем `apply_runtime.sh`: при полностью остановленных dvtws2/supervisor и пустом owned IPFW прежняя legacy-директория (без нового `voice-plan.json`) сохраняется штатным atomic backup, запускается общий runtime, а отказ до Config save восстанавливает именно прежнюю директорию и пустой kernel. Успешный повторный Apply оставляет старый backup доступным; работающий legacy-процесс по-прежнему отвергается. Это **не** автоматическая остановка и не эксперимент над живым OPNsense; API GUI и утверждённое ТЗ не менялись. Переход с running legacy требует отдельного доказанного live-owner handoff; FreeBSD owner-live и реальный STUN/call acceptance всё ещё не завершены.

State-line scope: **`v0.5.x`**. Текущий этап — **`v0.5.2_120`**, открыт владельцем 13.10.2026 без релиза. Поток состояния: `START_HERE -> PROJECT_STATE -> version-line archive`; смена третьего компонента не закрывает линию `v0.5.x`.

## Сохраняемая продуктовая база

- DNS считается исправным; старое расследование закрыто до нового воспроизводимого отказа.
