## Что входит

- Состояние native Voice/Strategies из установленной `v0.5.3_28`: один общий `dvtws2`, supervisor, Config/FD9 shared Apply, destination-scoped Telegram UDP IPSET/IPFW, пять редактируемых Voice профилей. Исходное исправление native OPNsense `InterfaceField` scalar leaf setter подтверждено [PR #377](https://github.com/Tolian82/os-zapret2-restyle/pull/377) и рабочим Telegram ON Apply на приборе.
- Новый этап `0.5.4` документирует эксплуатационную готовность отдельной TNAS/Docker `tgcalls_cli` лаборатории: реальные SSH/маршрут/Docker/target/IPFW параметры, безопасный 15-секундный smoke, будущие A2 LAN/WAN PCAP, A3 STUN-aware тесты и A5 приёмочный звонок. [Текущий runbook](../architecture/TELEGRAM_NATIVE_VOICE_TNAS_LAB.md).
- В новый пакет **не** вводится второй helper/PoC, не меняется исполнительная Voice-стратегия, не добавляется новая IPFW/PFIL/NAT/SSH-политика и не утверждается, что удалённый Telegram reflector обязан отвечать на Hello.

## Результат owner-live, перенесённый из установленной _28

На OPNsense конфигурация Telegram ON, `voice_inspect=ready`, журнал `committed`, таблица `zapret2_voice_telegram` (14 CIDR), IPFW `19000` (`vtnet1`, divert 989). TNAS `192.168.1.100` имеет маршрут через `192.168.1.2` к `91.108.13.10`, контейнер `tgvoice-lab` в host mode. 15-секундный `tgcalls_cli --mode reflector --reflector 91.108.13.10:596` дал прирост счётчика **60 пакетов, 4080 байт**, но Caller/Callee `Reconnecting`, `Call established=no`, `TGCALLS_EXIT=1`.

Это **реальный IPFW_CAPTURE_PASS и MEDIA/CALL не пройдены**. Пакет/релиз нельзя описывать как проверенный рабочий двусторонний Telegram-звонок. Для финальной проверки STUN нужны корректный STUN-payload и подтверждённый ответ; для звонка — двустороннее аудио. [Протокол](../verification/evidence/2026-10-19-native-voice-tnas-reflector-first-run.md).
