## Scope

Native **Voice Transmission / Передача голоса** settings between Strategy and Laboratory, with five STUN service profiles (Telegram, Discord, X (Twitter), SIP (VoIP), Custom), one WAN selector, reusable IPv4 target IPSETs, bilingual guidance, and the existing shared Zapret2 process.

## Current implementation boundary

The model/form/navigation/help, named target normalization, and standalone fail-closed STUN profile compiler and declarative Voice IPFW capture plan and read-only persisted OPNsense Voice model export, private inert candidate-bundle preflight and one-engine traffic-merging helper are staged. An adapter-injected ownership/rollback IPFW algorithm, retryable cleanup and durable owner-private intent journal and mock-only activation ordering with read-only restart triage are tested but not connected to the router in Draft PR #328. Its initial allowlist is deliberately narrower than the final approved native parameter surface pending engine-specific verification. Strategies Apply now preserves other Voice/IPSET fields and rejects stale Telegram IPSET snapshots. A Voice-specific payload whitelist/freshness helper is staged, but no Voice Apply endpoint is active. Voice Apply remains disabled: none of the intended new persistent enabled-state/live integration of staged generated profiles, transaction, multi-service destination-scoped firewall rules, independent WAN isolation, compatible CLI migration, rollback, or boot recovery are complete. The previous `telegram_voice` PoC remains the implementation currently present on the stable installed product.

The known Telegram STUN fake template is a migration example, **not a qualified working voice strategy**. Non-STUN Telegram traffic stays in ordinary Strategies. No change to the user’s Squid/sing-box/PF/TNAS laboratory is included.
