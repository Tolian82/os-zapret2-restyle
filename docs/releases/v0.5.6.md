## Release scope

- Next development stage `0.5.6`; no new DPI-bypass mechanisms, proxy routing logic, Voice GUI or engine code introduced by this stage transition.
- Existing native common `dvtws2`, Traffic Strategies, Strategy Lab, shared Strategies/Voice Apply and per-service Voice STUN profiles remain installed and configurable.
- The owner has ended the Telegram voice laboratory campaign in the current network environment. The native profile has **working Config/Apply and outbound packet interception**, but **not a proven bidirectional Telegram UDP response, working MEDIA_PASS or CALL_PASS**. Do not market the Telegram voice profile as a verified solution for the owner's provider.
- pfSense direct-reflector success proved **not comparable with the OPNsense unproxied path**: pfSense routes the reflector subnet via OpenVPN `ovpnc6`, next-hop `10.1.11.1`, with explicit `<Telegram>` NAT to `10.1.11.2`. A traceroute from pfSense confirmed `10.1.11.1` as hop 1. No tunnel traffic capture from that successful TNAS run was taken; the exact transmitted session path is inferred from routing/NAT and is not separately packet-proven.
- On OPNsense fake-ON, fake TTL7, fake-OFF, valid synthetic STUN and direct non-STUN reflector tests were performed. WAN outbound injection/original verified; replies/media absent. The fake-OFF trial and alternate TNAS `/32` routes were restored and verified. OpenWrt SOCKS5 UDP ASSOCIATE and 6×UDP64 + STUN20 egress succeeded but received no server reply; this did not test Telegram's real calling transport.
