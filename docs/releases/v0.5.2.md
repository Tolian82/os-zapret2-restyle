# os-zapret2-restyle v0.5.2

**Решение владельца 15.10.2026: сначала завершить программирование по ТЗ, потом один тестовый релиз и живые испытания.** Новый [короткий контроль завершения](../VOICE_CODE_COMPLETION_GATE.md) — текущая очередь проекта; **не выпускать** тестовый/stable release и не устанавливать промежуточные ревизии на OPNsense. Пункт «проводить FreeBSD live испытания сейчас» в старых заметках больше не является немедленным следующим действием. `v0.5.2_122` остаётся Draft/неопубликованным кандидатом. Исправлена согласованность двух штатных валидаторов общего Voice/STUN Apply.

**`v0.5.2_122` — согласована проверка повторных STUN-параметров GUI и общего native runtime.** В существующем `voice_profile_compiler.validate_arguments` устранён реальный разрыв: дубли `--out-range` и `--lua-desync` ранее могли пройти Python staging, хотя `VoiceCandidateValidator` запрещает их в форме. Общий backend теперь отклоняет такие кандидаты до изменения Config, IPFW или запуска dvtws2. Расширены существующие тесты компилятора и дифференциальная проверка PHP/Python; интерфейс, общий lifecycle и прежняя архитектура восстановления не изменены. **Реальные STUN/MEDIA/CALL и GUI/CONFIG/BOOT остаются неиспытанными; без релиза.**

**`v0.5.2_121` — подготовлена проверка реального прохождения Voice UDP на FreeBSD OPNsense без вмешательства в службу.** Новый небольшой read-only `voice_live_trial.py` использует существующий `SharedApplyOperation` и `voice_live_inspect.examine_shared` (только `committed/ready` общий владелец), читает `/sbin/ipfw -a list`, извлекает исключительно счётчики принадлежащих Voice правил и повторно проверяет неизменность владельца. Режим `snapshot` формирует JSON, режим `compare` сопоставляет два снимка до/после **ручного** Telegram-вызова, отказывает при смене owner/правил, потере IPFW или сбросе счётчиков. Рост счётчиков означает **только совпавший исходящий UDP**, не STUN-ответ, медиатрафик или успешный звонок (`stun_verified/media_verified/call_verified=false`). Никаких рестартов, ipfw zero, pcap, новых демонов или изменений frontend/ТЗ. Добавлены маленький offline regression для Linux/FreeBSD CI и [инструкция реальной приёмки](../VOICE_LIVE_TRIAL.md). **Реальные STUN/MEDIA/CALL и GUI/CONFIG/BOOT пока не подтверждены**; Draft PR, без merge/release.

**`v0.5.2_120` — диагностика штатной страницы «Передача голоса» сверяет реально установленные STUN/IPSET файлы с запечатанным общим runtime.** Раньше `voice_live_inspect.inspect_common_runtime` разрешал `ready`, когда `voice-plan.json`, `dvtws.args`, процессы и IPFW были корректны, даже если активный `traffic.conf` или `managed/ipset-{service}.txt` изменился после применения. Списки берутся только из запечатанного `source.ipset_sha256` / `source.ordinary_scope_ipset_sha256`, посторонние пути не принимаются. Существующий regression расширен на валидное состояние, подменённые Voice/ordinary IPSET и traffic/argv, исчезнувший IPSET. ТЗ/frontend, штатный Apply, процессы и IPFW не изменены; живой FreeBSD STUN/MEDIA/CALL по-прежнему требует испытаний, релиза нет.

**`v0.5.2_105` — фактическое применение read-only reconciliation при утраченном native IPFW COMMIT receipt.** Приватный forward сразу после fsync `legacy-common-committing` по-прежнему вызывает **не более одного** штатного `apply_runtime_commit`. **`v0.5.2_104` — безопасное read-only завершение прерванного IPFW COMMIT живого общего владельца.** Доработана прежняя приватная `commit_native_common_after_legacy_config_save`: когда единый WAL уже содержит `legacy-common-committing`, повторное обращение под исходным FD9 и **актуальным** заблокированным Config inode **никогда** не вызывает `apply_runtime_commit`, `Config::save`, `activate` или rollback. Вместо этого оно повторно сверяет sealed старый Config/runtime backup и journal, затем вызывает только существующий `verify-committed`: проверку установленного native release, единственного dvtws2+monitor и итогового IPFW **без staging-таблиц**. При полном совпадении ранее потерянный final receipt можно завершить записью обычного `committed`; при остаточных таблицах, отсутствии процесса или иной неопределённости `legacy-common-committing` остаётся заблокированным без мутаций. В существующем Python suite добавлены отдельные случаи удачного read-only reconciliation, частичного IPFW и недоступного нового engine; повторное завершение отвергается. **Граница:** это reconciliation только пока verified common runtime жив; cold reboot и частичная очистка по-прежнему требуют отдельного безопасного механизма. Не подключено к CLI/configd/GUI, публичная миграция/релиз закрыты, ТЗ и frontend неизменны.
