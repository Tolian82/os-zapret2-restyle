# 2026-08-08 — v0.3.3_27 Stage-40 DNS deadline correction

## Trigger

Owner-assisted Scenario-1 testing of published `v0.3.3_26` repeatedly stopped at Stage 40
with the required DNS endpoint reported unresolved. The initial diagnostic job was
`job.Cs5ryG` against `rutracker.org`.

## Live diagnosis

`baseline-evidence.json` records a real Python subprocess timeout, not a parser rejection:

- `/usr/bin/drill rutracker.org A`;
- `duration_ms=2024`;
- `returncode=null`;
- `timed_out=true`;
- `classification=timeout`;
- no stdout/stderr before termination.

The owner demonstrated that the same resolver at `127.0.0.1` sometimes returns immediately
and sometimes takes about 8–10 seconds before returning valid A answers. Five additional
Strategy Lab attempts reproduced the Stage-40 stop.

The `_26` diff did not touch Stage-40 request/probe code, so the `_21` ANSWER-section parser
fix was not lost. Source inspection instead found two nested deadlines: 2 seconds for the
DNS subprocess and 5 seconds for the whole Stage-40 adapter.

## Corrective implementation

Created package candidate `_27` and changed only the Stage-40 DNS deadline envelope:

- `request.py`: shared DNS timeout is 15 seconds for `dns_request()` and the compatibility
  `request dns` operation;
- `orchestrator.py`: Stage-40 operation limit is 20 seconds;
- overall Standard budget remains 150 seconds;
- resolver selection and parser/classification behavior are unchanged.

Focused tests add a deliberately slow valid DNS answer beyond the old two-second cutoff,
retain a genuine over-deadline timeout case, and assert the enclosing Stage-40 limit.

## Documentation/live gate

The `_26` evidence is now the current owner-tested boundary. Scenario 1 remains failed and
selects `_27` as the corrective source candidate. The prior `_26` Stage-50 correction is
not marked live-fixed because the `_26` runs did not reach Stage 50.

The misleading `PARTIAL` summary wording observed after the early Stage-40 stop is recorded
as a separate follow-up and intentionally excluded from `_27`.

## Delivery

The source change proceeds through the ordinary Ready-PR workflow. No `_27` tag, Release,
Pages or pkg-repository publication is implied by the source patch itself.
