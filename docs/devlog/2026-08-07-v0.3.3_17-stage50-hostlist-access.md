# v0.3.3_17 — Strategy Lab post-drop hostlist access

Date: 2026-08-07
Scope: one live-proven stage-50 temporary-runtime defect.

## Live trigger

Owner-assisted Scenario 1 on installed `v0.3.3_16`, job `job.VmWk32`, again passed
stages 00–40 and stage 90 but failed stage 50. `_16` did, however, create the full
candidate-runtime working set and started dvtws2 far enough to expose the exact next
failure.

Evidence:
`docs/verification/evidence/2026-08-07-v0.3.3_16-scenario-01-stage50-hostlist-access.md`.

## Root cause

The temporary dvtws2 process initially loads its hostlist as root, binds divert port 9989,
then applies `--user=nobody`. Its post-drop file check immediately fails:

```text
Running as UID=65534 GID=65534
file_open_test: Permission denied
cannot access hostlist file '.../candidate-runtime/hostlist.txt'
```

The hostlist is already mode 0644. The problem is the random parent job directory: the
launcher creates it with `mktemp -d`, so it begins private. A readable file nested below a
non-searchable parent remains inaccessible after dvtws2 drops privileges.

## Correction

- keep Strategy Lab job directories private (0700) by default;
- only for a running hostlist-backed candidate, grant search-only traversal (0711) on the
  random job directory and keep candidate-runtime traversable;
- leave the hostlist itself mode 0644;
- restore the job directory to 0700 on every candidate cleanup path;
- strengthen the production candidate-runtime regression so it starts from a 0700 job
  directory, models dvtws2 as a non-owner/non-group post-drop process, requires hostlist
  traversal to succeed, and proves the job directory returns to 0700 after cleanup;
- advance package revision to `_17`.

The access change is deliberately temporary. It does not make the job directory listable
to non-owner users and it restores the private state after each candidate.

recorded but intentionally not mixed into this runtime-access patch.
