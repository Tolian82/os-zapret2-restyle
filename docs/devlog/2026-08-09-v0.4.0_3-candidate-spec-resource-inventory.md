# 2026-08-09 — v0.4.0_3 adaptive-search `_29`

## Trigger

Focused `_28` owner testing proved that an empty Stage-50 acceptance set no longer blocks
Stage 60. The next approved slice was the representation/resource boundary required
before `_30` can safely add new candidates, semantic resource branches or variable
ranges.

## Source diagnosis

Python already owned candidate outcome and search decisions, but the active candidate
adapter still scanned every installed Lua file and injected `--out-range=-d10`. Exact
runtime strategy construction was therefore split across Python and shell, no immutable
candidate schema existed, and a job did not persist which installed Lua/fake resources
were actually available.

The replay adapter repeated the same resource/range preparation cases. Timeout and error
records could identify a catalog candidate but could not preserve a normalized candidate
or installed-resource identity.

## Implementation

Added `strategy_lab_py/resources.py` with immutable installed-resource records and one
job-scoped snapshot written before Stage 00. The inventory records complete installed
Lua/fake directory metadata, built-ins, inline capability and a deterministic identity.
Candidate resolution rejects missing or empty required resources while unrelated files
remain inventory evidence.

Added `strategy_lab_py/candidate_spec.py` with frozen normalized candidate, Lua-instance,
Lua-argument and BLOB-requirement records. It preserves action order, native argument
text, filters, ranges, resource classes, dependencies, provenance/search metadata and
exact profile/fragment rendering. BLOB-free, built-in, direct/aliased inline and installed
external forms are independently representable; candidates without an output range and
non-`-d10` values are regression-covered.

`candidate.py` now constructs the spec before a candidate attempt, writes exact runtime
arguments itself and invokes generic protocol firewall installation. `family.py`,
`search.py` and `extended.py` preserve the same spec/inventory evidence for timeout paths.
`orchestrator.py` creates the inventory immediately after the running job snapshot.

Both active candidate adapters are now system-action delegates. They contain no Lua/fake
directory enumeration, BLOB selection, selector replacement or range injection.

## Dependency review

The installed directory is always inventoried completely, but runtime initialization is
candidate-minimal. The upstream Zapret2 `zapret-antidpi.lua` header identifies
`zapret-lib.lua` plus `zapret-antidpi.lua` as the static desynchronization startup pair.
`zapret-auto.lua` describes dynamic automation/orchestration and is therefore not loaded
into every current static catalog candidate merely because it is installed.

## Regression boundary

Added a focused test for frozen identity, ordered Lua arguments, all four resource
classes, inline aliases, IPv6 representation, variable/absent ranges, missing resource
rejection, exact profile selector replay, immutable job inventory and shell-adapter
policy absence.

Existing candidate, family, orchestration and final-result fixtures now provide installed
resource trees and assert that runtime arguments load only declared dependencies while
inventory records unrelated installed resources. CI and FreeBSD package checks require
the new modules/test and execute the focused test with Python 3.13.

The local preparation environment provides Python 3.12 rather than the production 3.13.
Syntax compilation, the focused pure-Python contract, final-result structural regression,
shell syntax, live-matrix contract, FreeBSD package contract and diff checks pass locally.
Production-launcher integration remains assigned to the exact GitHub Linux/FreeBSD
Python-3.13 gates and is not reported as a local 3.13 PASS.

## Scope retained for `_30` and later

`_29` deliberately does not add a search graph, golden corpus, new catalog rows, range
neighbors, endpoint epochs, telemetry, deadline changes, fail-fast stability, deep GET or
warm runtime. Current catalogs still carry `-d10` as candidate data and current QUIC/cold
execution behavior remains unchanged.

`VERSION` remains `0.4.0`; `PLUGIN_REVISION` advances once from `2` to `3`. Latest
published and owner-tested testing candidate remains `v0.4.0_2`; `0.4.0_3` is the source
candidate until separately authorized publication/live evidence says otherwise. `_30` is
the next independent source cycle.
