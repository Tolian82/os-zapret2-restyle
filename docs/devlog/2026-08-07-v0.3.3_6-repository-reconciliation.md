## Stage-50 corrective finding

The `_5` symptom is narrower than a generic candidate startup failure. Stage 50 reported `Temporary candidate runtime failed internally.` rather than `Temporary candidate result was not produced.`. Therefore the candidate runner had already produced its result file and returned non-zero afterwards.

Source inspection found an ownership mismatch in candidate teardown:

- startup/readiness accepts the temporary dvtws2 by reading the job-owned PID file and validating that exact PID, executable and `--port=9989` command identity;
- teardown ignored that already-proven owner and attempted to rediscover the process only through a global `ps ax` snapshot before sending TERM/KILL;
- if the pid-specific identity remains valid while the global process snapshot omits or formats the child differently, the divert listener remains active and cleanup returns failure after a valid candidate result was already written.

The `_6` stage-50 correction makes the job-owned PID file the primary termination and absence authority. TERM and, when required, KILL are sent first to that PID only after the same executable/port identity validation used by readiness. The global process scan and socket discovery remain secondary evidence. Cleanup still succeeds only after the owned PID is gone, no matching candidate process remains, and the divert port is absent.

A focused regression deliberately keeps pid-specific identity valid while both global process and socket discovery omit the candidate. The corrected teardown must still terminate the owned candidate, remove the PID file and prove runtime absence. The previous implementation could falsely declare the runtime absent and discard the ownership file.

The stage-50 correction passed full repository CI and FreeBSD 15 package verification and was squash-merged to `main` as `808d77bcdb4f9e5fb63f94985d01144e7f2216a4`. The verified Actions artifact for its exact PR head is `8980523385`, package `os-zapret2-restyle-0.3.3_6.pkg`, ABI `FreeBSD:15:amd64`, architecture `freebsd:15:x86:64`.

This is a repository/source correction for the confirmed stage-50 failure class. It is not a live OPNsense PASS.

## Stage-90 restoration-path finding

The `_5` stage-90 failure is also supported by a concrete source timing defect rather than only a generic restoration error.

Before this correction, Strategy Lab wrapped the normal service start in `STRATEGY_LAB_RESTORE_TIMEOUT=15`. The normal service path itself contains bounded waits that can legitimately exceed that outer limit:

- `launcher_start_once` waits up to 10 seconds for the dvtws2 PID;
- it then applies a default 5-second startup stability window;
- `supervisor_start` can then wait up to another 5 seconds for the supervisor;
- configuration rendering, runtime generation/validation/activation and firewall installation happen in the same native start transaction around those waits.

Therefore the outer 15-second restoration timeout could terminate a valid native start transaction before its own bounded startup sequence had completed. The `_5` live evidence is consistent with that failure mode: the normal firewall evidence had returned while both child and supervisor were false, leaving semantic state `INCOMPLETE`.

The `_6` restoration-path correction:

- raises the default bounded restoration-start window to 45 seconds so it exceeds the complete normal native startup waits instead of truncating them;
- after any nonzero or semantically incomplete first start, checks the actual service state rather than trusting only the outer command status;
- accepts a service that actually reached healthy RUNNING even if the outer command returned nonzero at the boundary;
- otherwise normalizes `INCOMPLETE` to verified STOPPED and permits exactly one second bounded start attempt;
- if the second start still fails, performs a best-effort bounded normalization to STOPPED rather than intentionally leaving a known incomplete runtime;
- retains mandatory semantic verification and truthful `RESTORE_FAILED` when healthy RUNNING plus the original runtime/config/firewall evidence cannot be re-established.

The recovery is deliberately finite: maximum two start attempts, never an automatic loop.

A focused regression covers three cases: interrupted first start followed by one successful recovery, a nonzero outer result whose service nevertheless reached RUNNING, and two failed starts that must return failure after safe STOPPED normalization. No repository test is allowed to turn that source correction into a live OPNsense PASS.
