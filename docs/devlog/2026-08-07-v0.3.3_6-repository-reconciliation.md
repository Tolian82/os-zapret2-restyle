## Stage-50 corrective finding and closure

The `_5` message `Temporary candidate runtime failed internally.` was narrower than a generic candidate-start failure: the candidate runner had already produced its result file and returned non-zero afterwards.

Source inspection found an ownership mismatch in candidate teardown:

- startup/readiness accepted temporary dvtws2 by reading the job-owned PID file and validating that exact PID, executable, and `--port=9989` command identity;
- teardown abandoned that already-proven owner and attempted to rediscover the process through a global `ps ax` snapshot before TERM/KILL;
- pid-specific identity could remain valid while secondary process/socket discovery omitted or formatted the child differently, producing post-result cleanup failure or an unsafe false absence conclusion.

The `_6` correction makes the job-owned PID file the primary termination and absence authority. TERM and, when required, KILL target that PID only after the same executable/port identity validation used by readiness. Global process and socket discovery remain secondary evidence. Cleanup succeeds only after the owned PID is gone, no matching candidate process remains, and the divert port is absent.

Focused regression `scripts/test-strategy-lab-candidate-owned-pid-cleanup.sh` deliberately keeps pid-specific ownership valid while both secondary discovery paths omit the candidate. The corrected teardown must still terminate the owned process and prove absence.

## Stage-90 restoration-path finding and closure

Before the correction, Strategy Lab wrapped normal restoration in `STRATEGY_LAB_RESTORE_TIMEOUT=15`. The native service start itself can legitimately spend:

- up to 10 seconds waiting for the dvtws2 PID;
- a default 5-second startup stability interval;
- up to another 5 seconds waiting for the supervisor;
- additional bounded time rendering, validating and activating runtime state and installing firewall rules.

The outer 15-second restoration timeout could therefore terminate a valid native start transaction before its own bounded startup sequence completed. The `_5` live evidence is consistent with that failure mode: normal firewall evidence had returned while child and supervisor were false, leaving semantic state `INCOMPLETE`.

The `_6` restoration correction:

- raises the default bounded restoration-start window to 45 seconds so the outer bound can contain the complete native startup transaction;
- inspects actual semantic service state after a nonzero outer start result instead of treating the command status alone as semantic proof;
- accepts healthy RUNNING if native start completed at the boundary;
- otherwise normalizes `INCOMPLETE` to verified STOPPED and permits exactly one second bounded start attempt;
- after a second failure, performs best-effort bounded normalization to STOPPED instead of deliberately retaining a known incomplete runtime;
- preserves mandatory semantic verification and truthful `RESTORE_FAILED` when healthy RUNNING plus original runtime/config/firewall evidence cannot be re-established.

The recovery is finite: maximum two start attempts, never an automatic restart loop.

Focused regression `scripts/test-strategy-lab-restoration-recovery.sh` covers interrupted-first-start recovery, late healthy completion, and two failed starts with safe STOPPED normalization. Existing e2e `restore_failure` remains strict: a deliberately corrupted final semantic hash must still end as `error/RESTORE_FAILED`. During PR validation its generic failure reporting was made diagnostic so future mismatches expose actual state/outcome/stage; the expected failure semantics were not weakened.
