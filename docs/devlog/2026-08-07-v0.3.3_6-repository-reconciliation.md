## Stage-50 corrective finding

The `_5` symptom is narrower than a generic candidate startup failure. Stage 50 reported `Temporary candidate runtime failed internally.` rather than `Temporary candidate result was not produced.`. Therefore the candidate runner had already produced its result file and returned non-zero afterwards.

Source inspection found an ownership mismatch in candidate teardown:

- startup/readiness accepts the temporary dvtws2 by reading the job-owned PID file and validating that exact PID, executable and `--port=9989` command identity;
- teardown ignored that already-proven owner and attempted to rediscover the process only through a global `ps ax` snapshot before sending TERM/KILL;
- if the pid-specific identity remains valid while the global process snapshot omits or formats the child differently, the divert listener remains active and cleanup returns failure after a valid candidate result was already written.

The `_6` stage-50 correction makes the job-owned PID file the primary termination authority. TERM and, when required, KILL are sent first to that PID only after the same executable/port identity validation used by readiness. The global process scan remains as a secondary sweep for duplicate or stale candidate processes. Cleanup still succeeds only after both candidate-process absence and divert-port absence are proven, so the change does not weaken the safety gate.

A focused regression deliberately exposes the process through pid-specific inspection while omitting it from the global process list. The corrected teardown must terminate the owned candidate, remove the PID file and prove runtime absence. The previous implementation fails that fixture.

This is a repository/source correction for the confirmed stage-50 failure class. It is not a live OPNsense PASS. Stage 90 remains a separate confirmed defect and is not declared fixed by this patch.
