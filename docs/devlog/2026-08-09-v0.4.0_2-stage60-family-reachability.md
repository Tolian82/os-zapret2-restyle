# 2026-08-09 — v0.4.0_2 adaptive-search `_28`

## Trigger

After v0.4.0 release/installation, the approved adaptive-search implementation series
starts with `_28`: remove the Stage-50 accepted-family hard gate without combining this
work with the later candidate/resource/search-graph redesign.

## Source diagnosis

Python already owns automated Stage-60 policy. Its `search.expand()` loaded Stage-50
`accepted`, converted it to a set and selected only catalog rows whose family was in that
set. The explicit `no_accepted_family` early return made an all-rejected Stage 50 produce
zero Stage-60 candidate attempts.

This is a search-policy gate rather than a candidate-runtime or lifecycle defect. The
shell expansion helper still contains the historical behavior but is not the active
automated owner; the production expansion runner launches Python.

## Implementation

`search.expand()` now creates a stable accepted-first ordering and appends all remaining
catalog rows. Stage-50 evidence therefore influences priority only. With no accepted
families the selected rows are simply the complete catalog in its existing order.

The obsolete `no_accepted_family` Stage-60 result is no longer produced by the Python
owner. An actually empty catalog converges to the existing `catalog_exhausted` result.

The Stage-60 running/error text was updated so current presentation no longer describes
the stage as accepted-family-only. No candidate syntax, runtime adapter, budget, timeout,
early-stop or final-result schema changed.

## Regression boundary

The Python search/extended core fixture now verifies:

- accepted family evidence is tried first even when its catalog row appears later;
- a rejected family remains reachable and executes afterward;
- an all-rejected Stage-50 fixture still enters Stage 60 and reaches a working candidate;
- Stage-70 stability replay continues from that Stage-60 result.

The legacy shell parameter-expansion test remains only a compatibility fixture and its
PASS text now says explicitly that Python owns active Stage-60 policy.

The lifecycle integration fixture also injects its existing mock candidate runner into
Python Stage 60. Before `_28`, its all-rejected Stage-50 path returned before expansion;
after `_28`, that path is intentionally reachable and must not fall through to the real
candidate runtime during a lifecycle-only test.

Preparation-tree checks passed for shell syntax, the legacy compatibility fixture, the
risk-based live-matrix contract, corrective-matrix discovery, FreeBSD-15 CI contract,
repository hygiene and GitHub workflow/hygiene. The local preparation environment has
Python 3.12 rather than the required Python 3.13, so the changed Python 3.13 functional
fixture is intentionally left to the normal GitHub CI/FreeBSD qualification gate rather
than being reported as a local PASS.

## Delivery/live boundary

`VERSION` remains `0.4.0`; `PLUGIN_REVISION` advances once from `1` to `2`. This source
cycle authorizes the ordinary Ready-PR/CI/squash flow only. No prerelease tag or package
publication is implied.

After an explicitly authorized `v0.4.0_2` testing publication, focused OPNsense evidence
should prove non-zero Stage-60 attempts after an all-rejected Stage 50 and exact Stage-90
restoration. Until then `_27` remains the latest owner-tested Strategy Lab evidence and
`_29` remains queued rather than started.
