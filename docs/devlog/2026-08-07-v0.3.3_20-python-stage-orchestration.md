# 2026-08-07 — v0.3.3_20 Python stage orchestration

Migration Patch 3 continues the approved Strategy Lab Python transition after `_19`
made Python the authoritative automated-job persistence owner.

## Implemented ownership cutover

The production outer boundary remains compatible:

```text
zapret_service.sh
  -> strategy_lab_worker.sh
  -> strategy_lab_python_launcher.sh
  -> strategy_lab_python.py orchestrate JOB_ID
  -> strategy_lab_py/orchestrator.py
  -> strategy_lab_stage_adapter.sh for still-unmigrated stage operations
```

`strategy_lab_worker.sh` no longer sources or owns the shell stage machine, budget,
cancellation, watchdog, or terminal-control graph.

Python now owns:

- deterministic stage progression;
- Standard/Extended wall-clock budgets and per-stage remaining-time arbitration;
- stage-80 shared deadline;
- cancellation/signal handling and adapter process-group termination;
- timeout classification at the stage-machine boundary;
- terminal state/outcome/report mapping;
- mandatory stage 90 restoration and stage 99 terminal convergence.

The shell stage adapter remains deliberately narrow. It reuses audited lifecycle and
FreeBSD helpers and invokes the existing stage-specific algorithms that are scheduled for
Patch 4–6 migration. It returns a structured one-action result to Python and does not
choose the next stage or final outcome.

The shared lifecycle lock is preserved through inherited fd 9. The active-job PID
contract now accepts the Python `orchestrate` process as the authoritative automated-job
worker owner.

## Compatibility preserved

- schema-2 automated-job state;
- Patch-2 Python revision/progress/event ownership;
- stage numbers and progress percentages;
- existing API/configd entry points;
- existing evidence paths;
- private circular-session shell state ownership;
- saved Traffic Strategy immutability.

No request/probe parser, candidate/family algorithm, expansion/stability algorithm, or
extended-protocol algorithm is migrated in this patch.
