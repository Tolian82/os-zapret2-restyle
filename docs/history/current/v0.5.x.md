# v0.5.x — current working ledger

## 2026-10-13 — v0.5.2_5, общий engine/IPFW switch (внутренний этап 3)

В общий service module chain добавлен `backend/apply_runtime.sh`. Он использует полный candidate общего generator, прежний atomic/launcher/supervisor и release-derived IPFW adapter. Перед изменениями сверяется процессная и firewall ownership. `activate` оставляет previous runtime и IPFW stage до подтверждённого штатного Config save, `restore` проверяет rollback, `commit` чистит stage после успешного save. Изолированный shell test проверяет ON/update/rollback/OFF/first start и отказы. Чужие правила, неполный процессный состав и работающая legacy конфигурация не принимаются без миграции.

Функции ещё не подключены к публичным кнопкам и не дают crash recovery. Полный native Config worker, отказ при interrupted transaction и OPNsense/live acceptance остаются следующим шагом. Никакой новый Voice daemon или второй persistent preferences writer не создан.


## 2026-10-13 — v0.5.2_4, общий PHP candidate/dependency boundary (этап 3)

Обе действующие формы `SettingsController` и `VoiceController` переключены на чистую `SettingsApply`-подготовку, которая не изменяет native Config или runtime. Strategies overlay ограничен прежним whitelist и raw baseline Telegram; Voice использует прежний пятисервисный валидатор и общий snapshot. Обе стороны получают full-model candidate, изменённые поля и dependency SHA-256. Проверка generation предназначена для повторения внутри будущего привилегированного Apply после нового Config lock, не является разрешением на persistence по одному browser token. PHP тест обеих форм проверяет защиту чужих Voice-настроек, stale Telegram, изменённые runtime-зависимости и независимую правку strategylab.

Исследование OPNsense Core Config показало, что `Config::save()` снимает flock и штатно вызывает revision/backup/config event; нельзя переносить прежнее владение lock через save. Версия platform source и реальный запуск на OPNsense подтверждаются отдельно до включения privileged worker. Штатный GUI ON ещё не разрешён, общие IPFW/activation и полноценный откат не подключены. Frontend, ТЗ и установленный appliance не изменяются; PR остаётся Draft, release/testing package не публикуется.

## 2026-10-13 — v0.5.2_3: общий firewall полного release

`firewall_shared_runtime` использует существующие bounded IPFW adapter/transaction функции и производное владение из предыдущего/кандидатного общего release, без `VoiceOwnershipStore` или новой persistent схемы. Install сохраняет prior table contents до общего commit, rollback возвращает их при отказе runtime/Config, commit удаляет проверенные stage/retired таблицы. First start и Stop выражаются пустым observed/desired manifest. Native CLI требует FreeBSD root и исходный удерживаемый FD9; общая attestation вынесена в adapter с compatibility wrapper прежнего executor.

Сквозной full generator → injected IPFW прошёл all-five/update/repeat/all-OFF/Stop/rollback и сохранение чужих объектов. Семантическая сверка обнаруживает команды, вернувшие успех без нужного изменения, в install/restore/cleanup. В runtime/GUI новый путь подключается этапом 3; reboot/crash/live capture не объявляются пройденными. Frontend и разделы 1–11 ТЗ сохранены.

В этой же поставке исправлена конкретная FreeBSD CI ошибка `_2`: common-runtime fixture теперь даёт generic `python3` и `python3.13` одному установленному интерпретатору, поскольку строгий existing IPSET normalizer вызывает `python3`. Повтор изолированного сценария с ограниченным PATH проходит локально; FreeBSD 3.13 подтверждает CI. Локальные Python проверки выполнены на 3.12; PHP parity здесь не запускалась успешно из-за отсутствующего PHP и проверяется обязательным GitHub CI.
