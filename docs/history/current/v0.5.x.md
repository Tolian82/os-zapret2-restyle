# v0.5.x — current working ledger

**Решение владельца 15.10.2026: сначала завершить программирование по ТЗ, потом один тестовый релиз и живые испытания.** Новый [короткий контроль завершения](../../VOICE_CODE_COMPLETION_GATE.md) — текущая очередь проекта; **не выпускать** тестовый/stable release и не устанавливать промежуточные ревизии на OPNsense. Пункт «проводить FreeBSD live испытания сейчас» в старых заметках больше не является немедленным следующим действием. `v0.5.2_121` остаётся Draft/неопубликованным кандидатом. Попутно исправлены две относительные ссылки, блокировавшие `_121` CI artifact hygiene; VERSION/PLUGIN_REVISION не изменяются (только документация).

**`v0.5.2_121` — подготовлена проверка реального прохождения Voice UDP на FreeBSD OPNsense без вмешательства в службу.** Новый небольшой read-only `voice_live_trial.py` использует существующий `SharedApplyOperation` и `voice_live_inspect.examine_shared` (только `committed/ready` общий владелец), читает `/sbin/ipfw -a list`, извлекает исключительно счётчики принадлежащих Voice правил и повторно проверяет неизменность владельца. Режим `snapshot` формирует JSON, режим `compare` сопоставляет два снимка до/после **ручного** Telegram-вызова, отказывает при смене owner/правил, потере IPFW или сбросе счётчиков. Рост счётчиков означает **только совпавший исходящий UDP**, не STUN-ответ, медиатрафик или успешный звонок (`stun_verified/media_verified/call_verified=false`). Никаких рестартов, ipfw zero, pcap, новых демонов или изменений frontend/ТЗ. Добавлены маленький offline regression для Linux/FreeBSD CI и [инструкция реальной приёмки](../../VOICE_LIVE_TRIAL.md). **Реальные STUN/MEDIA/CALL и GUI/CONFIG/BOOT пока не подтверждены**; Draft PR, без merge/release.

Теперь read-only проверка common owner требует точного совпадения файлов `voice-plan.json`, `dvtws.args`, `traffic.conf`, управляемых IPSET включённых Voice-служб и управляемых IPSET, по которым обычный STUN «Стратегий» прошёл проверку при stage (включая службы с выключенной галочкой Voice). Списки берутся только из запечатанного `source.ipset_sha256` / `source.ordinary_scope_ipset_sha256`, посторонние пути не принимаются. При расхождении статус становится `unverified-release`, `engine_verified=false`, без автоматического перезапуска или изменения IPFW. Существующий regression расширен на валидное состояние, подменённые Voice/ordinary IPSET и traffic/argv, исчезнувший IPSET. ТЗ/frontend, штатный Apply, процессы и IPFW не изменены; живой FreeBSD STUN/MEDIA/CALL по-прежнему требует испытаний, релиза нет.

После проверки вызывается **только прежний** `firewall_shared_runtime commit` (идемпотентная очистка подтверждённых стадий), затем два `verify-committed` и терминальный shared journal; без Config save, запуска engine и повторной установки правил. Ошибки сохраняют pending и старый backup, автоматического обхода нет. Добавлены регрессии на частичное завершение и конфликты; ТЗ/frontend неизменны, FreeBSD owner-live STUN/MEDIA/CALL и полная приёмка ещё впереди, релиза нет.

**`v0.5.2_105` — фактическое применение read-only reconciliation при утраченном native IPFW COMMIT receipt.** Приватный forward сразу после fsync `legacy-common-committing` по-прежнему вызывает **не более одного** штатного `apply_runtime_commit`. **`v0.5.2_104` — безопасное read-only завершение прерванного IPFW COMMIT живого общего владельца.** Доработана прежняя приватная `commit_native_common_after_legacy_config_save`: когда единый WAL уже содержит `legacy-common-committing`, повторное обращение под исходным FD9 и **актуальным** заблокированным Config inode **никогда** не вызывает `apply_runtime_commit`, `Config::save`, `activate` или rollback. Вместо этого оно повторно сверяет sealed старый Config/runtime backup и journal, затем вызывает только существующий `verify-committed`: проверку установленного native release, единственного dvtws2+monitor и итогового IPFW **без staging-таблиц**. При полном совпадении ранее потерянный final receipt можно завершить записью обычного `committed`; при остаточных таблицах, отсутствии процесса или иной неопределённости `legacy-common-committing` остаётся заблокированным без мутаций. В существующем Python suite добавлены отдельные случаи удачного read-only reconciliation, частичного IPFW и недоступного нового engine; повторное завершение отвергается. **Граница:** это reconciliation только пока verified common runtime жив; cold reboot и частичная очистка по-прежнему требуют отдельного безопасного механизма. Не подключено к CLI/configd/GUI, публичная миграция/релиз закрыты, ТЗ и frontend неизменны.

**`v0.5.2_103` — проверка legacy lifecycle после terminal native COMMIT.** CI `_102` подтвердил, что новая native IPFW COMMIT-последовательность доходит до финального общего journal owner. Два прежних ожидания в `test-shared-apply-operation.py` ошибочно предполагали `safe_to_mutate=True` для **устаревшего legacy lifecycle** при фазе `committed`. По действующему `voice_cutover_guard.check_pending` этот lifecycle ОБЯЗАН оставаться заблокированным с причиной `shared-runtime-owned`, иначе после reboot может появиться второй dvtws2. Обычный `start/reconfigure` автоматически разрешает этот точный случай перед guard; при неудаче или фазе начиная с `activating` блокируется без legacy fallback. CI моделирует успешное восстановление, провал attestation и отказ на постмутационной фазе. Pending после kernel/runtime/Config изменения требует дальнейшей разработки точного recovery, а public Voice ON пока не подключён.
