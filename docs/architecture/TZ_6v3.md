## 2. Текущий функционал и пять записей реестра

| ID | Тип / владелец | Нынешнее место хранения |
| --- | --- | --- |
| `youtube_manual` | ручной HOSTLIST | Config `hostlist.youtubedomains` |
| `youtube_found` | автонайденные YouTube, редактируются пользователем | защищённый `auto-detect-owned/youtube.txt` |
| `user_manual` | ручной HOSTLIST | Config `hostlist.userdomains` |
| `user_found` | автонайденные User, редактируются пользователем | защищённый `auto-detect-owned/user.txt` |
| `shared_found` | общий автонайденный | защищённый `ipset/auto-domains.txt` |

Реестр для страницы «Стратегии» описывает `id`, `kind=hostlist`, `owner`, `storage_kind=config|file`, привязку платформенного поля/защищённого файла, политику проверки, status/revision и соответствие существующему целевому `HOSTLIST` Zapret2. **Не заменять** target registry `backend/registry.sh` и не менять семантику источников/обнаружения. Текущий каталог — только пять записей; код итерации не должен быть зашит на число пять. Новые реальные цели в текущем ТЗ не добавляются.

## 3. Чтение: единый версионированный API

- Штатная OPNsense Model загружает **полное сохранённое содержание двух ручных полей** непосредственно в GUI. При согласованном root-read через Config/P2 блокировки API отдаёт для них только ID, owner, status, **байтовую длину и SHA-256** сохранённого текста плюс версию Config. Не передавать второй экземпляр огромного текста через configd в JSON.
- Исходный текст (baseline) и текущий пользовательский черновик различаются: проверка baseline по байтам/хэшу не может подменять ввод. При несовпадении версия не принимается и несохранённые изменения не стираются.
- Для трёх найденных источников API возвращает **реальное содержимое** защищённых текстовых файлов, статус и SHA-256. `empty`, `missing`, `uninitialized`, error нельзя сводить к фиктивному пустому. Пустой `shared_found` отображается, даже если отдельный source ошибочен; **неполный снимок не разрешает Apply**.
- На F5/загрузке страницы GUI читает исходные версии. Неизменённый вид/размер полей, справка и существующий общий статус сохраняются. Запрещены запись/инициализация файлов при чтении.

## 4. Сохранение: единый FormData + JSON для всех пяти

- **YouTube Domains и User Domains тоже переводим на общий протокол**, как и будущие аналогичные ручные HOSTLIST. Браузер отправляет один `FormData` для обычного нижнего Apply. В нём — JSON-манифест со схемой/версиями/ID/статусами и **фактические изменения** только затронутых списков: точный новый текст (обычное поле/Blob) либо компактная проверяемая дельта против SHA исходного списка. SHA-метаданные **не заменяют** изменённый текст.
- Три найденных списка участвуют в том же реестре и заявке; адаптировать уже существующие `found-intent.json` / `SharedApplyFoundIntent` / root staging, а не делать параллельный механизм записи. Списки без изменений не пересылаются огромным payload в `configd` и не перекладываются в argv: прежний `SharedApplyEnvelope` ограничен 65 536 символами и расширяет SHA-дельту под FD9.
- Прежняя единственная кнопка «Применить» и защищённый original FD9 + Config lock + P2 WAL + rollback/сервисный lifecycle остаются единственными хозяевами записи. Нормализация через существующий Python domain-policy/PSL/IDNA и ручные `!/^/!^` остаётся штатной. Минутный Auto-detect не останавливает dvtws2.
- Изменять действующие проверки согласованности **только там, где новый контракт этого требует**, сохраняя отказ от stale/mismatched source и несохранённый черновик. Полная переделка всего tracking и concurrency отложена.

## 5. Не входящие в это ТЗ и хранение

- Реально сейчас **только OPNsense и Стратегии**. **IPSET Telegram**, другие IPSET, **«Исключить домены»**, **«Исключить IPSet»**, «Передача голоса», Strategy Lab, WAN, CSS/UI layout, остальные формы и жизненный цикл не переделываем. Exclude Domains остаётся входом прежней доменной политики и Apply, не дополнительным HOSTLIST в реестре.
- **Не переносить** текущие ручные значения из `config.xml`; автонайденные остаются в обычных защищённых `.txt`. Оба типа storage можно описывать в каталоге, но делать файловую миграцию вручную не нужно.
- **Не увеличивать глобальные лимиты PHP** (post_max_size, upload_max_filesize, memory_limit или php.ini). `FormData` — GUI→HTTP, сам по себе не лечит root-read и не обходит POST лимиты. Исправить собственные несогласованные 1-МиБ проверки продукта в рамках проверенных конечных лимитов Python/OPNsense, измерить реальный HTTP/Config/argv budget; не выключать проверки.
- Не создавать второй writer `config.xml`, SQLite, новый daemon, собственный uploader вне общего Apply или обязательную многозапросную chunk-систему. 6–8 списков **в сумме**, а не 17, с примерно тем же общим числом доменов — **только дальнейший потенциал**, не новые поля сегодня.

## 6. Шаги внедрения и приёмка

1. **S0: воспроизведение старой ошибки** — настоящий путь 1 774 109 байт User + пустой shared, красный тест на `_94`, без вмешательства в OPNsense владельца.
2. **S1: общий реестр** — пять записей с валидаторами, owner/storage/target, без нового engine registry и без новых полей.
3. **S2: корневой read + GUI** — метаданные больших ручных вместо дублирующего JSON, настоящий текст found, F5 и сохранение черновиков; безопасный пустой shared виден.
4. **S3: единый multipart/JSON транспорт** — перенос YouTube/User в тот же подход, что found, с reuse существующих SHA-дельт/`found-intent` и единственным original FD9 Apply; текст произвольно редактируется.
5. **S4: целевая проверка** — маленькие/большие/пустые списки, F5, неправильная версия, оба ручных edits, found edits, RUNNING/STOPPED, terminal journal, сохранение IPSET/Exclude/Voice без изменённой логики.
6. **S5: пакет и приёмка** — только затронутые точные CI/нативные FreeBSD 15 проверки, merge, публикация новой тестовой `.pkg` по принятым правилам, затем отдельное подтверждение на OPNsense владельца. #1190 закрывается только после реального подтверждения чтения и Apply.

Статус на момент публикации ТЗ: **ТЗ согласовано, источник и пакет не исправлены, S0–S5 открыты**. Дополнительные направления — [Future](STRATEGIES_LIST_FUTURE.md) и [Issue #1192](https://github.com/Tolian82/os-zapret2-restyle/issues/1192).
