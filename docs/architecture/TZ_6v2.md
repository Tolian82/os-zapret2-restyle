## 1. Observable result and invariants

- The Strategies page exposes **five editable domain lists** grouped as two manual/automatic pairs and one shared automatic fallback. The existing primary “YouTube Domains” and “User Domains” fields retain their separate `config.xml` model references and their manual-data semantics. The two automatically discovered companion editors unfold underneath their respective primary fields. The shared “Найденные домены” / “Auto Hostlist” is a full-sized third automatic editor.
- All five list values and their validation/read revisions are loaded **on opening or refreshing the page**, even for collapsed companion panels; opening a panel requires no additional read and does not mutate data. A page left open does not overwrite unsaved edits with background polling. F5 performs a new read.
- **Exactly one existing bottom “Применить” / “Apply”** applies all edited fields. Do not create a second Apply. Remove the independent “Сохранить список” / “Save List” and “Обновить список” / “Reload List” controls and the ordinary “Список пуст” / “List is empty” caption from the shared editor. Keep real error, conflict and validation diagnostics.
- The button executes the **ordinary native shared Strategies Apply/reload and its existing, intended Zapret2 plugin service restart lifecycle**, also when only automatic files were edited. A validation preflight is not a replacement for the lifecycle/rollback protocol. **No special file-only, no-restart Apply mode is authorized.** The owner explicitly accepts ordinary restarts caused by an intentional click.
- The unattended 60-second Auto-detect worker is a different path. It updates the effective HOSTLIST files **without a service restart, SIGSTOP/SIGCONT or divert interruption**. Auto Restart is another distinct, independently selected scheduled operation.
- One existing original shared FD9 owner, real Config lock/writer, common generation/Apply rollback and existing GUI destination flock; no second Config writer, engine, daemon, package hook, process interrupter, independently invented service manager, duplicated domain parser or Strategy Lab changes.

## 3. Canonical domain grammar and normalization

Use the **existing** canonical Python `backend/domain_policy.py` (including IDNA, strict host syntax, ICANN+PRIVATE Public Suffix List and known policy) through established bridges. Do not introduce a PHP, JavaScript or shell competing parser.

1. **Manual YouTube/User:** unchanged ability to write a plain hostname, `!example.com`, `^example.com` or `!^example.com`. Preserve all valid user-selected modifiers. A `!example.com` in the corresponding **manual** list means a persistent policy prohibition on automated re-addition of that name and its covered subdomains by the background collector. `!^example.com` blocks only the exact name. The collector's cross-source broad/exact exclusion policy continues to apply; the native Zapret2 `!` remains a **local HOSTLIST exclusion** during engine evaluation (it is not a global Exclude Domains entry). Manual domain input is **not** automatically collapsed to registrable root merely because discovered data is.
2. **All three discovered-only editors:** plain normalized positive hostnames only; **`!` and `^` are forbidden**, including combinations, whether entered through the form or present in proposed auto-owned data. Only manual lists carry user exclusions and exact-match directives. Reject invalid manual editing with a clear field/line error; never silently strip a forbidden prefix into a positive domain. Existing experimental automatic files are **not compatibility/migration data**; explicit controlled empty reset/rebuild is permissible as specified in §8.
3. **Newly detected hostnames:** attribute to the proven source profile **before** collapse and reduce to their registrable domain (eTLD+1) with the qualified PSL (ICANN + PRIVATE). For example, `new.example.org` → **`example.org`**, `video.example.com` → **`example.com`**. The two distinct roots remain distinct: do not literally store either subdomain as a new automatic entry. Preserve private-suffix boundaries and refuse unknown/bare suffixes. This collapse applies to native discoveries, **not** an arbitrary user-authored manual domain.
4. Before any duplicate removal, parse and normalize all relevant lists. The order is: coherent five-list snapshot/revision → canonical syntax/IDNA/modifier checks → effective-coverage/exclusion-aware deduplication → canonical sort → final validation → protected commit → native Apply/reload. The existing parser's semantic treatment of exact versus broad inclusions and exclusions has priority over simplistic string equality.
5. **Known-list precedence:** remove a discovered YouTube duplicate already covered by its manual YouTube part, and likewise User versus manual User. For the shared fallback, remove automatic positives already accounted for by **either complete effective known HOSTLIST** (manual + its proven automatic part) in accordance with the original P1 source-identity and collision policy. A conflicting/ambiguous origin is handled by the original attribution/fallback rule and not guessed from text equality. Never relocate or remove a manual `!` or `^` entry. A manual exclusion vetoes a conflicting new automatic positive according to the existing broad/exact policy. All approved global exclusions remain separate.
6. **Sorting:** sort automatic positives alphabetically on every genuine automatic-list mutation. Sort a manual YouTube/User list **only when that manual field was actually edited**; an Apply changing an unrelated field must not touch its stored bytes or ordering. For a modified manual list, sort by the **entire normalized text line**, including leading characters: `!` and `^` entries precede ordinary names, not by a prefix-stripped domain key. Make the comparator deterministic on canonical ASCII/IDNA text. Sorting must not transform the meaning of a negative or exact entry. The original source profile and target priority/strategy ordering remain unchanged.
7. “Duplicate” means redundant **within equivalent coverage and the approved cross-source policy**; two strings naming the same root but having different semantic `!/^/!^` flags must not be dropped blindly. Show actionable conflicts and preserve the draft rather than guessing which of two contradictory user instructions wins.

## 4. Concurrent background discoveries and user editing

**Approved three-way resolution (owner chose variant A):** use (a) exact protected source snapshots and revision tokens acquired when the page opened, (b) the user's draft at Apply, and (c) the authoritative on-disk current sources read inside the existing Config+destination critical section.

- Compute the **user's intended additions/deletions/modifier changes relative to the original page snapshot**, after safe canonical parsing. Apply those user deltas to the **current** storage state, preserving **independently discovered positive domains** inserted after the page was loaded. If a domain visible in the original page was explicitly deleted by the user, that deletion wins for that domain even if an automatic writer touched it meanwhile.
- Example: original discovered list has `example.com`; the user deletes it; the minute worker adds `example.org`. After manual Apply, `example.com` is absent and `example.org` remains. The newly discovered host may not have been visible in the stale editor. A later *new* detection may re-add a plain deleted domain; to prohibit re-addition permanently the user writes the respective `!` rule in the **manual** list.
- If background data and manual edits produce an unresolvable semantic conflict, competing modification of the same protected entry, stale Config model, invalid ownership, unsafe FD/epoch or failed validation, **fail closed** with an explicit revision/conflict message and the user's exact typed draft retained. Do not replace the draft with the live file or silently drop confirmed background discoveries. No blind last-writer-wins overwrite.
- Revalidate duplicates/exclusions and fully normalized prospective contents under the same locks immediately **before** writing. The transaction must guard against the collector modifying one file after the snapshot but before committing all files. Reuse the original Config, GUI flock, FD9 and durable/atomic writer interfaces; lock order must be documented and consistent with the one-minute collector.
- The result is not required to byte-match the stale editor when independent new discoveries arrived. It **is** required to include the user's validated intended changes and all non-conflicting newly discovered positives. The new persisted baseline is returned on completed Apply/F5. Never mark a partially persisted operation as successful.

## 6. Native effective lists and zero-restart automatic detection

- **Mandatory end-to-end chain:** native observed domain → protected normalized/canonical automatic source → updated actual effective managed HOSTLIST file → **running original `dvtws2` demonstrably consumes the new entry without Apply or Restart**. - The one-minute collection and diagnostic raw/debug/generation maintenance continue without SIGSTOP/SIGCONT, dvtws2 stop/pause/implicit restart, or divert interruption. Four fully retired generation retention is a separate safety mechanism, not an Auto Restart prerequisite.
