# ТЗ_6v5 S10b2a — native legacy Apply fence + immutable PREPARED root attestation

**Основание:** [S10 #1319](https://github.com/Tolian82/os-zapret2-restyle/issues/1319) открыт; [S10a PR #1320](https://github.com/Tolian82/os-zapret2-restyle/pull/1320) и [S10b1 PR #1321](https://github.com/Tolian82/os-zapret2-restyle/pull/1321) GO; accepted main `v0.6.5_200 f4d317b4`. **S10b2a — подэтап, не окончательное S10 GO и не S11.**

## Проблема и граница

Исходный `zapret_service.sh::shared_apply_execute_service()` ещё использует legacy Apply без native S07/S08/S09 источника для нового JSON root. Его пред-Apply seal и `apply_runtime_probe` валидируют существующий runtime, но **не** дают права принимать новый sibling `manifest.json` как активное поколение. В `shared_apply_operation.py` уже есть S10b1-пин `manifest` в исходном `PREPARED`, который запрещает generic `advance("activating")`. Однако случай **наличия staged sibling root при ещё не привязанном journal** нуждается в защите непосредственно в исходном shell, иначе он может попасть на legacy physical path.

Особенно важно: оригинальный native `auto` проходит schema3 promotion и может модифицировать `dvtws.args` после исходного P2e/nonactivating map; S08c attestation нельзя просто объявить истинной для после-promotion bytes. Никакая новая ветка не угадывает эти соответствия, source-map или profile-first-match.

## Изменения в существующем owner

**`shared_apply_unbound_root_preflight_service`** — одно приватное shell-предусловие, не новый dispatcher/lock/daemon. Проверяет внутри заранее проверенного `shared_apply_workspace` ровно четыре пути: `manifest.json`, `.manifest.json.pending`, `release/manifest.json`, `release/.manifest.json.pending`. Любой inode или symlink (включая broken symlink) означает отказ; *никакой* автоматической очистки. Никакой обходной user-input path или новый Config writer; `bundle-seal.json` и остальные файлы исходного хозяина не изменяются.

Оно вызывается на трёх барьерах внутри того же исходного FD9: **перед seal verification и любым durable/Config/P1/IPFW действием** (стабильное `preflight-rejected=manifest-unbound`), **повторно непосредственно перед `PREPARED` / Found-save** (исключает root, появившийся во время preflight), и **перед original `record_current_service activating`**. Если файл появился *после* durable `PREPARED`, поздний отказ даёт код 70 и оставляет исходное незавершённое состояние для проверяемого восстановления. Не выдаёт `applied-id`, не переводит его в `COMMITTED` и не вызывает `apply_runtime_activate`. Если root нет, исходный legacy Apply byte-order, Voice/Strategies, WAN-only Save и предзапуск Lab не меняются.

**`neutral_root_bound_preflight.py`** — только чтение: сверяет schema-1 original `SharedApplyOperation(PREPARED)`/S10b1 `manifest` pin с двумя повторными S10a `attest_staged_candidate`, а те — с оригинальным seal, S09b physical bytes, S08c native proof и S08d effective semantics. Публичная внутренняя точка `attest_bound_under_fd9` принимает только фиксированные `shared_apply_seal.WORK` и `shared_apply_operation.DEFAULT_ROOT`, требует `voice_ipfw_adapter.require_lifecycle_lock()`, никогда не читает произвольный путь из root JSON. Положительный `BoundRootReceipt` **всегда** `authorization=NONE`, `physical_transition_allowed=False`, `promotion_allowed=False`, `native_owner_preflight_required=True`. Никакого CLI, нового WAL, Config writer, физического перехода или маркировки ACTIVE.

## Проверки и приёмка

В `scripts/test-tz6v5-s10b2a-original-unbound-fence.py` проверяются положительная read-only идентичность, SHA root/seal/candidate, повторная проверка/отсутствие записи, нет FD9, tamper release/root/pending, другая генерация/mode/native/Enabled, не-`PREPARED` и гонка журнала между двумя аттестациями. В **исходном** `scripts/test-shared-apply-execute.sh` по извлечённым настоящим функциям проверяются отказ sibling/release, pending, broken symlink, появление файла между preflight и `PREPARED`, а также появление *после* `PREPARED`. Проверяется порядок: для позднего отказа видна только одна исходная запись `record:prepared`, без `record:activating`, `runtime-activate` или `applied-id`. Существующие положительные сценарии old Apply должны оставаться PASS.

Требуются exact-head CI и проверка оригинального VM shell/native FD9, Project, Voice, source-only package сборка и postmerge main. **S10b2a GO != S10b2 или весь S10 GO**. Следующий **S10b2b** должен получить доказанные original S07/S08c/S08d source inputs из *того же sealed native candidate*, решить schema3 Auto vs P2e исходный argv, пройти real native owner preflight и только потом добавить один конкретный положительный original FD9 bound transition. **S10c** — многократные аварии/rollback, Config::save ambiguity/P1 CAS и предыдущий active root. Никакого публичного `os-zapret2-restyle-0.6.5_201.pkg` и никакого воздействия на пользовательский маршрутизатор.
