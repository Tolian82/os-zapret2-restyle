# Strategy Lab — предварительный план браузерных HTTP/2 и HTTP/3 проверок

**Статус:** СОГЛАСОВАННЫЙ ПРЕДВАРИТЕЛЬНЫЙ ПЛАН, НЕ РЕАЛИЗОВАН.
**Зафиксировано:** 2026-10-20 по обсуждению владельца.
**Начало реализации:** только по отдельной явной команде владельца; запись плана не разрешает править код, менять пакет или запускать релиз.

## Цель и границы

Повысить точность автоматического поиска DPI-стратегий в существующей Strategy Lab: проверять HTTP/HTTPS так, как это делает современный браузер Chrome на сетевом уровне, и проверять настоящий прикладной HTTP/3 поверх QUIC. Перенять полезные идеи `ugorur/os-zapret2` и оригинального `bol-van/zapret2/blockcheck2`, **не заменяя** существующий Python-планировщик и Model C.

В рамках плана:
- единственный основной HTTP-клиент лаборатории — **`curl-impersonate` с явно заданным профилем Chrome**;
- **не** добавлять Firefox, выбор браузера в GUI, отдельный HTTPS-контроль обычным `curl` или fallback на обычный `curl`;
- сравнение «без DPI-обхода / с кандидатом dvtws2» обязательно, но **обе стороны используют одинаковый Chrome-профиль и одинаковый HTTP-запрос**;
- не изменять системный `/usr/local/bin/curl`, сервис OPNsense, общую конфигурацию браузеров и другие части плагина;
- OpenSSL можно оставить **только для узкой диагностики QUIC-handshake**, не в качестве доказательства успешного HTTP/3;
- произвольный UDP, STUN и не-HTTP протоколы остаются на действующих специализированных клиентах; `curl-impersonate` не является заменой им.

Сетевой профиль Chrome — приближение к браузерному TLS/HTTP fingerprint, а не полнофункциональный браузер с JavaScript. Не объявлять browser-equivalence без измерений.

## От чего отталкиваемся

**Подтверждено текущим кодом restyle:**
- `strategy_lab_py/request.py` выполняет HTTPS через системный `curl`, с обязательными `--http1.1`, `GET`, `Connection: close` и `Range`;
- в Standard преобладает IPv4/TLS 1.3, Extended добавляет TLS 1.2/HTTP/QUIC и Generic UDP;
- QUIC-проверка кандидата — `openssl s_client -quic` с проверкой сертификата, **без HTTP/3 GET**;
- каталог Stage 80 содержит четыре кандидата: `quic-fake-1`, `quic-fake-2`, `quic-ipfrag-8`, `quic-ipfrag-16`;
- Model C, привязка к фиксированному IP, атрибуция IPFW, адаптивные бюджеты, устойчивость, отмена и восстановление Stage 90 уже существуют.

**Источник идеи:** `ugorur/os-zapret2/scripts/build-curl-h3.sh` при сборке берёт **готовый FreeBSD `curl-impersonate` из репозитория `latest`**, извлекает бинарник, добавляет его в приватную директорию собственного OPNsense-пакета, сохраняет лицензии/версию и проверяет HTTP3. Компиляции `curl-impersonate` из исходников нет. Upstream `blockcheck2` использует HTTP/3 `--http3-only` и более широкий QUIC-каталог. Конкретный бинарник из FreeBSD `latest` не обязан совпадать с версией GitHub Release lexiforest.

Ссылки: [ugorur build-curl-h3](https://github.com/ugorur/os-zapret2/blob/master/scripts/build-curl-h3.sh), [ugorur blockcheck](https://github.com/ugorur/os-zapret2/blob/master/src/opnsense/scripts/OPNsense/Zapret/blockcheck.sh), [upstream QUIC catalog](https://github.com/bol-van/zapret2/blob/master/blockcheck2.d/standard/90-quic.sh), [lexiforest curl-impersonate](https://github.com/lexiforest/curl-impersonate).

## Протокольная матрица (целевое поведение, пока не реализовано)

| Ветка | Клиент | Требование к результату |
| --- | --- | --- |
| Standard, основной HTTPS | `curl-impersonate` / один фиксированный Chrome-профиль | Браузерный TLS 1.3 и согласованный HTTP/2, HTTP GET, валидный сертификат и фактический целевой IP |
| Extended, TLS 1.2 | Тот же `curl-impersonate` / Chrome | Отдельно маркированный тест TLS 1.2; искусственное ограничение TLS не объявлять точным штатным fingerprint Chrome |
| Extended, HTTP TCP/80 | Тот же `curl-impersonate` / Chrome | HTTP GET, прикладной ответ, атрибуция |
| Extended, Enable QUIC | Тот же `curl-impersonate` / Chrome, `--http3-only` | QUIC + реальный HTTP/3 GET; запрет TCP fallback, проверенный HTTP-ответ и сертификат |
| Stage 30 QUIC capability | Вспомогательный OpenSSL только где нужен | Диагностика доступности/handshake; не авторизация или запрет Stage 80 |
| Generic UDP/STUN | Действующий специализированный путь | Без изменений в связи с переходом HTTP-клиента |

HTTP/2 не может считаться подтверждённым, если сервер согласовал HTTP/1.1. Результат HTTP/1.1, если он встретился, должен быть помечен как HTTP/1.1, а не подменён успехом HTTP/2. Выбор конкретного Chrome-профиля осуществляется централизованно по поддержке включённого бинарника, **без настройки в GUI**. Не задавать опции TLS/HTTP/заголовков, которые случайно разрушают выбранный fingerprint. `--resolve`/эквивалент фиксирует IP, сохраняя SNI/Host/проверку имени.

Сохраняем полезный прикладной GET; пересматриваем обязательные `--http1.1`, `Connection: close`, `Range`, чтобы не превращать браузерный профиль в нетипичный. Ограничения времени/объёма/числа запросов сохраняются с учётом действующих бюджетов.

## Этапы и критерии завершения

### Этап 1 — поставка готового браузерного клиента

- Повторить проверенную ugorur схему **FreeBSD `latest` -> готовый пакет -> извлечение -> приватный файл внутри os-zapret2-restyle.pkg**.
- При сборке записывать фактически разрешившиеся **версию и SHA-256** бинарника, включать требуемые лицензии; не выдавать `latest` за неизменно закреплённую версию.
- Не перекрывать системный `curl`. Явно включить один поддерживаемый **Chrome**-профиль и его совместимые HTTP/2/HTTP/3 параметры.
- Не создавать отдельную широкую программу исследований зависимостей: достаточно не пропустить очевидную ошибку установки/запуска и проверить, что установленный клиент выполняет требуемый реальный HTTP/2 и HTTP/3 запрос. При отсутствии клиента лаборатория показывает техническую ошибку, **не** переключается на обычный `curl`.

**Приёмка:** пакет устанавливается на целевую FreeBSD 15 / OPNsense; приватный клиент с выбранным Chrome-профилем реально выполняет HTTPS и HTTP/3. Без изменения текущего рабочего runtime.

### Этап 2 — браузерный HTTPS в Standard

- Заменить вызов обычного `curl` в общем HTTP/HTTPS probe adapter, сохранив текущую модель кандидатов/состояний.
- Standard: Chrome-профиль, HTTPS/TLS 1.3, фактически согласованный HTTP/2 и HTTP GET.
- Один и тот же клиент/профиль/URL/привязка IP для «без обхода» и «с dvtws2».
- Подтверждать IPFW-перехват и все текущие критерии валидности ответа; отсутствие HTTP/2 не выдавать за HTTP/2 PASS.

**Приёмка:** реальный Standard-тест на сервере с HTTP/2 подтверждает HTTP/2, валидный сертификат, корректную атрибуцию и различает прямую доступность от результата кандидата. Обычный curl не вызывается.

### Этап 3 — полноценный HTTP/3 в Extended

- Для финального QUIC-критерия в Stage 80 использовать `curl-impersonate --http3-only` с Chrome-профилем и **HTTP GET**, а не успешность одного `openssl s_client -quic`.
- Проверять приложение/сертификат/фиксированный IP/IPFW и отсутствие перехода на TCP.
- Разделять «HTTP/3 не поддерживается сервером», «неуспешный запрос/возможная блокировка» и «ошибка клиента или тестовой инфраструктуры»; неизвестную причину не объявлять доказанным DPI.
- Сохранить **Enable QUIC OFF по умолчанию**, его persistence и независимость Stage 80 от `quic_ipv4=closed` Stage 30.

**Приёмка:** известный HTTP/3 endpoint успешно проверяется HTTP/3 GET; в случае блокировки QUIC пользовательское Enable QUIC всё равно инициирует поиск. Handshake OpenSSL сам по себе больше не победа.

### Этап 4 — расширение QUIC-каталога

- По мотивам upstream `blockcheck2.d/standard/90-quic.sh` оценить fake repeats `1/2/5/10/20`, IP fragmentation `8/16/32/64` и комбинации fake + fragmentation.
- Оставить нативный синтаксис Lua/dvtws2, существующие CandidateSpec, ресурсную модель, временный IPFW и Stage-80 runner; не импортировать целиком upstream `blockcheck2`.
- Применить адаптивный/ограниченный по времени перебор и раннюю остановку; текущие 4 кандидата не удалять без фактического основания.

**Приёмка:** новые кандидаты реально запускаются и атрибутируются, нет ложных победителей или превышения бюджета, восстановление не нарушено.

### Этап 5 — точные результаты и отчёты

- Сохранять браузерный профиль, фактическую версию `curl-impersonate`, выбранный IP/Host/SNI, согласованные TLS/HTTP, код HTTP, достаточность прикладного ответа, сертификат, статус IPFW, попытки и причину ошибки.
- Отдельно отображать прямую доступность без обхода. Успех HTTP с кодом 4xx/5xx сам по себе не означает DPI FAIL: учитывать существующий контракт достоверного прикладного ответа и происхождение перехвата.
- Не смешивать инфраструктурные ошибки с сетевым FAIL и не заявлять браузерный отпечаток фактом только по имени бинарника.

**Приёмка:** результат объясняет, какой протокол/профиль реально испытан, почему стратегия признана рабочей и какие детали не подтверждены. RU/EN соответствует текущему GUI.

### Этап 6 — очная квалификация на OPNsense

- Измерить на одинаковых целях корректность найденных стратегий и длительность Standard/Extended до/после изменения; приоритет — полезность, а не число тестов.
- Проверить Stop, оставшиеся процессы/правила IPFW, сохранение настроек, финальную стабильность, Stage-90 cleanup/restoration и отсутствие неожиданных изменений Voice/Strategies.
- Разделять подтверждение исходниками/CI, успешную сборку FreeBSD и **owner-live** результат на установленной OPNsense.

**Приёмка:** новые HTTPS/HTTP3 сценарии действительно работают в установленном пакете и не нарушают старый жизненный цикл.

## Правила выполнения после отдельного разрешения владельца

1. Выполнять этапы по порядку, каждый завершать наблюдаемым результатом; исправить блокирующую проблему прежде следующего этапа.
2. Один существующий Python-планировщик/Model C/приватные IPFW rules; без новых daemon, менеджера браузеров, параллельного Apply или новой архитектуры восстановления.
3. Не увеличивать бюджеты поиска «на всякий случай»; изменять только после измерения.
4. Применять действующее правило ревизий пакета при кодовых push; документационные изменения без packaged-source не требуют повышения ревизии.
5. До отдельной команды **это только план**. Текущие `request.py`, Stage 30/80, QUIC catalog, опубликованный пакет и приёмка OPNsense остаются неизменными.
