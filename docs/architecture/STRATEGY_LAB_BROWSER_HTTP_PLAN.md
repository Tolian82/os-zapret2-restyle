# Strategy Lab — подробный план браузерных HTTP-проверок

**Статус:** технический план согласованного направления; реализация этапов 1–6 не начата.
**Уточнения владельца:** 20–21.10.2026. **Срез аудита:** исходники restyle `8b31fa49cfcf00617f3137b8eb7bc80427d1f19f`.
**Граница поручения:** оформить ТЗ и последовательность разработки. Изменение кода/пакета начинается по отдельной команде владельца. Этот документ не запускает релиз.

## Назначение и конечная точка

Первичный продуктовый контракт и определение готовности находятся в [REQUIREMENTS](../REQUIREMENTS.md), раздел «Strategy Lab — целевой результат браузерных HTTP-проверок», требования `BH-01`–`BH-12`. Здесь определены технические решения, участки кода, зависимости этапов и доказательства их завершения.

Результат разработки — установленная Strategy Lab, которая через один Chrome-профиль определяет прямую доступность, при необходимости находит и подтверждает нативные стратегии Zapret2, показывает фактические TLS/HTTP и готовые профили, а после любого исхода восстанавливает исходное состояние службы. Доступность по HTTP/1.1 столь же положительна, как по HTTP/2. Отсутствие победителя при корректно завершённом поиске также является допустимым результатом; универсальный обход любого сайта/провайдера не обещается.

Порядок: **1 → 2 → 3 → 4 → 5 → 6**. Номер этапа разработки не равен номеру стадии задания лаборатории. Для каждого этапа ниже заданы результат, задачи и приёмка. Обнаруженный блокирующий дефект исправляется в текущем этапе по `DEV-007`.

## 2. Технические решения для реализации

### Клиент и поставка

- Приватный путь: `/usr/local/libexec/zapret2-restyle/curl-impersonate/bin/curl-impersonate`. Системный `/usr/local/bin/curl` не меняется.
- Готовый пакет FreeBSD `latest` получается в сборочном окружении для целевого ABI. В пакет плагина включаются исполняемый файл, необходимые файлы его поставки и лицензии; установка плагина не скачивает и не компилирует клиент.
- Рядом сохраняется машинно читаемая запись: имя/версия исходного FreeBSD-пакета, ABI, SHA-256 исходного пакета и извлечённого бинарника, вывод версии, один выбранный Chrome-профиль. После сборки конкретного кандидата эти значения неизменны.
- Профиль выбирается один раз на этапе 1 из реально поддерживаемых поставляемым бинарником и пригодных для HTTP/2 и HTTP/3; `chrome145` — проверенный по изученному upstream кандидат, а не обещание версии будущего пакета. Выбор фиксируется централизованно, не определяется заново для каждого сайта и не выводится в GUI как настройка.
- Проверка наличия клиента/профиля и системного CA выполняется до остановки нормальной службы. Отсутствие клиента, нужной возможности или CA — техническая ошибка. Firefox, обычный curl-контроль и fallback исключены.
- По примеру ugorur используется существующее доверенное хранилище CA OPNsense/FreeBSD. Конкретный рабочий путь фиксируется по целевому пакету/системе; `-k` не допускается.

### Единая политика запросов

| Режим | Параметры | Успех |
| --- | --- | --- |
| Основной HTTPS | `--impersonate <зафиксированный Chrome>`; штатное согласование TLS, HTTP/2 с допустимым HTTP/1.1 | Достоверный прикладной ответ по фактическому HTTP/1.1 или HTTP/2 |
| Extended TLS 1.2 | Тот же профиль, `--tlsv1.2 --tls-max 1.2` | Достоверный HTTPS-ответ; ограничение TLS явно отмечено |
| Extended HTTP | Тот же клиент/профиль, `http://`, TCP/80 | Достоверный HTTP-ответ; отсутствие TLS явно отмечено |
| Extended HTTP/3 | Тот же профиль, `--http3-only`, UDP/443 | Именно HTTP/3 GET, сертификат/имя проверены, адрес и перехват подтверждены |

Общие параметры: GET, IPv4 для пользовательской цели, тот же URL и фиксированный IP, сохранённые Host/SNI, retry=0, ограниченные времена соединения/запроса. Для целевого запроса остаётся `--resolve` и запрет автоматического ухода по redirect на другой адрес; ответ 3xx описывает проверенный endpoint, а не доказанную загрузку конечного сайта.

Убираются обязательные `--http1.1` и `Connection: close`. Для Standard не добавляются `--tlsv1.3`/`--tls-max 1.3` и ручные настройки шифров/ALPN/HTTP2. Поддержка сжатия и заголовки согласуются с выбранным upstream-профилем; отдельный произвольный User-Agent не нужен.

Первым параметром клиента задаётся отключение пользовательского curlrc (`-q`); запрос явно исключает прокси окружения. Это локальная политика процесса лаборатории, без изменения системного прокси. Ни cookie jar, ни Alt-Svc cache другого задания не используются. Успех через незапланированный proxy/другой IP не принимается за прямую доступность.

### Короткая проверка и проверка финалиста

Начальная политика сохраняет существующий GET-4K для прямой проверки, discovery и stability. Обе стороны одного сравнения используют одинаковый Range и лимиты. Глубокий replay запрашивает до 64 KiB и отдельно оценивает достижение 16 KiB; это существующие уровни глубины, а не дополнительный самостоятельный поиск.

Range остаётся осознанным ограничением запрашиваемого объёма лабораторного GET. Он отличается от обычной полной загрузки страницы и не должен называться точной имитацией всей браузерной навигации. Сервер может проигнорировать Range: записывается фактически полученный объём, жёсткое ограничение времени сохраняется. Получение более запрошенного количества само по себе не ошибка; тайм-аут/оборванный ответ не превращается в успех только из-за ненулевого объёма.

Полностью полученный короткий ресурс допустим как доказательство доступности; критерий глубины 16 KiB при этом не подтверждён. Достоверные 4xx/5xx сохраняют действующее значение прикладного ответа, а не автоматически означают DPI FAIL. Совпадение удалённого IP и, для кандидата, доказанный перехват остаются обязательными.

### Результат запроса

Расширяется существующее структурированное доказательство; отдельная система хранения/диагностики не создаётся. Общий разбор результата используется всеми путями, включая Model C и установленные обработчики IPv4.

Минимальные поля:

- режим запроса, профиль Chrome, версия/хеш клиента;
- URL, Host/SNI, выбранный IP, фактический remote IP; запрошенный и наблюдённый local port там, где порт является частью атрибуции;
- политика TLS и фактически согласованные TLS/HTTP, код HTTP, результат проверки сертификата;
- код завершения, тайм-аут, достаточность/завершённость ответа, полученные байты и критерий глубины;
- job/search epoch, candidate/spec/resource identity, номер попытки, исход атрибуции и причина результата.

Новые поля не добываются догадками из названия ветки `tls13` или команды `--http3-only`. Формат штатных диагностических данных для фактического TLS проверяется на бинарнике этапа 1; недоступное наблюдение хранится как неизвестное с причиной. В частности, действующее присваивание выбранного IP в качестве якобы наблюдённого адреса QUIC заменяется реальным наблюдением клиента.

Строковый write-out и его регулярные выражения меняются согласованно во всех потребителях. Внутренний старый ключ `tls13` может временно читаться как совместимый идентификатор основной ветки, но новые GUI/отчёты не называют автоматически согласованный TLS 1.2 «TLS 1.3». Старые задания читаются без перезаписи и без присвоения им новых доказательств Chrome/HTTP3.

### Управление HTTP/3

1. Если все обязательные endpoints доступны в прямой основной HTTPS-проверке, сохранить `TARGET_ACCESSIBLE`, пропустить поиск/Extended и выполнить Stage 90. HTTP/3 GET и QUIC-кандидаты не запускаются даже при включённой галочке.
2. Если прямой HTTPS не подтвердился, HTTP/3 относится только к Extended с Enable QUIC ON и достаточной Host/SNI-идентичностью. Standard, OFF и bare IPv4 без нужного имени дают понятный пропуск.
3. Stage-30 OpenSSL остаётся необязательным для доказательства HTTP/3 вспомогательным handshake-контролем; его отрицательный результат не запрещает Stage 80. Новый обязательный внешний HTTP/3-тест перед каждым заданием не добавляется.
4. Перед QUIC-кандидатами выполняется одна прямая проверка целевого HTTP/3 без dvtws2 с теми же параметрами. Её успех отражается как доступность без QUIC-обхода, с нулём кандидатов. Итог задания не должен называть эту ситуацию недоступностью только из-за отсутствия стратегии.
5. При неуспехе прямого HTTP/3 запускается ограниченный поиск. Успешный handshake или переход на TCP не являются HTTP/3-победой.
6. Тайм-аут не различает доказанно «сервер не поддерживает HTTP/3» и «пакеты блокируются». Без прямых данных причина остаётся неизвестной. Ошибка клиента/CA/опции/атрибуции отделяется от сетевого неуспеха.

## 3. Этапы разработки

### Этап 1 — готовый клиент внутри пакета

**Зависимость:** отдельная команда начать реализацию. **Наблюдаемый результат:** устанавливаемый пакет содержит запускаемый приватный клиент с одним явным Chrome-профилем.

Задачи:

1. Добавить небольшой сборочный помощник по схеме ugorur и вызвать его из `scripts/build-pkg.sh` до plist. Сохранить собственные имя пакета и приватный путь restyle.
2. Использовать временную конфигурацию официального FreeBSD `latest` с обычной проверкой подписей; извлечь артефакт без установки/обновления системного curl и без сборки исходников.
3. Включить бинарник, необходимые файлы поставки, лицензии и запись происхождения. Проверить фактический запуск в целевой FreeBSD 15 среде; исследовать зависимости только при конкретном сбое.
4. Выбрать поддерживаемый Chrome-профиль для HTTPS и HTTP/3, определить рабочий CA и доступные поля результата. Зафиксировать эти параметры в одном месте.
5. Добавить ограниченную проверку готовности клиента до остановки службы; ошибки сообщать как технические. Существующие запросы переключаются полностью на этапе 2.

**Приёмка:** содержимое pkg и SHA-256 согласованы; на FreeBSD приватный клиент реально выполняет HTTPS с HTTP/2 и GET с `--http3-only` на подходящих контрольных endpoints. Известный только HTTP/1.1 endpoint также доступен. Подтверждена работа проверки сертификата. Возможности `--version` без запросов не закрывают этот пункт. Нет изменения системного curl/конфигурации службы.

**Граница доказательства:** сборка/запуск в FreeBSD CI не равны приёмке пользовательского поиска на установленной OPNsense. Результаты пригодных проверок повторно используются на этапе 6.

### Этап 2 — сквозной основной HTTPS-поиск

**Зависимость:** этап 1. **Наблюдаемый результат:** Standard от прямой проверки до готовой рекомендации работает через выбранный Chrome-профиль со штатным TLS.

Задачи:

1. Реализовать единый построитель команд/разбор результатов в `request.py`, локальную изоляцию curlrc/proxy и общую политику GET/CA/фиксированного IP.
2. Перевести `probe.py`, `candidate.py` и действующие подмены `ip_target_support.py`; согласовать baseline/discovery/stability по URL, профилю, IP, Range и лимитам.
3. Перевести прямой вызов `_curl_command` в `model_b_parallel.py`, добавление local port/write-out и разбор в `model_b_parallel_attribution.py`. Проверить вызов через `stage60_model_c_production`/`stage60_model_c`, не ограничиваться отдельно вызванной базовой функцией.
4. Сохранить source-port leasing, контроль remote IP/порта и IPFW, ширину Model C до трёх, CandidateSpec/ResourceInventory, ранжирование и существующую последовательность endpoints.
5. Обновить `adaptive_validation.py`, установленный `truthful_result_support.py` и финальный replay: доступность положительна при HTTP/1.1 и HTTP/2, TLS 1.2 и TLS 1.3 в основном согласовании. Принудительный TLS 1.2 Extended пока остаётся отдельным режимом.
6. Сохранить ранний `TARGET_ACCESSIBLE` в `orchestrator.py`; при нём не запускать Stage 50–85/HTTP3, но всегда выполнять восстановление.
7. Обновить необходимые подписи основной ветки и отчёт уже в этом этапе, чтобы измерение TLS 1.2 не выводилось как TLS 1.3. Удалить использование обычного curl из производственных HTTP/HTTPS путей лаборатории, включая контрольные HTTP-запросы; другие компоненты плагина вне этой миграции.

**Приёмка:** прямой HTTP/1.1, HTTP/2 и HTTPS сервера с TLS 1.2 завершаются как доступность; на отрицательной прямой проверке кандидат получает результат через реальный производственный вход Model C. Рекомендация проходит 3/3 устойчивость и один глубокий replay точного профиля, либо отклоняется по конкретной причине. Несовпадающие IP/порт, неверный сертификат и ошибка атрибуции не дают победителя. Достоверные 4xx/5xx и короткий полный ответ сохраняют принятую трактовку. При прямом успехе счётчики HTTP3/кандидатов равны нулю.

### Этап 3 — Extended и прикладной HTTP/3

**Зависимость:** этап 2. **Наблюдаемый результат:** Extended проверяет реальные HTTP-запросы, а QUIC-победа подтверждена HTTP/3.

Задачи:

1. Подключить принудительную TLS 1.2 и HTTP TCP/80 к тому же клиенту и общему доказательству; явно отметить изменённую TLS-политику/отсутствие TLS.
2. Заменить целевой `quic_target_request` на Chrome HTTP/3 GET с `--http3-only`, фиксированным IP и проверкой Host/SNI/CA. OpenSSL-контроль Stage 30 не используется как финальный критерий.
3. Добавить прямой HTTP/3 baseline и отдельный исход «доступен без QUIC-обхода»; сохранить результаты основного поиска и Generic UDP. Агрегатор должен корректно представлять доступность даже при пустом списке стратегий.
4. Применить общий разбор результата к основному и подменённому IPv4 candidate-probe; подтвердить фактический remote IP и IPFW именно UDP/443. Не принимать TCP fallback.
5. На действующих четырёх QUIC-кандидатах добавить 3/3 подтверждение первого потенциального победителя с ранним отказом при неудаче; при неустойчивости продолжить допустимый поиск. Повторные попытки используют свежие соединения и тот же endpoint epoch.
6. Включить QUIC в прикладную проверку финалиста и точный replay UDP/443 профиля; убрать обход HTTP-критериев через `non_http_protocol` для QUIC. Generic UDP сохраняет свой отдельный контракт.
7. Разделить ошибки запуска/CA/профиля/возможностей, сетевую неудачу, отсутствие времени и отмену. Проверить OFF, ON при закрытом Stage 30, bare IP и Host/SNI.

**Приёмка:** endpoint HTTP/3 выдаёт реальный GET-ответ; handshake без HTTP не проходит; доступный TCP endpoint не маскирует неработающий UDP/443. ON запускает допустимый поиск независимо от отрицательного Stage 30; OFF и прямой HTTPS-успех не запускают его. Прямой HTTP/3-успех не создаёт фиктивную стратегию. QUIC-финалист имеет действительные 3/3, HTTP-доказательство и replay опубликованного профиля. Предыдущие проверки Generic UDP не переписываются в HTTP3.

### Этап 4 — ограниченное расширение QUIC-каталога

**Зависимость:** этап 3; расширять поиск до исправления критерия победы нельзя. **Наблюдаемый результат:** лаборатория пробует больше полезных нативных вариантов в существующем бюджете.

Начальный конечный набор:

| Семейство | Значения | Число |
| --- | --- | --- |
| Fake | repeats `1, 2, 5, 10, 20` | 5 |
| IP fragmentation | `8, 16, 32, 64` | 4 |
| Fake + fragmentation | repeats `2`, fragmentation `8, 16, 32, 64` | 4 |

Итого 13 вариантов до исключения ресурсно несовместимых/дублирующихся. Первые четыре сохраняют действующие ID и порядок: `quic-fake-1`, `quic-fake-2`, `quic-ipfrag-8`, `quic-ipfrag-16`. Затем добавляются оставшиеся простые варианты и четыре комбинации. Параметры основаны на подходе [upstream 90-quic.sh](https://github.com/bol-van/zapret2/blob/master/blockcheck2.d/standard/90-quic.sh); при реализации фиксируется реально использованный upstream-срез и проверяется нативный синтаксис установленного dvtws2.

Задачи:

1. Представить варианты в существующем каталоге/CandidateSpec с точным порядком действий и реальными ресурсами; не импортировать движок blockcheck2 и не генерировать полный декартов продукт.
2. Для fake использовать поддерживаемый встроенный либо уже установленный ресурс из ResourceInventory. Его отсутствие явно исключает соответствующие варианты, не заменяет содержимое незаметно.
3. Выполнять допуск кандидата по оставшемуся абсолютному времени, числу обязательных endpoints и стоимости запуска/проверки. Резервировать время для подтверждения найденного победителя, Stage 85 и обязательного восстановления.
4. Сохранить текущие конечные родительские бюджеты и первоначальное начало часов. При оценке учитывать действующий Python launcher и его QUIC candidate timeout, а не старый shell reference.
5. Останавливаться после подтверждённого победителя, отмены либо исчерпания допустимого времени. В отчёте различать выполненные, несовместимые и отложенные по бюджету варианты; «все проверены» допустимо только при фактическом завершении набора.

**Приёмка:** точные аргументы 13 вариантов воспроизводимы; каждый запущенный вариант атрибутируется; при достаточном бюджете и отсутствии победителя все допустимые варианты достижимы. При малом остатке поиск завершается с честным неполным результатом и чистым восстановлением. Бюджет не увеличивается заранее ради полного перебора; изменение чисел возможно только по измеренному конкретному ограничению.

### Этап 5 — результаты, GUI и сохранённые задания

**Зависимость:** этапы 2–4. **Наблюдаемый результат:** по обычному результату понятно, что доступно, что испытано и почему рекомендована стратегия.

Задачи:

1. Дополнить существующие JSON/отчёт/представление выбранным профилем и фактическими TLS/HTTP, адресом, кодом ответа, объёмом/глубиной и подтверждением попыток. Обычный экран остаётся кратким; подробности доступны через существующую детализацию.
2. Показать прямую доступность отдельно от успеха стратегии. Для HTTP/1.1 не использовать предупреждение о неуспехе только из-за отсутствия HTTP/2. Для HTTP3 вывести число действительно испытанных кандидатов и причину пропуска/незавершённого поиска.
3. Сохранить верхний список до трёх рекомендаций и существующий принцип предпочтения основной HTTPS-ветки. Успешный HTTP/3, не попавший в верхние три, остаётся видимым в протокольных результатах; непроверенный профиль не становится рекомендованным из-за одного Stage-80 успеха.
4. Сохранить отдельный circular handoff основной HTTPS-ветки и его действующие условия. Изменить устаревшие TLS1.3 подписи/потребители ключей, но не вводить HTTP3 circular или новый жизненный цикл.
5. Обеспечить RU/EN, перечитывание после F5, чтение старых заданий и отсутствие новых выдуманных измерений в исторических результатах. Историческое «QUIC работает» не переименовывать в «HTTP/3 GET подтверждён».
6. Синхронизировать user guide, основную архитектуру, QUIC control, unified shortlist и выбранные строки live-матрицы по фактически реализованным этапам.

**Приёмка:** таблица и подробный результат согласованы для прямого успеха, H1/H2 кандидата, H3 кандидата, пустого/неполного поиска, технической ошибки и отмены. F5 сохраняет смысл результата и Enable QUIC. В старом задании отсутствующие профиль/HTTP3-данные показаны как неизмеренные. Никакого автоматического Apply найденного профиля нет.

### Этап 6 — установленный пакет и завершение разработки

**Зависимость:** этапы 1–5. **Наблюдаемый результат:** владелец получает пригодную к использованию лабораторию в проверенном пакете.

Задачи:

1. Собрать и доставить точный тестовый пакет FreeBSD 15 amd64 обычным путём проекта; записать source commit, пакет, SHA-256, профиль/версию клиента и выполненные проверки. Не подменять поставку Actions artifact.
2. На установленной OPNsense выполнить только выбранную ниже матрицу. Повторно использовать уже полученное доказательство того же сценария/артефакта, если оно не устарело от последующих изменений.
3. Для сравнения времени использовать одинаковые цели, режим, набор endpoints и условия; сохранить длительности и причины остановки. Новый профиль меняет сетевой запрос, поэтому различие числа найденных стратегий само по себе не считается регрессией или улучшением без разбора.
4. При Stop, отрицательном поиске и ошибке проверить отсутствие временных процессов/правил и восстановление исходного RUNNING/STOPPED. Не расширять этот этап в новую recovery-архитектуру или Telegram-исследование.
5. Закрыть требования `BH-01`–`BH-12` конкретными ссылками на CI/пакет/наблюдение владельца. Непроверенная строка остаётся открытой; найденный блокирующий дефект устраняется до объявления готовности.
6. Согласовать текущие документы с реализованным состоянием. Полный стабильный Web/pkg-релиз выполняется только при отдельной команде владельца; готовность тестового пакета и публикация стабильного релиза — разные факты.

**Приёмка:** обязательные строки новой матрицы подтверждены, документация описывает фактическое поведение, пакет доступен владельцу, критических дефектов результата/восстановления нет. До этого модернизация не обозначается полностью завершённой.
