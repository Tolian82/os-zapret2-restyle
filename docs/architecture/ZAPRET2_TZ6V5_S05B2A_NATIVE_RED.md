## Original native lifecycle proof, not a simulated status

The original `supervisor_loop.sh` observes disappearance of its monitored real `dvtws2` child *after ready* and calls `zapret_service.sh runtime-failure <fixed message> <old PID>`. Original `service_with_lifecycle_lock 0` deliberately refuses an FD9 busy callback instead of queueing behind a replacement owner. Under a genuinely committed Common owner, `shared_apply_stop_service "$_shared_owner" "$3"` validates the callback PID **against the current original `/var/run/dvtws2.pid`** before the sealed Config/release/IPFW transition. It therefore correctly **refuses rc69** when that PID witness is gone, rather than cleaning unknown kernel objects. `voice_live_inspect.examine_shared` independently classifies the stopped engine with unverified/remaining kernel state as foreign/modified, not as verified stopped.

In [disposable native failure #45240400594](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/45240400594) the isolated OPNsense 26.7 guest installed an actual source-built plugin and upstream engine and reached authenticated original Common **RUNNING** through Strategies Apply. A deliberately **wrong-PID** runtime-failure command returned **rc69**. The original Apply journal/Config/engine/process/IPFW were unchanged. This protected mutating command touched only the **original fixed FD9 lockfile metadata**, which is not a public `status --json` call; JSON's own no-write contract still has no exceptions.

Only inside that disposable VM, test code then sent `/bin/kill -TERM` to the genuine monitored engine PID to trigger a real post-ready disappearance. After 90 seconds, the original journal **had no confirmed failure receipt**. Fresh read-only `status --json` reported **`FOREIGN_OR_UNVERIFIED`, rc2**, NOT verified STOPPED. At that later observation, **both** engine and supervisor-monitor PIDfiles were absent. The historical pipeline stage was `ok`, not causal error evidence. A diagnostic-only **manual subsequent** invocation of the same root FD9 `runtime-failure` command with the earlier PID returned **rc69** and did not record an event. Exact bounded test marker: `S05B2_SUPERVISOR_CALLBACK_UNCONFIRMED_FOREIGN_OR_UNVERIFIED_status2_monitor0_pidfile0_stageok_direct69_absent`.

**What is established:** the automatic supervisor/FD9 chain did not produce a terminal, qualified original error record, and the physical kernel/owner state was unverified after the exit. **What is NOT established:** whether the first automatic callback reached FD9, its exact return code, or the precise time the PIDfile disappeared. The later manual rc69 is consistent with the current PIDfile comparison refusing; it is **not proof** of the first callback's failure cause. No real upstream exit code is available, so `exit_status=null`. Never invent a chronological latest-error record, kernel ownership or original exit rc from this evidence.
