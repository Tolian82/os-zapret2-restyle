# «Передача голоса» — исправление поставки и приёмка v0.5.3

**Утверждено владельцем 17.10.2026.** Начало этапа — `v0.5.3_1`, сначала фиксация правил и полного плана, затем выполнение. Источник исходной постановки — [полное ТЗ](VOICE_TRANSMISSION_GUI.md). Пять сервисов, внешний вид и общий backend Voice/«Стратегии» сохраняются. Текущие факты и единственное следующее действие принадлежат [PROJECT_STATE](../PROJECT_STATE.md) и [START_HERE](../START_HERE.md).

## Основание и критерий работы

Установленный через GUI пакет `0.5.2_194` при переходе на `/ui/zapret/voice` показывает «Страница не найдена». В исходниках подтверждено отсутствие UI `VoiceController::indexAction`, требуемого штатным Router; имеющийся `IndexController::voiceAction` адресуется иначе. Наличие API VoiceController не закрывает UI route. Старые статические проверки наличия `voiceAction` не доказывали доступность адреса меню.

Каждый шаг имеет наблюдаемый результат. Применяются [DEV-007, DEV-011, DEV-018](../PROJECT_PRINCIPLES.md) и [CHAT-003](../CHAT_RULES.md): блокирующий дефект исправляется прежде следующего участка; отчёт содержит изменение, фактически проверенное и неподтверждённое. Сборка, проверка маршрута и работа страницы на установленном OPNsense — разные результаты. Архитектурная переделка не обоснована этим дефектом.

## 1. Исправить вход на страницу

**Объём:** добавить UI `VoiceController::indexAction` по штатному образцу `DiagnosticsController`; сохранить `/ui/zapret/voice`. Проверить menu → ACL → controller → form/view и связанные переходы, RU/EN названия. Не создавать второй API/backend/службу. Убрать ошибочное дублирование UI-обработчика, если больше нет вызовов.

**Проверяемый результат:** штатный Router находит нужный обработчик, тот выбирает существующую Voice-форму и шаблон. Все три пункта плагина имеют согласованные маршруты. Этот результат проверяет интеграцию исходников; отображение страницы принимается после установки в шаге 3.

## 2. Проверить обнаруженный пробел

**Объём:** одна целевая регрессионная проверка использует настоящий Router целевой OPNsense, адреса настоящего Menu.xml и файлы исходников/распакованного собранного пакета. Проверяется соответствие контроллера/action, формы и шаблона; сопутствующие проверки PHP/JS/GUI выполняются по изменённому объёму и обязательным правилам проекта.

**Проверяемый результат:** проверка отвергает старый `_194` именно из-за отсутствующего Voice UI handler и проходит на исправленном кандидате, включая `.pkg`. Нельзя заменить Router самописной копией его алгоритма или считать grep по `voiceAction` проверкой адреса. CI/package-проверка не выдаётся за визуальную приёмку OPNsense.

## 3. Доставить обновление и принять доступность GUI

**Объём:** интегрировать переход версии `_1` без релиза, затем исправление следующей ревизией; выполнить проверки окончательного кандидата, подготовить полноценное исправляющее обновление `v0.5.3` через существующий FreeBSD:15:amd64 GUI/pkg-репозиторий. Владелец одобрил весь этот порядок, включая доставку через GUI; отдельное повторное согласование обычных операций не требуется. Уже опубликованная идентичность v0.5.2 сохраняется.

**До установки:** проверить точный tag/source/package/checksum/repository; в release notes явно указать, что это исправляющая поставка для приёмки, а не подтверждение всего ТЗ.

**После установки:** открыть Voice из меню и напрямую; получить форму с пятью сервисами и загруженными настройками, проверить отсутствие ошибки страницы и ошибок загрузки API. Открыть «Стратегии» и «Лабораторию», проверить названия/порядок в RU/EN. Зафиксировать версию и наблюдение. Пока такого результата нет, статус: **«исправление подготовлено; работа установленной страницы не подтверждена»**. Отсутствие доступа к appliance — конкретная граница выполнения, не разрешение объявить сценарий пройденным.

## 4. Принять полное исходное ТЗ пользовательскими сценариями

Открытие страницы закрывает только первый дефект. Последовательно пройти все действующие требования раздела 10 [ТЗ](VOICE_TRANSMISSION_GUI.md), с учётом отмены старой PoC-миграции:

| Сценарий | Требуемое наблюдение |
|---|---|
| Интерфейс | RU/EN, справка, native компоновка по «Стратегиям», WAN наследуется со «Стратегий» без отдельного выбора, все пять enabled/args/IPSET групп |
| Сохранение | Значения совпадают после повторного открытия; OFF сохраняет текст; обе формы сохраняют чужие поля и общие IPSET |
| Валидация и Apply | Неверные поля не меняют runtime; OFF→ON, edit ON, add/remove, all OFF и повторный Apply дают фактическое ожидаемое состояние |
| Общая служба | Один dvtws2, нужные scoped IPFW правила/таблицы/WAN/порты; ordinary Strategies сохраняются; Start/Stop отражают фактический результат |
| Boot | Сохранённые ON/OFF и global OFF соблюдены после reboot до ручного enable/Apply |
| UDP/STUN | Отдельно подтверждены нужные forwarded/local/SOCKS сценарии и отсутствие воздействия вне выбранного scope |
| MEDIA/CALL | Реальный двусторонний звук/звонок проверен отдельно; счётчики, GUI ON и Telegram-тест не доказывают работу всех сервисов |

Проверять следующий сценарий после устранения мешающего ему блокера. Новые найденные дефекты исправляются в существующем общем backend; старый PoC/отдельные recovery framework не возвращаются. Неподтверждённый результат остаётся открытым, даже если остальные тесты зелёные. Реальные сетевые исследования ведутся по существующей [кампании](TELEGRAM_VOICE_DOCKER_STRATEGY_CAMPAIGN.md), без повторения закрытых опытов без нового основания.
