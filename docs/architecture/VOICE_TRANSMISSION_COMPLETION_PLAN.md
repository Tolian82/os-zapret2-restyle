# Voice Transmission — граница архитектуры и согласования плана

**Обновлено: 13.10.2026. Кандидат `v0.5.1_174`, Draft PR #328; изменение только документации.**

## Утверждённая архитектура

Владелец утвердил общий backend со «Стратегиями». Полный нормативный контракт находится в [разделе 12 ТЗ](VOICE_TRANSMISSION_GUI.md#12-общий-backend-со-стратегиями-утверждено-13102026). Фронтэнд, поля, пять сервисов и все функциональные критерии приёмки сохраняются.

Существующие общий генератор, `zapret_service.sh`, orchestrator, firewall, launcher/supervisor и штатная модель OPNsense должны обслуживать обе страницы. Voice добавляет STUN-профили и адресный UDP-перехват к полному общему runtime. Независимый Voice lifecycle или собственный писатель Config не являются целевой архитектурой. Доказанные гарантии отказа/отката и защиты чужого состояния сохраняются в общих компонентах.

## Текущий следующий шаг

**Обсудить с владельцем и утвердить подробный поэтапный план изменения кода под уже утверждённую архитектуру.** План пока не утверждён. Предыдущий «этап 3», следующий legacy actuator/WAL/receipt и предложенный одиночный STUN-профиль не являются текущими командами к реализации.

Нынешняя задача ограничена фиксацией архитектуры. Код, GUI, `VERSION`, `PLUGIN_REVISION`, установленные настройки и пакет не меняются. Успех этой записи не означает готовность backend или аппаратную приёмку.

## Что должен определить обсуждаемый план

| Предмет | Необходимый результат обсуждения |
|---|---|
| Карта компонентов | Какие имеющиеся части сохранить, адаптировать, объединить или вывести из пакета; конкретные общие точки интеграции |
| Общий Apply | Полная форма, права владения полями, сериализация двух страниц, штатное сохранение и согласованный Config/runtime/IPFW при успехе и отказе |
| Генерация и перехват | Все пять сервисов, native STUN, ordinary/non-STUN, IPSET/порты/WAN/local UDP, коллизии и порядок профилей |
| Lifecycle | First/stopped start, stop/reconfigure/restart, глобальная OFF, runtime-failure, normal reboot и прерванное применение |
| Миграция | Old ON/OFF, потерянный marker и чистая установка; совместимые Telegram команды; один постоянный источник состояния |
| Этапы и зависимости | Для каждого этапа конкретный результат по ТЗ, затронутые компоненты, зависимости, критерий завершения и условие перехода |
| Проверки | Необходимые конечные сценарии и доказательства; уже пригодные проверки повторно используются, рост числа тестов не заменяет функциональный результат |
| Завершение | Полная GUI/CONFIG/BOOT приёмка, аппаратные проверки, пакет/GitHub; отдельная квалификация конкретного Telegram preset |

Это перечень вопросов для согласования, **не утверждённая последовательность кодовых работ**. Детальные способы блокировок, переноса/удаления модулей и минимального аварийного состояния выбираются в плане по фактическим разрывам и существующим гарантиям.

## Контроль выполнения после утверждения плана

- Этап закрывается проверяемым поведением из полного ТЗ, а не выпуском helper, журнала или отчёта.
- Развитие backend использует общий механизм; новый самостоятельный владелец состояния не появляется как промежуточное удобство.
- Новая защитная операция требует конкретного подтверждённого разрыва. Полезные проверки отказов сохраняются; повторённые исследования без нового основания не становятся работой этапа.
- Текущая очередь живёт в START_HERE и этом плане; хронология — в существующем working ledger. Не копировать рассказ о каждом патче во все активные документы.
- Документация без продуктовых изменений не увеличивает `_N`; кодовые изменения следуют действующим правилам версий.
