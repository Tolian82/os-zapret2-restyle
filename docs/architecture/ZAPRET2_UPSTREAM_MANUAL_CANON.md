# Канон поведения Zapret2 — upstream manual.en.md (обязательный контракт)

**Решение владельца от 23.11.2026.** Это **политика проверки и разработки плагина**, а не второе руководство по движку и не перепроверка официального документа.

**Единственный нормативный первоисточник по поведению Zapret2:**
**https://github.com/bol-van/zapret2/blob/master/docs/manual.en.md**

## Иерархия и обязательное правило

1. Для **любого поведения движка**, прямо описанного в указанном `manual.en.md`, принимаем написанное **как установленный факт, без исключений и повторной экспериментальной проверки**. Не добавлять в ТЗ, план, CI/native test gates, issues или acceptance формулировки «проверить, действительно ли Zapret2 поддерживает X», если X прямо описано в руководстве. Не допускать альтернативных трактовок, дополнительных подтверждений исходниками `nfqws2/dvtws2`, проверкой сигналов на OPNsense или ссылкой на другие документы ради доказательства или опровержения изложенного.
2. Для **поведения, которое руководство не описывает**, допускаются направленные исследования, тесты и нативная проверка. Сюда относятся **наши собственные** OPNsense/FreeBSD интеграция, вызовы configd, GUI, FD9, права/владение процессом, IPFW capture/rules и kernel tables (когда речь именно об интеграционных таблицах, а не о документированном перечитывании движком list files), sealed manifests, компилятор и классификатор diff, атомарность нескольких файлов, транзакции/rollback и безопасная передача сигналов.
3. **Нельзя заменять канон экспериментом.** В случае несоответствия результата **нашего плагина** предписанному руководством сначала диагностировать реализацию плагина, его конфигурацию, интеграцию и исполняемые аргументы. Само описание движка в каноне не оспаривать, не заводить тест «а правда ли» и не ослаблять ТЗ.
4. В проектной документации и коде **точно сохранять различие**: (a) документированное upstream поведение — принимается без испытаний; (b) обещанное/утверждённое поведение **плагина** — проверяется; (c) отсутствующая в руководстве функциональность — может потребовать отдельного теста. Приоритет документа по engine-семантике имеет указанный URL на ветке `master`; локальные выдержки, другие upstream файлы и наши наблюдения **не заменяют** его.
5. При изменении плана и после смены версии движка не создавать автоматическую «повторную проверку» описанного поведения. Уточнять только, как **плагин** формирует вызовы и соблюдает безопасность.

## Применение к ТЗ_6v5 / reload

В главе **Filtering by lists** руководство устанавливает: файлы hostlist/ipset перечитываются автоматически при изменении **без перезапуска** движка, а `SIGHUP` помечает все списки для принудительного перечитывания при обработке **следующего пакета**. Глава **Signals** документирует принудительное перечитывание по `SIGHUP`. **Это не предмет проверки.** Формулировки «нужно доказать возможность reread», «нужно испытать SIGHUP движка» и «manpage недостаточно для native PASS» запрещены.

**Что проверяем вместо этого:** чистый diff выбирает `RELOAD` только для контента уже подключённых list-файлов, а `RESTART` — при структурных изменениях; обновление идёт через один original FD9/Config writer, разрешённые пути и проверенные файлы; при необходимости сигнал направляется только в подтверждённый наш процесс; Apply не останавливает процесс или divert во время `reload`, не трогает чужой IPFW; `NO_CHANGE` не перезапускает; ошибки/откат/GUI результат правдивы. Эти требования к **плагину** не даны upstream руководством и остаются нативными acceptance gates.

**Native Auto-detect также защищён каноном:** главы **Filtering by lists** и **Autohostlist failure detector** задают upstream условия срабатывания и внесения домена в auto-list. **Не воспроизводить и не доказывать работу этого upstream алгоритма** искусственными сетевыми отказами. Для нашей P1/P2/Source Map/Found/managed цепочки принимать ранее зафиксированное событие или контролируемую fixture **как вход** и тестировать лишь маршрутизацию, сохранение, исключения, ownership, WAL/ACK и отсутствие ненужных перезапусков. Отсутствие события в эксперименте провайдера не опровергает руководство и не обязывает повторять испытание движка.

**Статусы:** пока плагин подтверждает только доставку `SIGHUP`/commit файлов, он может сообщать `RELOAD_REQUESTED` (следующий пакет ещё может не быть обработан). Отсутствие отдельного подтверждения из памяти движка **не является основанием** вводить тест/прослушивание для проверки написанного в каноне. `APPLIED_VERIFIED` допускается лишь когда подтверждены собственные шаги применения и состояние плагина, с точно указанным объёмом подтверждения; не приписывать к статусу невыполненное собственное действие. При отказе `reload` запрещён тайный `restart`.

**Сфера действия:** проект `os-zapret2-restyle`, действующая [ТЗ_6v5](TZ_6v5.md), [план S00–S20](ZAPRET2_TZ6V5_STEP_BY_STEP_PLAN.md), принцип [DEV-069](../PROJECT_PRINCIPLES.md). Прежние ограничения FD9, single process, P1/ACK и WAN-first G05/G08 сохраняются.

**Состояние документа:** docs-only, не реализация команды `reload`, не испытание engine и не подтверждение новой `.pkg`.
