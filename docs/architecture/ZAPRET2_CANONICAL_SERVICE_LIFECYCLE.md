## 3. One canonical implementation — required structure

At the privileged original service boundary, create one **authoritative, context-aware Start transition** and one **Stop transition**. Both execute only with the original held FD9 (or a proven inherited FD9 token for Lab/worker), attest a single caller/current owner, choose native committed versus legitimate legacy under one selector and preserve the original Command/PID/epoch/IPFW/Config verification. Subsystems supply validated *intent/context*, never make their own copy of the Common/legacy choice. Restart is the same guarded Stop then the same guarded Start; Apply/installer/package transactions keep required separate candidate, rollback, old/new version and receipt steps but use the exact shared physical lifecycle transitions. Do not invoke `zapret_service.sh start` from within FD9 as a nested lock or bypass its guardian.

The owner requires **real source consolidation**, not a superficial wrapper named `common_start` while separate paths still perform their own process stop/start, PID cleanup or kernel writes. A future primitive may have mode-specific implementations behind it (native Common vs legacy) but there must be **exactly one owner and one selection path for each physical Start/Stop intention**.
