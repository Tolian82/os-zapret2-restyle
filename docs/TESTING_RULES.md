# Testing, risk and verification rules

**Status:** CANONICAL · MANDATORY LEVEL 1
**Updated:** 2026-11-26

The normative home for test selection, risk classes, verification evidence, release/owner acceptance, preflight and scope-based CI qualification. Existing DEV and GH identifiers are retained. See [PROJECT_PRINCIPLES.md](PROJECT_PRINCIPLES.md) for product safety and upstream canon (DEV-069), [DEVELOPMENT_PLANNING.md](DEVELOPMENT_PLANNING.md) for functional blocks, [GITHUB_PUBLICATION.md](GITHUB_PUBLICATION.md) for GitHub operations (GH-066–GH-068, GH-070 queue and trigger governance), [DOCUMENTATION_RULES.md](DOCUMENTATION_RULES.md) for documentation and [CHAT_RULES.md](CHAT_RULES.md) for owner reporting. Specific subsystem and release criteria remain in their approved contracts.

## Engineering verification and evidence

DEV-011. **Never claim an unexecuted verification as PASS.** A test, live row, package build, restoration check, benchmark, or release gate is PASS only when corresponding evidence exists. Distinguish implementation in source, executed CI/package verification, and observed operation on installed OPNsense. State the exact scenario, candidate and evidence for a readiness claim; successful packaging or static GUI assertions do not prove that a menu opens a rendered page, that settings persist, or that voice traffic works.

DEV-012. **Diagnose from exact evidence before changing code.** Read the concrete failure, log, source, and state first; do not patch a plausible cause and retrofit the explanation.

DEV-013. **A stale test never outranks current owner canon or current architecture.** Update the stale assertion, fixture, or contract rather than bending valid implementation back toward obsolete behavior.

DEV-014. **External infrastructure failures do not justify speculative product changes.** Runner, network, service, action, or dependency outages are retried or diagnosed as infrastructure unless source evidence establishes a product defect.

DEV-015. **Unknown platform behavior is verified, not guessed.** Material OPNsense, FreeBSD, configd, package, shell, firewall, process, PHP, JavaScript, or upstream Zapret2 behavior must be checked against current source/runtime evidence when correctness depends on it.

DEV-016. **Audits and refactors are scope/risk based.** Inspect enough surrounding behavior to prove the change safe; do not repeat broad audits mechanically when existing evidence remains applicable.

DEV-041. **Live release gates are selected from current risk and evidence, not from a blanket checklist.** A live-only defect fixed by the candidate, materially changed appliance-only behavior, or affected lifecycle/restoration safety requires applicable replacement live evidence.

DEV-042. **CI, FreeBSD package qualification, and live OPNsense evidence are complementary.** None may fabricate or substitute for evidence that only another layer can establish.

DEV-043. **Known critical defects block a full release.** `RESTORE_FAILED`, unverified restoration, unexplained temporary runtime/firewall residue, or another known critical defect remains a blocker until resolved and evidenced.

DEV-044. **Only explicitly selected mandatory live rows block a given release for being pending.** Unrelated regression rows remain valuable coverage but are not silently promoted to mandatory gates; an unrun row is never rewritten as PASS.

DEV-051. **Detect automatable defects before exercising the real target execution platform.** Self-checks must exercise the changed production path with its real templates, rendering/generation machinery, produced artifacts, and the consuming interpreter or parser wherever equivalent execution is available outside the target system. Cover relevant empty, populated, edge-sized, and invalid inputs; verify the generated output and observable failure behavior, not merely source syntax, isolated mocks, or package-build success. Before opening the PR or starting long CI/package qualification, reproduce each known defect with a focused check that fails against the faulty implementation and passes with the correction; retain that check in applicable automated CI so a recurrence blocks publication. **The real target execution platform is for genuinely platform-dependent behavior and final integration/acceptance—not the primary discovery environment for errors reproducible in automated tests.** Missing off-target capabilities must be disclosed as an unverified boundary, never disguised as a PASS or delegated to the owner as routine manual debugging.

DEV-057. **Discover and classify all changed production paths before accepting a change.** Combine the actual version-control change set, including additions, deletions, renames and moves, with existing build/package metadata and coherent path policies to select the relevant checks. A new path must not evade compatibility, dependency, interpreter, packaging or caller-contract checks because it is absent from a former hard-coded path list. Unknown or conflicting classifications require a clear diagnostic and block the affected merge until resolved. Test the actual changed production path where feasible. Documentation-only work need not run the entire unrelated native platform matrix. Do not create an independently curated second package-file inventory.

DEV-058. **Validate shipped files from actual source and native package metadata, not a historical count.** Reconcile tracked production sources and deliberately generated content with the native builder's package manifest and installed files. Verify inclusion, bytes, necessary executable modes, hooks, metadata, declared dependencies and permitted generated entries. New features may legitimately increase file count; a past count or fixed filename list is not a permanent product invariant. Reject missing or unexpected payloads, unqualified executable modes and symlink behavior. Renaming or relocating a file must not remove it from verification.

DEV-060. **Bind cross-environment qualification and publication to the exact tested deliverable.** Record the source revision, qualified environment, relevant input identities and cryptographic digest of the actual output. If distinct clean, running-upgrade, reboot or other environments are said to exercise the same candidate, transfer and verify the same physical bytes instead of rebuilding independently from the same commit. A different digest is a separate artifact with separate acceptance scope. Do not publish an unchecked rebuild as a qualified binary or treat source-only success as installed acceptance. Preserve truthful PASS, PARTIAL, SKIPPED and NOT TESTED evidence boundaries.

DEV-061. **Verification is a bounded means to deliver an accepted result, not an open-ended search for certainty.** Before a logical change, define the observable user outcome, changed production paths and dependencies, required safety invariants, and the smallest checks that can establish the applicable acceptance criteria. Reuse prior qualified evidence for unchanged behavior when its source, relevant dependencies, platform assumptions and execution conditions still apply; never relabel old evidence as a PASS on new bytes. Add or repeat a test only for an affected execution path, a concrete reproducible failure, a credible change-specific safety risk, or an expressly applicable acceptance/release gate. For every additional expensive native/VM test identify the distinct risk, why prior checks are insufficient, and what decision its result can change. Speculative failure possibilities alone do not create new blocking gates or authorize unrelated matrices. **When the preselected applicable checks pass and no actual critical defect or mandatory gate remains, stop expanding tests and proceed to the authorized package, merge or owner acceptance without asking the owner to rein in testing.** A testing `.pkg` is an input to owner acceptance, not a reward after every owner-live row has passed: qualify the exact package and any changed high-risk safety behavior before handoff; keep outstanding physical acceptance marked OPEN. This rule never weakens fail-closed/FD9/Config/IPFW/process/Voice/restoration safety, exact-head merge checks, proven package identity or the full release's genuinely mandatory evidence.

Reuse existing tests first; extend a fixture or parameterize meaningful cases instead of creating overlapping suites. One targeted acceptance set applies to the completed functional block, not every internal edit. Use DEV-072 for risk classification. Do not reopen unchanged proven behavior solely because a new internal edit was made.

DEV-062. **Test real user journeys before internal breadth, with an observable red→green result.** Every user-visible or Config/transport change starts with a written shortest complete journey from the real input and native Model through Python validation, request transport, original FD9/Config owner and the consumed output (HOSTLIST/strategy/GUI), with at least one realistic boundary/invalid case. Reproduce every known relevant owner failure on the pre-fix code with a short test that truly fails; fix the cause, then run the identical test on the candidate until it passes. When a step genuinely needs OPNsense/Chromium, keep its installed evidence separate from portable checks. A successful isolated parser, mock, packaging job, synthetic read-only probe or native engine dry-run cannot be presented as successful UI Apply/save. The first automated gate is the cheapest actual changed-path journey; an unknown or safety-critical path retains fail-closed qualified checks. Track what bug the test would catch, what result it decides, scope, elapsed CI time and reused evidence. If the test cannot demonstrate a credible user-visible failure or safety invariant, do not make it an automatic blocking gate; retain optional historical matrices for explicit risk/acceptance/manual use. Follow the permanent GitHub routing contract `GH-072`.

The targeted gate and any extra S2/S3 checks follow the functional-block acceptance plan in DEV-007. Evaluate results at the production boundary; internal checks that do not change an acceptance decision are not independent blocking gates.

GH-016. **Validate the latest head with checks proportionate to the changed scope.** Pure documentation changes run the documentation, rule-reference, link, release-governance, and repository-integrity checks that can be affected, without mechanically running the full product matrix. Product or packaged-source changes run the scope-applicable product checks, not every historical regression by default. CI/workflow changes run their affected CI contracts, expanding to the general validation matrix only when its semantics actually change and require that evidence. Select the bounded check set before execution; stop adding unrelated tests after the gate passes. Never merge based on an unverified older head.

GH-017. **Read exact failed-job evidence before changing source, tests, workflow, or branch state.** Apply `DEV-012`; a plausible explanation is not enough.

GH-018. **A confirmed same-scope defect is corrected in the same PR.** Update the PR head and rerun applicable checks.

GH-019. **A stale test or CI assertion is corrected, not obeyed as obsolete product authority.** Apply `DEV-013` and preserve current intended architecture.

GH-020. **An external runner, network, action, service, or dependency outage does not justify speculative source changes.** Apply `DEV-014` and diagnose infrastructure first.

GH-021. **Only successful checks for the latest mergeable head authorize merge.** If the head changes, prior successful checks do not prove the new head.

GH-022. **Never report a skipped or unrun job as PASS.** A legitimately path-skipped build is `SKIPPED`, not successful qualification, under `DEV-011`.

GH-023. **Path-gated package builds remain meaningful.** Packaged-source or package/CI-infrastructure changes run required FreeBSD package qualification; pure docs/governance changes may skip package build when the workflow classifies them as non-package changes.

GH-062. **Быстрые локальные проверки — обязательный входной контроль ДО открытия PR и запуска длинной CI-матрицы.** Перед публикацией ветки/открытием PR с изменённым кодом, тестами или конфигурацией разработчик **самостоятельно выполняет на точных подготовленных файлах** доступные быстрые проверки синтаксиса и форматирования, целевые unit/contract/regression-тесты для изменённого поведения и **запускает каждый новый или изменённый тест**, а не только проверяет его текст. Проверяются также относящиеся к изменению версия/ревизия, заголовок PR и элементарные ошибки тестовых фикстур, регулярных выражений, shell, PHP, Python и JavaScript. **Любой провал блокирует открытие PR и долгую CI:** сначала исправить ошибку локально в том же scope, повторить быстрый тест до успеха, и лишь затем запускать полную требуемую матрицу. При каждом последующем изменении head те же затронутые быстрые проверки повторяются **до отправки изменений**. Для docs-only и изменений правил выполняются локальные проверки ссылок, идентификаторов правил, реестров перекрёстных ссылок и целостности документации; это не требует запускать продуктовую матрицу, если она не относится к изменению. Если конкретный тест технически невозможно выполнить локально (например, требуется FreeBSD 15), явно зафиксировать причину и выполнить максимально узкую доступную отдельную проверку до длинной матрицы; **не объявлять невыполненную проверку успешной**. Перечень действительно выполненных команд и их результаты отражаются в PR. Длинная CI остаётся обязательной по сфере изменения, но не служит средством обнаружения простых ошибок, которые можно найти до PR.

GH-069. **Четырёхуровневая экономная CI обязательна; объём определяется необходимыми доказательствами, не количеством тестов.** S0 — реально выполненные локально синтаксис/unit/регрессия до push; S1 — быстрые обязательные PR version/title/docs/rules/source gates; S2 — точные, обоснованные изменённым кодом нативные сценарии на одноразовых FreeBSD/OPNsense, включая FD9/IPFW/Voice/GUI только когда они затронуты; S3 — обоснованная полной финальной приёмкой или релизом комплексная package/clean/RUNNING/reboot/Voice/GUI проверка, без автоматического прогона всех исторических матриц перед каждым промежуточным testing package. Публикация промежуточного тестового `.pkg` требует достоверной квалификации его физических байтов/ABI, сборки и затронутых функций и рисков безопасности, но не заранее завершённой физической приёмки владельца: пакет является её входом. Для связанных native-проверок использовать один побайтово идентичный `.pkg` с SHA-256, когда этого требует критерий. Исторические одноразовые тесты сохранять доступными для осмысленного ручного прогона, не гонять автоматически на каждый docs/revision-only PR. Отсутствие дополнительной проверки не является дефектом само по себе: её необходимость нужно обосновать по `DEV-061`. Экономия ресурсов **никогда** не заменяет обязательный exact-head PASS, критическую безопасность или реально требуемую финальную приёмку.

**Четыре уровня S0–S3 не означают четырёх GitHub check runs.** GitHub показывает отдельные jobs (включая SKIPPED), поэтому это число не равно объёму вычислений и не должно выдаваться за «четыре проверки». Рабочая цель обычного функционального PR: быстрый S1 плюс **один** обоснованный нативный S2-набор для затронутой подсистемы. Каждая дополнительная тяжёлая VM требует конкретного объяснения независимого критерия приёмки (например, общая GUI-страница действительно затронула нижний Apply). Полная Strategy Lab corrective matrix для несвязанного first-install, документации или CI-policy запрещена: только изменения Lab/shared runtime либо явно выбранный S3. Полная обязательная релизная квалификация S3 сохраняется; для промежуточного testing package используем заранее определённые, пропорциональные изменению ограничения, а не повторяем финальную приёмку. В отчётах различать число workflows, число check runs, реально запущенные VM, SKIPPED и причины запуска. Отдельный PR budget test обязан проверять fan-out **внутри** `CI`, а не только standalone YAML.

Apply R0–R3 in DEV-072 and the functional block in DEV-007. A heavy matrix is not a default consequence of a revision or private helper. Record the independent reason for each additional native workflow. A successful exact-head PR S3 is reusable after squash only if the verified merged tree, relevant inputs and tested deliverable identity are unchanged and applicable main verification passes; it is not a new PASS on different bytes. Retain full release/owner qualification and run affected native checks whenever merge changes those inputs. See GH-026 and GH-064.

GH-071. **Native-test placement, infrastructure readiness, and strict time budgets are mandatory.** Run routine syntax, unit, contract, source, rule, and CI-policy validation as fast S0/S1 checks without provisioning a FreeBSD/OPNsense VM. An S2/S3 native test is justified only by the affected subsystem or an explicit release/acceptance criterion; do not couple a GUI localization or read-only browser smoke to historical RUNNING package upgrades, engine compilation, IPFW, or unrelated lifecycle matrices merely to obtain an installed page. Keep genuine installed OPNsense/FreeBSD and authenticated Chromium where the acceptance criterion requires them; an offline mock, source inspection, or skipped test is **not** native acceptance.

**Native execution environment:** Prefer a qualified, isolated, pre-provisioned KVM/FreeBSD/OPNsense test host (including an approved, maintained self-hosted runner) with a known guest image, installed hypervisor/dependencies, bounded access and reliable restore/cleanup. Treat it as test infrastructure, never silently use the owner's production appliance. A GitHub-hosted runner may be used only when a fast prerequisite gate verifies the **runner's own** QEMU/KVM/image/network/package-manager readiness before any long VM operation. A DNS check from the developer's PC is not evidence of runner connectivity. Cache reusable verified base images and dependency preparation where safe, with identity/invalidation checks; never cache secrets or a private owner Config.

**Budget and failure policy:** Set an explicit job timeout and individual bounds for image download, package installation, boot, SSH readiness and other potentially blocking network/VM steps; a narrow GUI smoke should have a short budget (the P3 browser workflow is capped at 15 minutes), while materially longer S3/release tests require a distinct documented rationale and intentional trigger. Detect inaccessible repositories, DNS, missing hypervisor/KVM, guest boot failure and no-progress states early. Fail closed with an explicit **infrastructure failure / NOT TESTED**, not PASS and not a product regression. Do not rerun a known failing external preflight blindly, start multiple equivalent VM jobs, or push empty commits to retry an outage; repair the environment or move the same exact-source required native test to a qualified alternate host. Preserve the evidence gate before merge/publication and distinguish S0/S1 PASS from outstanding S2/S3 and owner-live acceptance.

GH-072. **Outcome-first CI routing and real-user boundary priority are mandatory.** For every PR classify exact changed paths into lightweight GUI/domain/IPSET, critical shared Config/FD9/transport, full lifecycle or documentation-only; a new/unclassified production path fails **toward more** checking, never toward silent exemption. First run a bounded (target at most five minutes) real changed-path regression using production Model, Python bridges, shared Apply encoder/root-contract and actual UI render/semantics where portable; it must exercise the input and downstream consumer, not only regex/mocks. A known owner failure must be reproduced *before its fix* by a test that genuinely fails old code, then passes fixed code; a previously green irrelevant matrix does not qualify it. Keep separate correctness for short synthetic checks, installed native browser/FD9, exact qualified .pkg and owner appliance. Only dispatch full legacy 100-step Project/Voice matrices when critical changed paths, unknown paths or intentional manual/full release criteria warrant them; run targeted S2 native browser/FD9 only for those relevant paths. A documentation or CI-policy-only PR, even one containing a noninstalled read-only Python probe under docs/, does not launch product/VM matrices. Preserve original FD9, Config/IPFW/Voice, immutable package identity, exact-head and fail-closed gates. The native package job for actual packaged-source changes waits for the fast user-journey gate; it need not await unrelated whole-project matrices, but required critical checks **must** pass before an authorized merge/release. Record selected/missing checks and their cost in PR, and stop once the justified decisions are established. This implements `DEV-062` and supplements `GH-069`–`GH-071` without weakening them.

Distinguish governance-only integrity scripts from installed production tests. Keep a narrowly enumerated metadata allowlist, reject unknown production paths toward more checking, and run the actual modified documentation/CI-policy checks on the fast gate. Do not remove a native check merely because its filename begins with a test prefix.

DEV-072. **Four risk classes define the minimum sufficient verification scope.** Classify exact affected behavior, production paths, dependencies, failure impact and uncertainty before implementation. Mixed blocks use the highest applicable class; unknown execution paths default to R3. R0–R3 classify changes; S0–S3 under GH-069 classify execution/evidence levels.

| Risk | Scope | Minimum applicable evidence |
|---|---|---|
| R0 — minimal | Non-executable documentation, comments, wording or cosmetics with no functional effect | S0/S1 syntax, style, links, rule, version and affected presentation integrity. No product matrix/VM solely for docs/revision metadata; if actual packaged payload or UI semantics change, applicable package/UI gates still apply. |
| R1 — ordinary | Local functions, parsers, validation, ordinary UI behavior, small isolated fixes without privileged effects | Existing focused S0/S1 regression and changed-path journey where applicable; one new focused case when existing coverage is insufficient; native only for genuine platform-dependent criteria. |
| R2 — elevated | Strategy generation, list storage/processing, integration between components, resource selection | S0/S1 real changed-path regression plus one scoped S2 native scenario when required. Extra native cases require distinct uncovered criteria. |
| R3 — critical | Shared ownership, FD9/Config, IPFW, processes, privileged lifecycle, transaction/rollback, uncertain or new execution paths | S0/S1 and mandatory focused native S2 safety proof on disposable infrastructure; fault/rollback proof for actual mutations; S3 for applicable full lifecycle, final acceptance or release. Preserve fail-closed ownership, exact-head, package identity and owner-live gates. |

Before making any new or repeated test blocking, record the concrete defect or distinct safety risk, why existing coverage is insufficient and what decision can change. No blanket count or coverage percentage; no test per private helper by default. Several genuinely distinct failure modes may warrant several cases even for a two-line critical fix. A new credible critical defect or mandatory gate can expand the preselected set; otherwise stop on sufficient PASS. DEV-069 prohibits re-proving behavior documented by the canonical upstream manual; test our integration only. Full mandatory release qualification, actual FreeBSD/OPNsense evidence and owner-live acceptance remain required where applicable.
