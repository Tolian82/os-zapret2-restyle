# os-zapret2-restyle — краткий master plan

**Решение владельца 15.10.2026: сначала завершить программирование по ТЗ, потом один тестовый релиз и живые испытания.** Новый [короткий контроль завершения](VOICE_CODE_COMPLETION_GATE.md) — текущая очередь проекта; **не выпускать** тестовый/stable release и не устанавливать промежуточные ревизии на OPNsense. Пункт «проводить FreeBSD live испытания сейчас» в старых заметках больше не является немедленным следующим действием. `v0.5.2_129` остаётся Draft/неопубликованным кандидатом. После общего IPFW COMMIT повторно подтверждаются installed runtime, engine/supervisor и kernel.

**`v0.5.2_129` — после native Config::save и IPFW COMMIT общий Apply больше не объявляет успех до финального read-only подтверждения live release.** Исполнитель под исходным FD9 повторно проверяет seal кандидатного bundle, точное установленное дерево (включая `traffic.conf`, managed IPSET, native args), существующий `apply_runtime_probe` для актуального IPFW/argv/процессного census и строгую пару engine/supervisor согласно сохранённому global ON/OFF. Если после очистки stage исчез `dvtws2`/monitor, изменилось дерево или IPFW, вместо ложного `applied-id` записывается `requires-review`; откат за COMMIT не имитируется. Расширена существующая shell fault-injection matrix: success, tree drift, native probe drift, engine/monitor missing. Архитектура, GUI и frontend по ТЗ не менялись, новый recovery не добавлялся. Релиз не создавался.

**`v0.5.2_128` — ON→ON reapply отклоняет старый supervisor или осиротевший движок до запуска замены.** В общем `apply_runtime_activate` зафиксирован исходный PID monitor до вызова best-effort `supervisor_stop` (он удаляет PID-файл даже после неудачного kill). После остановки повторно проверяются живость старого PID, статус supervisor/launcher и независимый существующий `apply_runtime_attest_engine_inventory` с ожиданием нулевых `dvtws2`. Если остался supervisor, engine либо осиротевший процесс, новая копия `dvtws2` не запускается, IPFW не меняется, атомарный backup прежнего runtime сохраняется, а общий журнал отмечает необходимость проверки. Расширен существующий `test-voice-common-apply-runtime.sh`: три сценария выжившего процесса, отсутствие нового запуска, сохранение evidence и проверяемый ручной откат. Успешный ON→ON/ON→OFF продолжает использовать один штатный backend. **Без релиза, GUI и нового recovery слоя.**

**`v0.5.2_127` — починен выбор Python при производстве managed IPSET на OPNsense FreeBSD.** Общий `targets_normalize_ipset` раньше вызывал только `command -v python3`, хотя пакет зависит от `python313` и не гарантирует ненумерованный alias. На установленном OPNsense теперь используется тот же `/usr/local/bin/python3.13`, что и native Voice builder; если он отсутствует, production отказывает до записи целей. Лишь checkout/CI вне установленного пути допускает `python3.13` либо тестовый `python3`, чтобы оставить существующие интеграционные проверки пригодными. Так устраняется возможный отказ генерации пяти managed IPSET перед ON/reapply и общее поведение Strategies тоже сохраняется. Без нового dependency, GUI, daemon, recovery и релиза.

**`v0.5.2_126` — единая дедупликация Voice IPSET при изменении включённого профиля.** В GUI PHP-проверке и подготовке кандидатного Config, нативном Python Voice-компиляторе и штатном общем Targets-нормализаторе `A.B.C.D` и `A.B.C.D/32` теперь канонизируются в один IPFW host key `A.B.C.D`. Ранее комбинация могла сохраниться как два разных элемента, вызвать расхождение между управляемым IPSET, планом перехвата и выводом FreeBSD IPFW, блокируя ON/reapply. Порядок первых вхождений сохраняется; CIDR отличной длины не изменяются, host bits по-прежнему запрещены. Регрессии: GUI-кандидат, Python Voice профиль, и сквозной реальный shell Targets → пять IPSET → native Voice release/capture-plan. Frontend/ТЗ, FD9, recovery, общий WAN и релиз не менялись. `v0.5.2_125` Voice CI прошёл; общий CI дал `RESTORE_FAILED` в отдельном Strategy Lab corrective matrix, полный CI той ревизии НЕ зелёный.

**`v0.5.2_125` — повторный Start общего Voice/Strategies runtime больше не перезапускает работающий `dvtws2`.** В `shared_apply_boot_service` после проверки seal и нативного Config добавлена read-only проверка уже запущенных engine/monitor, точного установленного дерева и существующего `apply_runtime_probe` (проверка привязанных аргументов и IPFW). Если обе роли и весь runtime подтверждены, команда возвращает прежний `native-common-boot` без вызова `apply_runtime_activate` и без IPFW/процессных мутаций. Частичный engine/supervisor, несовпадающее дерево или IPFW и работающий процесс при общем `enabled=0` отклоняются. Для остановленного процесса, реального boot/restart остаётся прежний общий Apply-actuator. Дополнен существующий shell test штатного Start/Boot; новых демонов и recovery нет; релиз не создан.

**`v0.5.2_124` — общий генератор сохраняет работоспособность Strategies при полностью выключенном Voice с другим сохранённым Voice WAN.** `voice_profile_compiler.compile_candidate` ранее отвергал неактивный WAN override, хотя GUI SaveDraft разрешает его и выключенный Voice не создаёт правил. Теперь модель всех пяти сервисов проверяется до сборки, а при all-OFF эффективный WAN релиза берётся исключительно из общего Strategies WAN, без Voice/IPFW правил и без изменения сохранённого черновика. Тесты проходят через настоящий shell `orchestrator_stage_native_voice` → Python `voice_release_stage` → генератор `traffic.conf` и `capture-plan.json`, с отрицательным включением через тот же маршрут. Никаких изменений GUI, FD9, восстановления либо релиза.

**`v0.5.2_123` — исправлено сохранение и проверка полностью выключенных Voice-профилей без настроенного WAN.** Ранее `VoiceApplyCandidate::prepare` отвергал `all-OFF` при пустом общем WAN либо заранее выбранном другом Voice WAN, хотя неактивные черновики не создают dvtws2/IPFW capture. Теперь проверка совместимости WAN требуется только при наличии хотя бы одного включённого Voice-профиля; включение по-прежнему блокируется до настройки общего WAN и совпадения интерфейса. Runtime Apply по-прежнему требует независимого native preflight; TЗ/GUI, общий FD9 и recovery не изменены. **Без релиза и без заявления об успешном STUN/MEDIA/CALL.**

**`v0.5.2_122` — согласована проверка повторных STUN-параметров GUI и общего native runtime.** В существующем `voice_profile_compiler.validate_arguments` устранён реальный разрыв: дубли `--out-range` и `--lua-desync` ранее могли пройти Python staging, хотя `VoiceCandidateValidator` запрещает их в форме. **`v0.5.2_121` — подготовлена проверка реального прохождения Voice UDP на FreeBSD OPNsense без вмешательства в службу.** Новый небольшой read-only `voice_live_trial.py` использует существующий `SharedApplyOperation` и `voice_live_inspect.examine_shared` (только `committed/ready` общий владелец), читает `/sbin/ipfw -a list`, извлекает исключительно счётчики принадлежащих Voice правил и повторно проверяет неизменность владельца. Добавлены маленький offline regression для Linux/FreeBSD CI и [инструкция реальной приёмки](VOICE_LIVE_TRIAL.md). **Реальные STUN/MEDIA/CALL и GUI/CONFIG/BOOT пока не подтверждены**; Draft PR, без merge/release.

Существующий regression расширен на валидное состояние, подменённые Voice/ordinary IPSET и traffic/argv, исчезнувший IPSET. ТЗ/frontend, штатный Apply, процессы и IPFW не изменены; живой FreeBSD STUN/MEDIA/CALL по-прежнему требует испытаний, релиза нет.

Добавлен целевой regression с IPv6-only, dual-stack, повторными IPv6+IPv4 и некорректными L3 селекторами. Никакой дополнительной инфраструктуры. **Текущая ревизия: v0.5.2_66 (без релиза).** В единственном durable journal `shared-apply/operation.json` теперь фиксируется `legacy-quiescing` — первый защищённый барьер непосредственно перед будущей остановкой старого Telegram PoC. Операторский `shared-apply-legacy-begin ID` через штатный FD9 и оригинальный Config flock повторно сверяет sealed previous-five snapshot, прежние Config/runtime/marker, точные FreeBSD процессы/argv и IPFW, затем атомарно записывает фазу без остановки процесса. После reboot обычные Apply/boot-recover не переходят через `legacy-quiescing`; ручной `legacy-cancel` допустим только если прежний PoC полностью неизменён. Нет нового backend/WAL/движка, GUI/ТЗ сохранены. **Это ещё не рабочая миграция; operator arm/begin на production не выполнять.** Следом нужен один исполнитель для настоящего STOP + restore-on-failure + restart/cutover и FreeBSD owner-live/STUN/CALL тесты.

## Независимая лаборатория и persistence

- Сохранять документированную LAN/router-local/SOCKS базу: отдельные TCP/TLS parent и UDP/Zapret2 пути. Router-local без explicit SOCKS и SOCKS UDP ASSOCIATE требуют отдельной квалификации.
- Предпочитать штатный OPNsense GUI/persistence; проверить сохранность non-GUI sing-box/ACL/alias/snapshot при regeneration и reboot. Уже рабочие LAN/SOCKS TCP-parent пути сохраняются.
- Persistence выбранного Voice теперь реализуется общей native страницей; дополнительный hook/Cron enable не создаётся. После reboot проверить effective profiles, процессы/правила, LAN/SOCKS/router-local TCP и релевантный UDP до ручного исправления.
- Ручные OPNsense→TNAS SSH/два host-route repair проверены; после реального TNAS reboot остаётся owner-manual проверка восстановления. Без route Cron/configd/boot scheduling и Docker autostart.
