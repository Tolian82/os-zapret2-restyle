# v0.4.0_7 — Strategy Lab Stage-60 deadline admission

Date: 2026-08-09
Status: implementation candidate; owner-live verification pending.

## Evidence that selects this patch

Owner-live `0.4.0_6` retesting against `telegram.org` produced the same boundary in both
Standard and Extended modes:

- Stage 50 completed successfully in about 39 seconds and tested all seven reconnaissance
  families;
- Stage 60 completed 12 of 16 scheduled expansion candidates;
- the enclosing Stage-60 adapter terminated at about 70.07 seconds;
- the thirteenth candidate, `syndata-1603`, had already written its `.args` and `.spec.json`
  inputs but never produced its candidate result JSON;
- Stage 90 restored the initially RUNNING Zapret2 service successfully and no temporary
  `19100-19131` IPFW rule remained.

The Standard run still had roughly 33 seconds of its 150-second search budget available
when the local Stage-60 limit fired. The Extended run still had roughly 154 seconds of its
270-second overall budget available. This proves that the observed failure is a local
Stage-60 parent/child deadline mismatch rather than overall job-budget exhaustion.

Exact owner-live evidence is preserved in
`docs/verification/evidence/2026-08-09-v0.4.0_6-stage60-timeout.md`.

## Scope

This revision makes Stage 60 budget-aware before it starts another cold candidate. It does
not implement `_33` discovery/validation changes and does not claim that all remaining
`_32` timeout-hierarchy work is closed.

## Changes

- bump the plugin revision to `0.4.0_7`;
- retain the eight-second cold expansion-candidate limit;
- replace the arbitrary 70-second Stage-60 ceiling with a 120-second ceiling, still capped
  by the existing Standard search deadline, so Stage 60 can use the search budget that is
  actually available instead of self-expiring early;
- before preparing or launching every Stage-60 candidate, require room for the complete
  bounded envelope: candidate execution + termination reserve + cleanup reserve + admission
  guard;
- use the same default reserves already established by the Stage-50 containment work:
  2 seconds termination, 7 seconds cleanup and 2 seconds admission guard;
- when the next candidate cannot fit, do not create its runtime input files and do not
  launch it;
- persist the completed Stage-60 evidence with `partial=true`,
  `stopped_reason=insufficient_stage_budget`, and an explicit budget-admission record;
- persist that partial result into the automated job state before returning timeout status;
- emit timing telemetry for the rejected admission decision;
- bound forced Stage-60 cleanup with the same seven-second cleanup reserve instead of the
  previous unrelated 15-second cleanup timeout.

The 120-second Stage-60 setting is **not** an attempt to hide the defect by merely moving
70 seconds to a larger number. The job-level Standard deadline remains 150 seconds and
continues to cap the stage. The new admission rule is the safety property: a candidate is
started only when its entire bounded lifecycle fits inside the remaining parent window.

## Expected behavior

For the measured `telegram.org` no-winner path, the larger stage ceiling should allow the
16-node expansion graph to finish when real candidate durations remain near the observed
5.5 seconds. If slower live conditions leave insufficient room, Stage 60 must stop before
starting the next candidate and terminate truthfully as TIMEOUT with structured partial
evidence; it must never fabricate `NO_CANDIDATE` from an incomplete graph.

## Boundary

`_32` remains open after this source patch until owner-live evidence is reviewed. Stage-70
and Stage-80 candidate admission plus explicit Stage-85/restoration parent bounds remain
separate acceptance work within `_32`. `_33` remains out of scope.

## Live acceptance

Retest `telegram.org` in Standard mode first, then Extended mode if the Standard result is
safe and coherent. Preserve the job status and timing telemetry.

Immediate acceptance conditions:

1. Stage 50 remains PASS.
2. Stage 60 is not killed in the middle of a newly admitted candidate.
3. If Stage 60 exhausts the graph, it publishes the complete structured result and allows
   later stages to proceed.
4. If Stage 60 lacks room for the next candidate, the result says
   `stopped_reason=insufficient_stage_budget`, is marked partial, and the rejected candidate
   has not been started.
5. Stage 90 restores the exact initial Zapret2 state.
6. No temporary Strategy Lab process or IPFW rule remains after terminal completion.
