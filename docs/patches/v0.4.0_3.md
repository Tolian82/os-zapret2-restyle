# v0.4.0_3 — CandidateSpec and ResourceInventory

Status: **SOURCE-QUALIFIED / NOT PUBLISHED OR OWNER-TESTED**

## Purpose

Implement adaptive-search `_29` as one candidate/resource ownership change without
pulling `_30` search-graph/catalog work forward. Python must own the complete normalized
candidate description, installed-resource eligibility and exact dvtws2 runtime rendering;
active shell adapters must retain only audited FreeBSD/IPFW/dvtws2 system actions.

## CandidateSpec contract

Every automated candidate attempt is represented by an immutable normalized Python
`CandidateSpec` that preserves:

- stable candidate identity and metadata-only family/provenance/cost/complexity fields;
- L3, transport, port, L7 and payload filters;
- ordered `--lua-desync` actions with every argument;
- optional input/output ranges, including a non-`-d10` value or no explicit range;
- BLOB-free, built-in, inline and installed-external resource requirements;
- functional Lua dependencies and target-binding requirements;
- the exact native strategy and exact rendered runtime argument vector.

The current fixed catalogs still use `-d10`; `_29` stores that value as candidate data
instead of allowing shell to inject it. New ranges, candidates and graph neighbors remain
`_30` work.

## ResourceInventory contract

At job initialization Python writes one immutable `resource-inventory.json` containing:

- every installed `/usr/local/etc/zapret2/lua/*.lua` resource;
- every installed `/usr/local/etc/zapret2/files/fake/*.bin` resource;
- Zapret2 built-in BLOB names and inline `0x` capability;
- stable resource names, resolved paths, sizes, mtimes and a deterministic inventory
  identity.

Later filesystem changes do not rewrite the job snapshot. Missing or empty resources
required by a candidate fail before dvtws2 starts. Installed resources that a candidate
does not declare remain evidence only and are not loaded automatically.

Static candidates declare `zapret-lib.lua` and `zapret-antidpi.lua`. Upstream
`zapret-antidpi.lua` documents those two startup dependencies; `zapret-auto.lua` is an
automation/orchestration library and remains discoverable inventory rather than an
unconditional static-candidate dependency.

## Adapter boundary

Python writes the target hostlist and exact `candidate-runtime/dvtws.args`, including
declared Lua initialization, external-resource path binding, filters, selector and range.
It then requests only generic protocol firewall installation plus existing runtime
start/readiness/counter/cleanup actions.

`strategy_lab_candidate_adapter.sh` and
`strategy_lab_profile_candidate_adapter.sh` no longer scan Lua/fake directories, choose
BLOBs, inject `-d10`, replace profile selectors or select search policy. Historical shell
helpers retained for compatibility/private paths are not automated owners.

## Evidence and compatibility

Candidate success, structured error and timeout records include normalized
`candidate_spec`, `resource_inventory_id` and exact `runtime_arguments`. Public stage
numbers, result shapes, cold candidate lifecycle, budgets, catalogs, QUIC branch,
stability/replay policy and mandatory Stage-90 restoration remain unchanged.
