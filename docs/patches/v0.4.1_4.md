# v0.4.1_4 — Measure BLOB common-set scaling

Status: **SOURCE MEASUREMENT / CI PENDING / OWNER-LIVE PENDING**

## Scope

Measurement-only Strategy Lab experiment for the remaining BLOB-loading question after the
accepted `_3` run. Production Model C, Model B fallback, cold Model A, CandidateSpec semantics,
source-port attribution, adaptive budgets and normal Zapret2 lifecycle behavior are unchanged.

## Why `_4` exists

`_3` established that one built-in fake and one representative `226`-byte external fake do not
show a material startup/readiness or RSS penalty relative to BLOB-free startup on the owner
appliance. It did not answer whether Model C pays measurable cost when a bucket eagerly declares
resources belonging to several candidates.

Production Model C collects compatible candidate `--blob=` declarations into one common worker
before candidate-specific selector chains. `_4` therefore measures declaration-set scaling rather
than repeating the one-BLOB experiment.

## Controlled variants

All four variants use exactly one adapter worker (`external`) and one divert port (`9992`). The
same Lua/filter/action shape is retained and only the resource set changes:

1. `blob-free` — no BLOB declaration or pattern;
2. `inline-small` — `seqovl_pattern=0x1603`, no external declaration;
3. `external-single` — one canonical `fake_tls_7` declaration, used by the active action;
4. `external-common-3` — three canonical TLS external declarations:
   - `fake_tls_7` — active pattern;
   - `tls_clienthello_rutracker_org_kyber` — eagerly declared but unused by the active chain;
   - `tls_clienthello_vk_com_kyber` — eagerly declared but unused by the active chain.

The three-resource set is a bounded synthetic upper-bound for the current production candidate
width of three. It is not a claim that the current search graph always places these exact three
resources in one bucket. The two extra resources are chosen because they are semantically
compatible TLS ClientHello resources, not unrelated files added merely to inflate count.

## Measurement controls

Policy: `blob-common-set-scaling-v1`.

- schema `2`;
- one physical worker and one divert port across every variant;
- arguments are rewritten immediately before each launch so variants cannot overwrite one
  another before sampling;
- default 12 trials per variant, 48 starts total;
- accepted trial counts are balanced multiples of four: 4, 8, 12 or 16;
- four cyclic order rotations remove simple first/last-order bias;
- `cache_policy=natural-cache-no-drop`;
- readiness still requires two consecutive qualified snapshots;
- settled RSS is sampled after the existing 200 ms delay;
- summaries retain min/median/p90/max and add mean/stdev so normal jitter is explicit;
- report records canonical resource paths, declaration count, declared bytes and the two
  intentionally unused eager declarations in the common set.

Primary comparison:

`external-common-3` vs `external-single`.

Supporting comparisons:

- `inline-small` vs `blob-free`;
- `external-single` vs `blob-free`;
- `external-common-3` vs `blob-free`.

## Isolation / safety

The existing lifecycle-owned measurement wrapper is retained. `_4` MUST NOT:

- install experiment traffic routes;
- stop/start/reconfigure normal Zapret2;
- modify the production Traffic Strategy, targets or resource files;
- change Model C/B/A production execution;
- leave temporary worker/rule/socket state after completion.

Initial/final semantic service evidence and cleanup remain mandatory acceptance gates.

## Decision boundary

`production_change_recommended=false` remains hard-coded.

A valid `_4` owner run does not itself authorize production BLOB-loading changes. If the
three-resource common set shows a material cost above observed jitter, reproducibility is required
before a separate production patch is considered. If no material cost appears at the current
production-width upper bound, the BLOB-loading optimization can be closed as a negative result for
the present width-three architecture.
