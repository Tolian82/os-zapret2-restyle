# v0.4.0_19 — Model B exhaustive multi-endpoint reference corrective

## Evidence selecting this patch

The owner installed the published `_18` measurement line and created a fresh Standard
`telegram.org` cold reference with a benchmark-only `STRATEGY_LAB_STANDARD_BUDGET=210`
override. Job `job.tMYnFA` completed truthfully:

- terminal outcome `NO_CANDIDATE`;
- Stage 60 `total_available=16`, `completed=16`;
- `working=[]`;
- `stopped_reason=graph_exhausted`;
- `partial=false`;
- persisted `candidates` and `schedule` both contain all 16 entries;
- semantic restoration is verified RUNNING -> RUNNING with the strategy unchanged and
  temporary runtime clean.

The first `_18` exhaustive Model B attempt then ended before any warm batch or probe with:

`error="exhaustive Model B requires one pinned endpoint"`.

Its report had no reference/timing/comparison payload and no batches, while final cleanup
and semantic restoration were verified. The live Strategy Lab target evidence contains
more than one required pinned endpoint for `telegram.org` (`telegram.org` and
`web.telegram.org`). The `_18` single-endpoint precondition was therefore a measurement
harness defect, not a Model B coexistence/runtime failure.

Exact owner-live evidence is preserved in
`docs/verification/evidence/2026-08-11-v0.4.0_18-model-b-exhaustive-multi-endpoint-gap.md`.

## Scope

This is a narrow experiment-only corrective. It does not change normal Strategy Lab,
production Model A execution, adaptive candidate ordering, normal search budgets, worker
width, divert ports/rules, or probe parallelism.

## Changes

- bump the plugin revision to `0.4.0_19`;
- allow an exhaustive reference search epoch to contain one or more pinned endpoint
  bindings instead of requiring exactly one;
- validate every reference endpoint and selected IP, retain their original order, and
  reject duplicate endpoint names;
- write all pinned reference endpoint names into each target-bound warm worker hostlist;
- for each Stage-60 candidate, replay every pinned endpoint sequentially against its own
  fixed selected IP;
- classify the warm candidate as PASS only if every pinned endpoint probe passes, matching
  the cold Strategy Lab `all_pass` contract; any non-PASS endpoint keeps the no-candidate
  replay non-PASS;
- retain per-endpoint route/interception/classification evidence inside each candidate
  probe record;
- require `reference_endpoint_bindings=true` and
  `all_reference_endpoints_replayed=true` for preliminary acceptance;
- retain exact Stage-60 corpus order, at most three warm workers per batch, sequential
  routing, numeric RSS, worker identity/readiness checks, cleanup between batches and final
  semantic restoration;
- extend the focused regression from one endpoint to two pinned endpoints and prove that
  every candidate replays both endpoints in exact order and routes each endpoint to its
  own selected IP.

## Measurement semantics

Candidate-level warm timing now represents the complete sequential endpoint set for that
candidate. Endpoint-level dispatch/probe medians are also retained separately. This keeps
the comparison meaningful for real Strategy Lab domain targets with multiple required
endpoints.

The benchmark remains:

- `experiment_only=true`;
- `parallel_probes=false`;
- `production_approved=false`.

## Live recheck

After `_19` FreeBSD qualification and testing-prerelease publication, install `_19` and
reuse fresh reference `job.tMYnFA` if its persisted `ResourceInventory` still matches the
installed Zapret2 resource inventory. A new 210-second cold run is not required merely
because the experiment harness code changed.

Acceptance requires:

1. the reference is accepted with all pinned endpoint bindings;
2. all 16 Stage-60 candidates are replayed in exact order;
3. every candidate replays every pinned endpoint sequentially;
4. no warm candidate becomes a false PASS relative to the cold no-candidate reference;
5. all batch readiness, worker-identity, RSS, route-attribution and cleanup checks pass;
6. final semantic restoration is verified;
7. final `conclusion=accept`.

Only after that result may the measured exhaustive Model A/Model B timing comparison be
used for the architecture decision.
