Status: **DOCS / GOVERNANCE ONLY**

## 1. What changes and why

The project already had the correct 2026-07-28 decision that documentation is part of architecture
and critical knowledge must live in the repository rather than chat history/model memory.

The process failure was that this principle and other settled working principles lived in
`DECISIONS.md` / `WORKING_CONVENTIONS.md`, while mandatory startup reading did not guarantee those
files were loaded in every new context. At the same time current-state/roadmap documents lagged from
`_6/_7` while packaged source advanced to `_12`. A new session could therefore obey the visible
startup procedure yet still miss permanent principles/current plan and spend hours rebuilding context.

This docs-only patch:

- creates `docs/PROJECT_PRINCIPLES.md` as the single concise always-read canonical principles layer;
- changes mandatory context order to
  `AGENTS -> PROJECT_PRINCIPLES -> START_HERE -> PROJECT_STATE -> task specialists`;
- makes `START_HERE.md` the operational handoff for exact next work;
- refreshes `PROJECT_STATE.md` from stale `_6` to current `_12`;
- refreshes `ROADMAP.md` from stale `_7` to current `_12 -> _13` plan and long-term backlog;
- rebuilds `INDEX.md` as navigation rather than a large mandatory current-history list;
- makes `WORKING_CONVENTIONS.md` procedural and refer to canonical principles instead of competing
  principle formulations;
- updates GitHub publication/workflow procedure to use scope-first inventory;
- records mandatory pre-publication plan reconciliation;
- records the exact root cause in
  `DEC-2026-08-14-operational-handoff-and-scope-first-preflight.md`.

Non-goals:

- no packaged/runtime source change;
- no Model-C behavior change;
- no package revision increment;
- no prohibition on audits;
- no deletion of historical decisions/evidence;
- no weakening of GitHub-plugin-first, evidence-first, CI, package/release or runtime safety rules.

A new/resumed project context must always load the same permanent principles before current state and
specialist work. It should then immediately know:

- current `0.4.1_12` packaged source identity;
- current accepted Model-C evidence;
- that B/A automatic production fallback is the remaining transition tail;
- exact next source patch `_13`;
- source files to start from;
- expected `_13` result/verification;
- immediate and long-term plan.

Expected process behavior:

- documentation, not chat memory, supplies current project truth;
- permanent principles cannot be accidentally skipped by the startup reading order;
- ordinary known-scope work does not enumerate unrelated branches/workflows/tags/releases/artifacts;
- broad audits still use broad reading/recursive-tree indexing when the plan/owner/evidence requires
  it;
- every future GitHub delivery contains synchronized documentation for:
  1. what changes and why;
  2. expected result and acceptance;
  3. complete next plan;
- immediately before publication, the current/long-term plan is rechecked and updated if the work
  changed it.
