# v0.4.0_18 — Model B exhaustive no-candidate benchmark

## Scope

This patch adds an experiment-only benchmark for the worst-case Strategy Lab search path.
It does not switch production Strategy Lab away from Model A and does not approve warm
workers for production use.

The benchmark exists because a successful target can stop Stage 60 early after enough
working candidates are found. That path is not representative of maximum user wait time.
A `NO_CANDIDATE` target that ends Stage 60 with `stopped_reason=graph_exhausted` is the
correct workload for exhaustive search timing.

## Prior evidence

The owner-live `_17` repeated coexistence set produced five consecutive Model B accepts
with verified restoration. Mean pool startup was `1163.6 ms`, mean dispatch median
`12.4 ms`, and mean probe median `200.3 ms`.

Relative to the accepted Model A cold total-candidate median of `1580 ms`:

- the already-warm dispatch+probe path is about `86.5%` lower;
- amortizing the three-worker startup over three probes gives about `600.6 ms/candidate`,
  or roughly `62.0%` lower than the cold median.

Those percentages describe the small coexistence experiment only. They are not presented
as full Strategy Lab or worst-case search speedups.

Exact reproducibility evidence:
`docs/verification/evidence/2026-08-11-v0.4.0_17-model-b-reproducibility.md`.

Historical current-architecture no-winner evidence already shows why this distinction
matters. On `v0.4.0_9`, Standard `telegram.org` `job.tU3wiL` checked all 16 Stage-60 graph
candidates, ended `graph_exhausted`, and took about `144.125 s` through mandatory
restoration. Standard `rutracker.org` `job.UPRDlc` stopped after six Stage-60 candidates
once three working candidates were found and completed in about `71.023 s`.

## Benchmark contract

New entry point:

`/usr/local/opnsense/scripts/OPNsense/Zapret/strategy_lab_model_b_exhaustive.sh REFERENCE_JOB OUTPUT`

The reference job must be:

- a completed Standard domain job;
- terminal outcome `NO_CANDIDATE`;
- Stage 60 `stopped_reason=graph_exhausted`;
- zero Stage-60 working candidates;
- complete persisted Stage-60 `candidates` and `schedule` arrays;
- verified semantic restoration with clean temporary runtime;
- based on the same current `ResourceInventory` as the benchmark run.

For the owner measurement, create a fresh Standard `telegram.org` no-candidate job on the
same packaged candidate before running this benchmark. This keeps endpoint, provider path,
resource inventory and cold reference contemporaneous.

## Batched warm design

The benchmark deliberately retains the already owner-proven Model B coexistence width:
**at most three warm dvtws2 workers at once**.

It does not start all exhaustive candidates simultaneously. The exact persisted Stage-60
corpus is partitioned into ordered batches of up to three candidates. Each batch:

1. verifies the dedicated Model B ports/rules are free;
2. renders the exact retained `CandidateSpec` records into the three physical Model B
   worker slots;
3. starts those workers before their probes;
4. requires stable readiness and numeric RSS;
5. executes candidate probes sequentially in the original Stage-60 order;
6. permits only the selected candidate's temporary IPFW route for each probe;
7. requires interception attribution and no inactive Model B route;
8. requires each no-candidate replay to remain a non-PASS result;
9. verifies the workers remain healthy during the batch;
10. cleans the complete batch before the next batch starts.

This design measures a practical Model B throughput option without introducing the new
memory/lifecycle risk of 16 resident workers or true parallel candidate probing.

## Measurements

The report records:

- exact reference candidate count and order;
- cold Stage-60 candidate runtime sum from the persisted adaptive schedule;
- cold full-job `job_total` telemetry when available;
- warm exhaustive search wall time;
- per-batch and aggregate pool-startup time;
- per-batch cleanup time;
- dispatch/probe medians;
- per-batch RSS and peak aggregate batch RSS;
- per-candidate cold classification and warm search classification;
- exact corpus-order completeness;
- route attribution and worker-health checks;
- final lifecycle restoration.

The benchmark calculates two clearly separated comparisons:

- `candidate_runtime_speedup_percent`: measured warm exhaustive runtime versus the cold
  sum of the same persisted Stage-60 candidate executions;
- `projected_full_job_speedup_percent`: a projection using
  `cold_job_total - cold_stage60_candidate_runtime + warm_exhaustive_search`.

The second value is explicitly marked as a projection, not a measured full Strategy Lab
run under Model B.

## Safety and acceptance

The benchmark remains:

- `experiment_only=true`;
- `parallel_probes=false`;
- `production_approved=false`.

Preliminary acceptance requires:

- current resource inventory identical to the reference;
- graph-exhausted no-candidate reference contract;
- complete exact-order corpus replay;
- every warm batch ready;
- numeric RSS evidence;
- no false PASS relative to the cold no-candidate search;
- deterministic route/interception attribution;
- workers remaining healthy during sequential probes;
- verified cleanup between batches;
- sequential-probe contract retained.

Final `conclusion=accept` additionally requires the existing semantic lifecycle finalizer:
initial/final service state, effective configuration, runtime arguments and normal firewall
must match, and temporary Model B runtime must be clean.

Any failed batch readiness stops that batch before probes and falls through to the common
cleanup/restoration path. The `_17` failed-readiness safety boundary is therefore retained.

## Non-goals

This patch does not:

- replace production cold Model A execution;
- change adaptive candidate ordering or early-stop semantics;
- test Model C;
- add true parallel candidate probes;
- start more than three warm workers at once;
- claim the projected full-job speedup as measured production performance;
- alter normal Strategy Lab timeout values from benchmark evidence before owner-live data
  is collected and reviewed.
