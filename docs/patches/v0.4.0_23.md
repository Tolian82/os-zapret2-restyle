# v0.4.0_23 — Production Stage 60 Model C

## Scope

This packaged patch changes **Stage 60 runtime execution only**. The native Zapret2 search graph, adaptive frontier/order, Stage-60 winner/budget/cancellation policy, pinned endpoint epoch, Stage 70/80/85 ownership and Stage-90 semantic restoration remain unchanged.

## Production switch

Normal Stage 60 now prefers `C-warm-bucket-source-port-dispatch`.

For each already-resolved adaptive frontier batch, up to three candidate tasks share **one physical warm `dvtws2` process**. Candidate probes may overlap up to width three; pinned endpoints inside one candidate remain sequential.

The candidate selector is deterministic and auditable:

- every candidate/endpoint probe keeps the existing unique controlled TCP source port;
- temporary IPFW rules remain exact source-port + pinned-destination + TCP/443 routes;
- all active Model-C routes divert to the one bucket worker;
- `zapret-auto.lua` `condition` instances wrap each candidate's existing Lua action chain;
- packaged `strategy_lab_model_c.lua` compares the client source port and fails closed on missing/invalid packet or selector metadata;
- every condition records `candidate_id`, the exact accepted source-port set and the exact number of following Lua instances.

## Candidate semantic preservation

Model C does not rewrite `CandidateSpec` identity. The bucket renderer preserves, per candidate:

- exact ordered `--lua-desync` action instances and arguments;
- exact `--payload` filter;
- exact candidate `--in-range` / `--out-range`, including the existing `-d8` regression and normal `-d10` candidates;
- built-in/inline/external BLOB identity, with external files resolved from the job's immutable `ResourceInventory`;
- the existing target hostlist and fixed endpoint epoch.

Candidates outside the compatible IPv4/TCP/443/TLS fragment bucket or with unsupported directives are not approximated. Model C fails closed instead.

## Fallback boundary

The accepted `_22` Model B implementation is retained unchanged as the first runtime fallback/reference. If Model C cannot prove selector file availability, compatible rendering, BLOB identity, worker readiness, source-port ownership, route attribution, required overlap or cleanup, Model C is disabled and the same already-planned work is executed by `B-warm-worker-parallel-batched`.

If Model B also cannot prove its warm infrastructure, the existing cold Model A fallback remains authoritative. Ordinary candidate network FAIL/timeout is still candidate evidence and is not by itself a runtime-infrastructure fallback trigger.

Explicit diagnostic override remains available through `STRATEGY_LAB_STAGE60_MODEL=model-b` or `cold`; normal unset operation selects Model C. Legacy `parallel` is treated as the Model B override.

## Safety / lifecycle

- maximum candidate concurrency remains 3;
- there is no CPU-count gate;
- one Model-C bucket contains at most the currently admitted frontier batch;
- batch cleanup runs before the next bucket and on every exit/signal path;
- dedicated rules remain `19128-19130` and are removed during cleanup;
- the existing lifecycle lock and final Stage-90 semantic restoration remain mandatory.

## Verification

Automated coverage must prove:

- Model C is the normal packaged Stage-60 owner;
- one physical divert worker and three distinct exact route rules;
- exact source-port selector configuration;
- preserved `-d8` / `-d10`, payload, Lua action and external-BLOB rendering;
- candidate-level width-three overlap with sequential endpoints;
- exact `_21` route-attribution reuse;
- Model C -> Model B -> cold Model A fail-closed chain;
- unchanged adaptive frontier/budget/cancel/Stage-70 handoff and cleanup contracts.

After CI and FreeBSD 15 package qualification, publish `v0.4.0_23` as a testing prerelease. Owner-live verification is intentionally after publication and should first exercise a Standard no-candidate graph-exhaustion run and a Standard working-candidate run, then inspect Model-C bucket/selector/fallback/cleanup evidence.
