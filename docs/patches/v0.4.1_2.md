## Key finding

All 16 current native TLS 1.3 expansion candidates declare the same two CandidateSpec Lua
dependencies: `zapret-lib.lua` and `zapret-antidpi.lua`. Current Model C already initializes
the batch union of those dependencies plus required shared `zapret-auto.lua` and
`strategy_lab_model_c.lua`.

Therefore current/common Model-C initialization and the candidate-minimal union are the same
four-file set for every native width-three batch. `_2` is a valid negative optimization
result rather than a timing/RSS improvement.

Accepted owner-live report:

- `policy=lua-init-set-equivalence-v1`;
- `candidate_count=16`;
- `all_candidates_same_dependencies=true`;
- every batch `equivalent_init_set=true`;
- `checks.all_required_files_present=true` on the canonical installed Lua root;
- `runtime_comparison_required=false`;
- `timing_claim=not_applicable_equivalent_init_set`;
- `rss_claim=not_applicable_equivalent_init_set`;
- `conclusion=equivalent_init_set`.

## Measurement-path correction carried forward

The `_2` command defaulted to `/usr/local/share/zapret2/lua`, while production
`ResourceInventory` uses `/usr/local/etc/zapret2/lua`. The first owner invocation therefore
reported the three Zapret2 Lua files absent. Re-running the unchanged measurement with
`--lua-dir /usr/local/etc/zapret2/lua` proved all required files present and all init sets
equivalent. This is a measurement-only default-path defect; production Model C was not
affected. The next packaged measurement patch must use the canonical ResourceInventory path.
