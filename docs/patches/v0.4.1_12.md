# v0.4.1_12 — Correct warm-worker readiness polling latency

Status: **SOURCE CORRECTIVE / OWNER-LIVE REQUIRED**

## Trigger

The owner-live `v0.4.1_11` Model-C lifecycle run completed all five repeats without fallback, with complete RSS/lifecycle evidence. Its warm-worker startup accounting repeatedly showed approximately `1056–1066 ms` for one physical profile segment and approximately `2116–2126 ms` when one logical batch contained two sequential profile segments.

Previously accepted BLOB startup/readiness evidence used the same worker snapshot predicates with 25 ms polling and measured stable readiness near 63 ms. Source inspection then confirmed that the shared production warm-worker helper still slept one full second between the two required stable snapshots.

## Corrective

`strategy_lab_py/model_b.py` keeps the existing readiness proof:

- process identity present;
- divert socket ready;
- clean worker log;
- two consecutive qualifying snapshots;
- four-second overall readiness bound.

Only the polling cadence changes from a fixed one-second interval to 25 ms, matching the already accepted BLOB startup measurement method. The helper remains shared by Model C and the accepted warm Model-B path.

## Boundaries

Unchanged:

- adaptive search graph and planner;
- candidate order and identity;
- Model-C logical batching/profile segmentation;
- source-port leasing and route attribution;
- candidate concurrency width three;
- discovery GET-4K policy;
- Model C -> Model B -> Model A fallback chain;
- cleanup and restoration semantics.

## Verification

A focused regression simulates the readiness clock and proves:

1. two consecutive good snapshots are still required;
2. a failed snapshot resets the stability counter;
3. the poll interval is 25 ms;
4. the overall readiness wait remains bounded at four seconds;
5. no one-second readiness polling interval remains in the helper behavior.

After latest-head CI, FreeBSD 15 package validation and publication, owner-live verification must rerun the retained lifecycle replay and compare `pool_startup_ms`, Stage-60 wall time, RSS, fallback state and cleanup/restoration against `_11`.
