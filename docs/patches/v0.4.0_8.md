# v0.4.0_8 — Strategy Lab late-stage timeout containment

Date: 2026-08-10
Status: implementation candidate; owner-live verification pending.

## Evidence that selects this patch

Owner-live `0.4.0_7` runs against `telegram.org` closed the Stage-60 defect and exposed
the next timeout boundary cleanly:

- Standard `job.RFVs75`: Stage 60 PASS after 90.243 s and all 16 candidates; total job
  time through restoration 145.181 s;
- Extended `job.QbUuYO`: Stage 60 PASS after 89.249 s and all 16 candidates; Stage 80
  completed; total job time through restoration 169.427 s;
- Stage 70 had only 13–14 seconds of Standard-search budget remaining in the measured
  no-winner path;
- Stage 85 completed quickly because there were no finalists, but telemetry recorded no
  parent operation timeout;
- Stage 90 restoration took about 6.9 seconds in both runs, also without a Python parent
  timeout;
- both runs restored the initially RUNNING service and left no temporary Strategy Lab
  IPFW rule.

Exact evidence is preserved in
`docs/verification/evidence/2026-08-10-v0.4.0_7-late-stage-pass.md`.

## Scope

This is the final `_32` source slice. It closes late-stage timeout containment without
implementing `_33` search-quality changes.

It does **not** change:

- the 150-second Standard search budget;
- the additional 120-second Extended budget;
- the verified Stage-60 admission logic;
- discovery probe semantics;
- the current three-attempt stability requirement;
- finalist deep-validation semantics;
- warm-runtime architecture.

## Changes

- bump the plugin revision to `0.4.0_8`;
- route Strategy Lab orchestration/search/extended commands through a narrow Python
  late-containment layer while preserving the existing authoritative modules;
- Stage 70 checks the full cold-candidate execution + termination + cleanup + admission
  envelope before the first stability attempt and again before every later attempt;
- when Stage 70 cannot safely start the next attempt, persist `stability.json` with
  `partial=true`, `stopped_reason=insufficient_stage_budget`, the exact next candidate /
  attempt and remaining-vs-required budget, then return timeout before launching it;
- Stage-80 TCP/QUIC/configured-UDP candidate execution uses the same pre-launch admission
  rule inside the existing one shared Stage-80 budget;
- when a Stage-80 candidate cannot fit, persist the protocol result as partial with the
  same structured admission evidence before returning timeout;
- Stage 85 receives an explicit parent operation limit, default 120 seconds, still capped
  by the remaining overall search deadline;
- mandatory Stage 90 restoration receives an explicit separate Python parent bound,
  default 180 seconds, outside exhausted search budget when necessary;
- the restoration parent bound is deliberately larger than the existing shell lifecycle
  transaction: that transaction can contain two 45-second start attempts plus bounded
  stop/normalization and cleanup work, so a short parent watchdog would be invalid;
- publish all late-stage timeout defaults through `strategy_lab_python_launcher.sh`;
- add a focused regression for Stage-70/80 admission plus Stage-85/restoration parent
  bounds and include it in the Python search/extended continuity gate.

## Containment model after `_8`

The executable timeout hierarchy becomes:

`operation <= candidate <= stage <= search budget`

with mandatory Stage-90 cleanup/restoration bounded separately after search budget
exhaustion, as required by the corrective contract.

A parent stage may still finish as `TIMEOUT`; the safety property is that Stage 70 and
Stage 80 do not knowingly start a new cold candidate when its complete bounded envelope
cannot fit. Stage 85 is guaranteed to have a parent bound, and any Stage-85 timeout is
followed by mandatory bounded restoration.

## `_33` boundary

`_8` does not attempt to make the current Stage-85 profile replay cheaper or smarter.
The approved `_33` cycle still owns:

- lightweight discovery selection;
- fail-fast 3/3 stability;
- two-to-three finalist selection;
- bounded real-GET deep validation and byte-count evidence.

Those changes may reduce late-stage work substantially, but they are not required to
close the `_32` safety defect.

Retest `telegram.org` in Standard and Extended mode.

Immediate acceptance conditions:
