# v0.4.1_7 — Measure Model-C per-batch lifecycle amortization

Status: **SOURCE / CI / FREEBSD15 PACKAGE / PUBLICATION / OWNER-LIVE PENDING**

## Scope

Measurement-only Strategy Lab experiment. Production Model C, Model B fallback, cold
Model A, adaptive planner, candidate width, source-port attribution, discovery GET-4K,
CandidateSpec semantics and normal Zapret2 lifecycle behavior remain unchanged.

## Why `_7` exists

Source review after the accepted `_2` through `_6` measurement sequence corrected the
next optimization question. Current production Model C is already lazy at the adaptive
batch boundary: the planner admits a currently reachable batch first, then one physical
bucket is rendered/launched for that batch and cleaned before a later batch is admitted.
There is no eager fleet of dormant branch buckets to optimize away.

The remaining measurable question is therefore the cost of repeating the existing
per-batch lifecycle itself. `_7` measures how much Stage-60 time is spent outside the
parallel candidate probes — including launch/readiness, setup/bookkeeping and cleanup —
and calculates a deliberately conservative upper bound on what any future cross-batch
keep-warm/reuse design could save after the first reached batch.

## Measurement design

Policy: `model-c-batch-lifecycle-amortization-v1`.

The packaged measurement:

1. consumes a completed owner-live reference job whose Stage 60 used production Model C
   with no Model-B fallback and reached at least two Model-C batches;
2. verifies that the current installed Zapret2 resource inventory still matches the
   reference inventory;
3. creates an isolated job-root copy containing only the immutable Stage-60 inputs
   (`endpoints.txt`, `search-epoch.json`, `resource-inventory.json` and Stage-50 evidence);
4. invokes the unchanged `stage60_model_c.expand()` path under the same discovery probe
   tier and `stage60_source_port_lease.install()` context as production;
5. instruments the already-leased `_bucket_batch` from outside production code so the
   measured outer batch wall time includes the normal `finally` cleanup boundary;
6. repeats the isolated Stage-60 replay five times by default (accepted range 3–12);
7. compares every replay with the reference result signature and requires an identical
   persisted Model-C batch sequence with no fallback;
8. finalizes only after reserved warm-runtime cleanup and exact semantic restoration of
   the normal Zapret2 service.

The original reference job is never used as the replay job root and is not modified by
the measurement.

## Recorded evidence

Per repeat:

- total Stage-60 wall time;
- first returned Model-C batch latency from Stage-60 start;
- reached batch count and exact candidate IDs per batch;
- physical bucket outer wall time;
- production-reported batch time;
- worker pool startup/stable-readiness time;
- parallel candidate-probe wall time;
- post-report cleanup-tail time;
- setup/bookkeeping remainder;
- non-probe lifecycle upper-bound time;
- ready RSS from normal Model-C batch evidence;
- source-port lease replacement count;
- exact result equivalence and persisted batch-sequence equivalence.

Across repeats the report records min/mean/median/stdev/p90/max summaries for Stage-60
wall time, first-result latency, batch count, startup/readiness, cleanup tail,
setup/bookkeeping, non-probe lifecycle cost, RSS and the calculated amortizable upper
bound.

The primary decision metric is deliberately conservative:

`amortizable_upper_bound = sum(non_probe_upper_bound_ms for every reached batch after the first)`.

This is an **upper bound**, not a predicted speedup. A future reusable bucket cannot be
assumed to eliminate all non-probe work, and reuse across different adaptive batches
would intersect candidate/profile grouping, dispatcher membership and resource unions.

## Safety / isolation

The top-level wrapper owns `/var/run/zapret2-lifecycle.lock`, captures semantic service
evidence, stops the normal Zapret2 service only inside that lock, cleans the reserved
Model-C/Model-B rules `19128–19130` and divert ports `9990–9992`, performs the measurement,
restores the original RUNNING/STOPPED state, captures final evidence and finalizes the
report.

The experiment MUST NOT:

- change production `stage60-parallel` routing or Model-C source;
- change dispatcher width three;
- change adaptive candidate order/search semantics;
- change discovery GET-4K;
- create eager dormant branch buckets;
- mutate the reference job;
- leave reserved IPFW/dvtws2 state or alter the normal Zapret2 semantic state.

## Decision boundary

`_7` itself never recommends a production change automatically. Owner-live evidence is
accepted only when all repeats remain Model-C-only, result/batch attribution is equivalent,
RSS evidence is complete, cleanup passes and normal service evidence is restored exactly.

If the measured amortizable upper bound is not material relative to Stage-60 wall-time
jitter, close cross-batch lifecycle reuse with no production change. If it is material and
reproducible, the only next step is a **separate** design/measurement change for cross-batch
keep-warm or broader dispatcher/bucket grouping; `_7` does not implement that architecture.
