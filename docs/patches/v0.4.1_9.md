# v0.4.1_9 — Preserve Model-C lifecycle fallback evidence

Status: **SOURCE CORRECTIVE / OWNER-LIVE PENDING**

## Trigger

Owner-live testing of published `v0.4.1_8` installed successfully and retried the retained
Rutracker reference `job.lWLjqL` with five requested lifecycle repeats. The measurement
stopped with:

`ERROR: instrumented and persisted Model-C batch counts differ`

No requested top-level report was left behind, so the follow-up `jq` command had no file to
inspect.

## Root cause

`_instrument_batches()` records a lifecycle sample only after production Model C
`_bucket_batch` returns successfully. Production Stage 60 is intentionally fail-closed:
when Model C raises `ModelCInfrastructureError`, `stage60_model_c.expand()` transparently
replays the admitted batch through Model B, and Model B can in turn fall back to cold Model A.

That fallback batch is valid persisted Stage-60 evidence but has no successful Model-C
instrumentation sample. `_8` compared the two counts before reading the persisted fallback
metadata, so the secondary count mismatch masked the primary Model-C failure reason. The
measurement worker then performed normal cleanup and removed its private session tree,
leaving no diagnostic report.

The `_8` observation proves that the previous `0700` traversal defect was passed and that an
isolated replay entered the production fallback path. It does **not** by itself establish a
production Model-C regression because the exact fallback reason was discarded by the
measurement harness.

## Corrective

`_9` changes only the experiment harness:

- extract persisted `model_c.fallback_reason`, `warm_error`, execution model, candidate IDs
  and batch number before any count/sequence acceptance check;
- represent instrumented/persisted batch-count mismatch as explicit report evidence instead
  of raising the generic masking exception;
- stop additional repeats after the first incomplete/non-Model-C replay;
- always write the requested report when Stage 60 itself produced a persisted result;
- exclude incomplete/fallback repeats from lifecycle-cost summaries;
- require `instrumented_batch_count_match=true` for final acceptance;
- preserve normal cleanup and semantic Zapret2 restoration before the final report conclusion.

A rejected diagnostic run therefore leaves a usable report with the exact primary fallback
reason. A fully Model-C-only run still executes all requested repeats and retains the
original lifecycle/amortization measurement semantics.

## Production boundary

Production Model C, Model B, cold Model A, adaptive candidate order, source-port leasing,
candidate width three, CandidateSpec semantics and discovery GET-4K are unchanged.

No production optimization decision is permitted from an incomplete/fallback replay.
Owner-live must first either produce `measurement_accepted` or expose the exact Model-C
fallback reason for a separate evidence-based diagnosis.
