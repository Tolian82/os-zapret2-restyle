# v0.4.1_5 — Discovery probe agreement measurement

Status: **SOURCE / CI / FREEBSD15 PACKAGE / PUBLICATION COMPLETE / OWNER-LIVE DATA COLLECTED / MEASUREMENT NOT ACCEPTED**

## Why

The accepted `_2` Lua and `_3/_4` BLOB investigations closed two local Model-C optimization ideas without a production change. The next open adaptive-search question is whether Stage-60 discovery can use a cheaper request while preserving agreement with finalist deep GET. A cheaper probe is useful only if it does not create false confidence and its wall-clock reduction is material.

## Scope

`_5` is measurement-only. Production Stage 60 remains
`C-warm-bucket-source-port-dispatch -> B-warm-worker-parallel-batched -> A-cold-fallback` and the current production discovery request remains the bounded 4 KiB GET.

The packaged experiment compares four cold candidate replays over the same reference job, pinned endpoint epoch and native TLS 1.3 candidate specifications:

1. `head` — HTTP `HEAD`, no response body target;
2. `get-1` — `GET` with `Range: 0-0`;
3. `get-4k` — the current discovery `GET` with `Range: 0-4095`;
4. `deep-16k` — the existing finalist deep policy (`GET` up to 64 KiB, acceptance requires at least 16 KiB when the resource is long enough).

Default corpus size is ten eligible native graph candidates. Reconnaissance candidates are followed by eligible golden candidates and then remaining expansion nodes. Variant order rotates over four cyclic orders to reduce order/cache bias.

## Evidence contract

For every candidate/variant the report records probe and total duration, classification, HTTP status/body-byte evidence, pinned-endpoint match, firewall interception attribution and search-epoch identity. Cheap variants are compared with the deep reference for agreement, false PASS, false FAIL and inconclusive pairs.

A live measurement is accepted only when:

- every planned sample exists;
- all samples belong to one pinned search epoch;
- every PASS has endpoint and interception attribution;
- temporary candidate runtime/firewall state is cleaned;
- semantic Zapret2 lifecycle evidence after the experiment is identical to the initial evidence.

The wrapper owns `/var/run/zapret2-lifecycle.lock`, temporarily stops normal Zapret2 when it was initially RUNNING, runs only sequential cold candidate replays, cleans candidate residue and restores the exact initial service state. It does not install a second routing architecture.

## Decision boundary

`production_model_changed=false`, `production_discovery_policy_changed=false`, and
`production_change_recommended=false` are hard gates in this patch. No production discovery change may be proposed until owner-live data shows **zero false PASS** against deep GET and a material, reproducible cost improvement.

## Owner-live multidomain measurement

Owner-live data was collected on three domain shapes using the published `_5` package:

- `telegram.org`, reference `job.xhdgCU`: production Model C exhausted 16 candidates with zero winners; discovery corpus was 10/10 FAIL for every variant;
- `rutracker.org`, reference `job.lWLjqL`: production Model C exhausted 16 candidates, retaining `seqovl-host` and `seqovl-midsld`; discovery deep reference produced 9 FAIL + 1 short-resource `inconclusive`, while each cheap variant produced 9 FAIL + 1 PASS;
- `www.youtube.com`, reference `job.NAYQxm`: production Model C stopped normally after seven candidates with three winners (`seqovl-midsld`, `multidisorder-midsld`, `golden-owner-multisplit-fake-tls-7`); discovery produced 9 FAIL + 1 PASS for all four variants.

All three production jobs reported `C-warm-bucket-source-port-dispatch` with `.parallel.fallbacks=[]`. The YouTube job therefore supplies a working three-winner `enough_candidates` early-stop case in addition to the existing Telegram graph-exhaustion case.

Across the three supplied ten-candidate discovery corpora, each cheap variant recorded 29/29 agreement on comparable pairs, zero false PASS, zero false FAIL, plus one Rutracker pair where deep validation was intentionally `inconclusive` because the valid response contained only 162 bytes.

The supplied aggregate timings do **not** show the required material benefit for HEAD or one-byte GET. Current `get-4k` was the lowest-cost cheap variant on the Rutracker and YouTube corpora and was within 9.5 ms of the best cheap mean total on Telegram. Equal-sample pooled mean total time across the 30 samples was approximately `3452.97 ms` for HEAD, `3442.37 ms` for `get-1`, and `3439.70 ms` for current `get-4k`.

The successful YouTube `get-1` and `get-4k` samples recorded approximately 873-875 KiB rather than the requested one-byte/4-KiB range, so the tested server/resource did not demonstrate a useful body-size reduction for those Range requests. Whether the server ignored Range is an inference from the recorded byte counts and was not independently verified.

Every live discovery report concluded `measurement_rejected` solely because `checks.cleanup_ok=false`; all other reported checks were true. The Telegram follow-up direct cleanup returned status 0 and showed no reserved IPFW, dvtws2 or divert-socket residue, so a harness/finalization defect is plausible but not yet localized.

Detailed multidomain evidence:
`docs/verification/evidence/2026-08-13-v0.4.1_5-multidomain-live-evidence.md`.

No production discovery change is recommended from the current data. Follow-up must localize `cleanup_ok=false`, extract fresh Rutracker/YouTube Stage-60 timing and successful/inconclusive per-sample rows, then decide whether one corrected repeat is needed or the cheaper-probe hypothesis can be closed negatively.
