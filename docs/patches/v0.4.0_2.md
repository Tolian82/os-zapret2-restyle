# v0.4.0_2 — Stage-60 family reachability

Status: **QUALIFIED / OWNER-TESTED FOCUSED LIVE PASS**

## Purpose

Implement adaptive-search `_28` without pulling later redesign work into the same patch:
Stage-50 family screening remains evidence, but `accepted` must no longer be an allowlist
that decides which Stage-60 catalog families can run.

## Previous behavior

`strategy_lab_py/search.py` filtered the Stage-60 expansion catalog to rows whose family
appeared in Stage 50 `accepted`. When Stage 50 accepted no family, Stage 60 persisted
`no_accepted_family`, tested zero candidates and returned successfully without allowing a
stronger catalog candidate from a rejected family to run.

That behavior is the exact hard gate superseded by
`docs/decisions/DEC-2026-08-08-strategy-lab-adaptive-search.md`.

## `_28` behavior

- keep the Stage-50 `accepted` field and its existing structural validation as evidence;
- keep catalog order stable inside each priority group;
- try rows from accepted families first, so positive Stage-50 evidence remains a simple
  priority signal;
- then keep every remaining catalog row reachable, including families whose Stage-50
  representative failed;
- when `accepted=[]`, retain the full catalog in its existing order rather than returning
  `no_accepted_family`;
- retain the existing Stage-60 candidate timeout, stage budget, target count, cold
  candidate lifecycle and early-stop behavior.

No adaptive graph, `CandidateSpec`, `ResourceInventory`, new resource/range semantics,
endpoint pinning, timeout redesign or finalist-validation change belongs to `_28`.

## Regression

`scripts/strategy-lab-python-search-extended-core.sh` covers both sides of the boundary:

- mixed PASS/FAIL Stage-50 evidence proves accepted-family rows are prioritized but
  rejected-family rows remain executable;
- `accepted=[]` proves Stage 60 still reports the full catalog as available, executes
  candidates in catalog order and can find a working candidate;
- existing early-stop and Stage-70 stability continuity remain exercised.

The lifecycle integration fixture now routes the newly reachable Stage-60 candidate
attempts through its existing mock candidate runner, so the lifecycle contract exercises
the `_28` path without accidentally invoking the real candidate runtime.

The old shell `strategy_lab_expansion_run` fixture remains compatibility-only; Python is
the authoritative automated Stage-60 policy owner.
