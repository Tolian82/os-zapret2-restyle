# v0.4.0_5 — Adaptive search planner and fixed endpoint epoch

Status: **SOURCE-QUALIFIED / NOT PUBLISHED OR OWNER-TESTED**

## Purpose

Implement adaptive-search `_31` without changing the cold candidate runtime or any
timeout value. Candidate PASS/FAIL evidence must select the next reachable graph node,
every comparison in one job must use the same Stage-40 endpoint binding, the normal
winner target must be two to three rather than five, and measured phase durations must
be durable input for the later `_32` timeout review.

## Live-evidence planner

`strategy_lab_py/search_graph.py` keeps the complete `_30` native DAG reachable and adds
a deterministic `next_expansion` decision for its current frontier:

- a successful representative prioritizes the simplest nearby compatible node;
- a failed representative prioritizes a stronger reachable neighbor;
- each decision records its evidence source/outcome, reason and complete priority tuple;
- every attempted node is appended to the job's Stage-60 `schedule` evidence;
- graph exhaustion remains truthful when the winner target is not reached.

Stage 50 remains evidence, not an allowlist. No PASS or FAIL removes an otherwise
resource-eligible branch.

## Fixed search epoch

Stage 40 resolves each domain endpoint once, binds its own TLS baseline request to the
selected A record and writes `search-epoch.json`. The document has a validated identity,
generation, target/type and ordered address set for every required endpoint.

Candidate, reconnaissance, expansion, stability, extended-protocol and final profile
replay paths load that document and reject a changed endpoint list or epoch identity.
Candidate execution no longer performs DNS. Its host/SNI contract remains the original
endpoint while curl/IPFW/protocol probes use the recorded selected IPv4 address. A
deliberate Stage-40 rerun creates a new recorded generation rather than silently changing
addresses between candidates.

## Winner and publication bounds

- Stage 60 now targets three working candidates by default and records the normal
  `minimum=2,target=3` band;
- Stage 70 stops after three stable candidates while retaining its bounded fallback scan
  when earlier candidates prove unstable;
- Stage 85 replays and publishes at most three TLS 1.3 finalists by default;
- one or two verified candidates remain truthful output when the graph/budget yields no
  additional winner;
- the separate circular three-to-five eligibility decision is unchanged.

## Timing evidence

Each job writes locked, atomically replaced `timing-telemetry.json` evidence. It covers
Stage-40 DNS/TLS timing, resource inventory, stage adapters, Stage-50/60 runner time,
candidate preparation/rendering/firewall/launch/readiness/probe/cleanup phases, Stage-70
attempts and job time through mandatory restoration. Candidate evidence explicitly states
that resource initialization is included in launch/readiness rather than fabricating a
separate value.

`_31` changes no operation, candidate, stage or job deadline. Telemetry is measurement
input for `_32`, not permission to tune constants in this patch.
