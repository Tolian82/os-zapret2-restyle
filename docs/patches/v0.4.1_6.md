# v0.4.1_6 — Discovery measurement cleanup finalizer correction

Status: **ACCEPTED / OWNER-LIVE PASS / PRODUCTION BEHAVIOR UNCHANGED**

## Why

The published `_5` discovery-probe experiment collected useful owner-live data on `telegram.org`, `rutracker.org`, and `www.youtube.com`, but every report was formally rejected only because `checks.cleanup_ok=false`.

Source inspection proved that the failure was deterministic and local to the measurement finalizer interface: the shell worker reports cleanup success/failure as numeric `1`/`0`, while the Python CLI previously decoded only literal `true` as true. Thus a successful cleanup value `1` was persisted as false.

Root-cause evidence:
`docs/verification/evidence/2026-08-13-v0.4.1_5-cleanup-finalizer-root-cause.md`.

## Scope

`_6` changes only the experiment finalizer input boundary:

- canonical boolean decoding accepts `1` and `true` as true;
- accepts `0` and `false` as false;
- rejects unknown boolean spellings instead of silently treating them as cleanup failure;
- regression coverage proves successful numeric cleanup can produce `measurement_accepted` when all other gates pass;
- regression coverage proves numeric cleanup failure remains `measurement_rejected`.

The shell lifecycle worker, candidate runtime, Model-C dispatcher, Stage-60 search graph, source-port selection and production request policy are unchanged.

## Production boundary

Production remains:

`C-warm-bucket-source-port-dispatch -> B-warm-worker-parallel-batched -> A-cold-fallback`.

Production discovery remains the bounded 4 KiB GET. `_6` does not promote HEAD or one-byte GET.

The `_5` multidomain data found no material cost advantage for HEAD or GET-1 over current GET-4K. Across equal 30-sample pooled corpora, mean total time was approximately `3452.97 ms` for HEAD, `3442.37 ms` for GET-1 and `3439.70 ms` for current GET-4K. No production discovery change is recommended.
