## Одна физическая сборка, четыре независимых проверяемых среды

Используем уже принятый `.github/workflows/stage5-native-cross-clean-running.yml`, **не запускаем вторую параллельную матрицу**. После `scripts/stage5-g10-preinstall-purge.py` в Guest A нативный `scripts/stage5-native-single-artifact.py` собирает **ровно один** пакет через штатный Mk, устанавливает его и повторно устанавливает тот же архив в STOPPED. Оригинальный архив и квитанции с SHA-256 передаются без новой сборки:

- **Guest A:** до сборки установленного плагина нет; создаём только disposable fixture — остаточный `OPNsense.Zapret` через запертый native PHP Config API и собственный временный файл. Проверяем безопасный dry-run, настоящий standalone `--purge` с изолированным CI-opt-in, отсутствие остатка, сохранность остальных узлов Config и повторный dry-run; только после этого собираем и устанавливаем пакет. Guest A формирует временную `/root/g10-preinstall-purge.json` **вне очищаемого штатным сборщиком каталога `dist/`**, затем **вкладывает её проверенный результат** в штатную копируемую `dist/stage5-native-single-artifact.json` через команду `bind`. После VM copyback команда `verify` повторно проверяет этот вложенный результат, SHA источников и успешную чистую установку. Отдельный G10 sidecar из гостевой VM не требуется при передаче между runners. Это тест очищенной системы **после реальной очистки осиротевшего Config**, но не повторяет отдельный G01 running-purge после установленного пакета.
- **Guest B:** тот же побайтово переданный пакет заменяет прежний опубликованный `v0.6.2_1` при настоящем RUNNING/Voice, затем проходят original-FD9, HTTPS, Exclude и Extra Resources/лабораторные тесты.
- **Guest C:** тот же архив с историческим RUNNING/Voice проходит настоящий новый запуск ядра и проверку восстановления.
- **Guest D:** тот же архив проходит независимую штатную установку через SHA-проверяющий companion installer на OPNsense без заранее установленного `git`; зависимости только из официального репозитория.

Стандартные SHA-256/manifest/source проверки Stage 5 остаются обязательны. Новая квитанция после `bind` проверяется после копирования из A как часть уже существующего исходного Stage 5 receipt, без требования передавать дополнительный файл. Любое несовпадение SHA/источника, неполная очистка или изменение чужих XML-полей отвергают проверку. Ни одно из этих испытаний не имеет права работать на продуктивной машине.

## Что этот инкремент **не** доказывает

Результат native CI не равен owner-live физическому GUI. Не считаются пройденными A01–A22 целиком только из-за PASS cross-archive: G03/G04/G05/G06/G07/G08/G09 точечно проверялись ранее, но часть их сценариев ещё не выполнена на **одном** G10 пакете. В частности, отрицательный TEST-NET-1 в G09 не доказывает обход DPI или работу заблокированного YouTube; реальная IPv6-сеть, внешние WAN/VPN, Voice media, browser-click и ручной GUI uninstall на устройстве владельца остаются отдельно не подтверждёнными. Перед публикацией нужно сопоставить новые точные G10 receipts с A01–A22 и устранить любую недостающую обязательную нативную проверку.

## Следующий переход

Только после успешных точных PR checks и **фактической** G10 native S3-проверки подтвердить объединённый `main`, действительный SHA физического пакета и исполняемый штатный installer. Затем через существующий testing publisher создать постоянные GitHub prerelease assets и отдельный bounded publication-record PR. Это **не** стабильный релиз и **не** разрешение устанавливать что-либо на рабочую OPNsense автоматически. G11 — последующая фактическая owner-live приёмка опубликованных байтов.

## Точечный блокер G10 — HTTP 403 и изменение inventory

Главный исходный `main=0c3fda2b` Guest B закончил FAILED: в попытке 1 источник непостоянства HEAD/каталогов/файлов не установлен; в попытке 2 API GitHub вернул документированный `HTTP 403: rate limit exceeded`. Для `_29` на production пути **только подтверждённый** GitHub API rate-limit разрешает чтение *того же публичного `refs/heads/main`* через read-only `git ls-remote` фиксированного `https://github.com/Tolian82/zapret2-extra-resources.git`. Никакого локально закреплённого/альтернативного каталога и повторной POST Install: полученный SHA проверяется, затем архив строго проверяется по SHA/Git blob до единственного native Install. Любой другой 403, TLS/сеть, неоднозначный Git ref или ошибка Git остаются отказом.

`extra_resources_reconcile.make_remove_plan()` теперь при *той же* fail-closed проверке сообщает класс конкретного расхождения (`HEAD`, `directory/root|lua|files|files/fake`, `runtime-files`, `upstream-files`). Изменённый witness не считается допустимым; это диагностика и возможность локализовать гонку при следующем единственном обоснованном native прогоне, но не устранённая/принятая гонка. S0/S1 тесты должны доказать не только успешный fallback, но и отказ при произвольных 403, таймауте Git, ошибке ref и изменении каталогов/ресурсов.
