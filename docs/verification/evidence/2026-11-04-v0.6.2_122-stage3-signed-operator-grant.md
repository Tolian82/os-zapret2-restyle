**Source-only candidate**: `VERSION=0.6.2`, `PLUGIN_REVISION=122`, parent `main cfd7b0b6263d0a9344ebed2c773db34ee392ddad`. **No new package published/installed, no change to native hooks or owner appliance.** [Authoritative TЗ v1.4](../../architecture/OPNSENSE_NATIVE_COMPATIBILITY_AND_PACKAGING_SPEC.md) and [plan v1.4](../../history/stages/native-packaging-2026-11/OPNSENSE_NATIVE_COMPATIBILITY_AND_PACKAGING_PLAN.md) remain binding.

## Why this increment is needed

The `_121` test client has an authenticated TLS certificate and the witness has a durable SQLite journal, but possession of that certificate alone granted the client unrestricted `RESERVE`, `CONSUME`, `ABORT` and `STATUS` requests for any syntactically valid operation/payload/checkpoint identities. Authentication is **not** authorization.

`_122` makes the same CI witness refuse **before any SQLite transaction** unless a separate signed *operator approval scope* names the exact requested operation, payload SHA-256, checkpoint SHA-256, positive checkpoint sequence and action. The CI test has three separate key roles: client/server mTLS identities, witness response RSA signer and **operator grant RSA signer**. Distinct operator authority/status signer PEM SHA-256 identities are checked; the witness derives its status-signer public PEM from its actual private key instead of accepting an assertion.

## Enforced mechanics

- New `scripts/stage3-prepkg-operator-operation-grant-ci.py`: strict raw-byte SHA256/RSA detached-signature verification via OS OpenSSL, duplicate-key/NaN JSON refusal, exact schema/repository/CI issuer, positive grant sequence, `not_before`/`not_after` window capped at one hour, bounded list of **1–8 exact entries** and strictly ordered action-rights set. Signed metadata records source commit (40-hex Git SHA), old and incoming package SHA-256 (64-hex), operator PEM fingerprint, actual status signing key fingerprint and approved client's certificate DER fingerprint. The package hashes and source SHA are **CI claims only, not verified against real installed archives**.
- The server's `serve` command **requires** grant bytes, detached signature, operator PEM and a separately supplied expected operator authority fingerprint. All three local inputs must be absolute, single-link, regular, owner-controlled `0600` files with no symlink; the authority public PEM SHA must match the expected value. There is **no unapproved fallback** to old `serve` arguments. Failure prevents the listener from opening.
- Validated grant is held by the process and checked again for expiration **on each request** after successful mTLS/leaf pin and request schema parsing but **before** SQLite `BEGIN IMMEDIATE`. A disallowed operation, wrong payload, wrong checkpoint, unauthorized action, expired policy, or absent grant refuses without inserting a nonce or operation. A client that steals valid mTLS credentials but lacks approved operation scope is not automatically authorized for other operations.
- Existing durable SQLite transitions, signed status/challenge, idempotent lost response recovery and deliberate **root database rollback counterexample** must remain intact. The signed grant does not authorize `pkg`.

## Residual blocking risks

This is **still a CI-only same-runner simulation**, not an independently managed off-box witness. The disposable runner creates the operator signing key, controls the expected fingerprint, source/package identity claims, TLS identities, SQLite journal and wall clock. Root of the runner can restore an old signed grant and DB, generate a new operator key and pin, or change process startup inputs; one-use across independent trust domains and nonrollbackable remote latest are **not** established. Even a correctly signed grant cannot verify that the actual old package and incoming package match its claimed SHA without trusted native artifact validation. No owner key enrollment/revocation, independent authority distribution, production service/API, original-FD9/pkg gateway or live no-mutation _74 acceptance exists. A TLS credential alone now lacks wildcard authorization **within this CI model**, but operational trust remains unapproved.
