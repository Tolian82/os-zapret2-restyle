Primary comparison, `external-common-3` versus `external-single`:

- median stable readiness: `+0.234 ms` / `+0.375%`;
- common-set mean is actually `1.445 ms` lower than single-external mean;
- common-set p90 is `6.502 ms` lower than single-external p90;
- within-variant readiness stdev is `2.276 ms` for common-3 and `5.502 ms` for single.

The `+0.234 ms` median delta is much smaller than normal run-to-run spread in either external variant. The mean and p90 direction is also not consistent with a startup penalty. Therefore the run does not show a material readiness cost from scaling the eager external declaration set from one file to the current production-width upper bound of three files.

Supporting median comparisons:

- `inline-small` vs BLOB-free: `-0.080 ms` / `-0.128%`;
- `external-single` vs BLOB-free: `-0.146 ms` / `-0.234%`;
- `external-common-3` vs BLOB-free: `+0.088 ms` / `+0.141%`.

All supporting differences are also below measured jitter.

## Decision

Accept `_4` owner-live measurement for the defined bounded production-width common-set scope.

The measured `external-common-3` versus `external-single` differences are below normal readiness/RSS jitter. Combined with the accepted `_3` one-BLOB result, there is no evidence that current Model-C eager BLOB declaration/loading has a material startup/readiness or RSS cost at candidate width three.

Therefore:

- do **not** change production Model C BLOB loading;
- do **not** add lazy BLOB loading for the current architecture;
- close the BLOB-loading startup/RSS optimization as a negative result for current width three;
- do not create another package revision solely for this optimization.

This is not a claim that arbitrary future BLOB counts or much larger resource sets are free. If production candidate width/resource scale changes materially, that future architecture requires a new measurement rather than extrapolating this bounded result.
