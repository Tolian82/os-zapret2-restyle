## Two independent official source representations and reproducible fingerprint relation

1. The [OPNsense 26.7 Xenial Xenops official release announcement](https://docs.opnsense.org/releases/CE_26.7.html) prints the complete **26.7-series RSA public key** in PEM form. The [official 26.7 changelog source](https://github.com/opnsense/changelog/blob/master/community/26.7/26.7) independently reproduces the PEM. The PEM is embedded in `scripts/stage0-verify-opnsense-official-key.py` with its exact line wraps and ending LF.
2. The [pinned official OPNsense core source](https://github.com/opnsense/core/blob/ac08367416c1d66dea87df0ef0de24c315b5d5bc/src/etc/pkg/fingerprints/OPNsense/trusted/pkg.opnsense.org.20260608), Git object/blob `08d6a4009b3d43509c746a3f8e5e4a10915f450c`, has `function: "sha256"` and `fingerprint: "9f3b76ffef38fb6405595038b324b61043c9a2c375ae5c151d628508e9a845ce"`. Its [official repository template at the same commit](https://github.com/opnsense/core/blob/ac08367416c1d66dea87df0ef0de24c315b5d5bc/src/etc/pkg/repos/OPNsense.conf.shadow.in) requires fingerprint verification at `/usr/local/etc/pkg/fingerprints/OPNsense`.
3. **Direct cryptographic check performed independently of the user appliance:** SHA-256 of **the literal complete PEM text** (BEGIN/END lines, base64 line breaks and final LF, **not** DER bytes) computed from the published official 26.7 release key equals **`9f3b76ffef38fb6405595038b324b61043c9a2c375ae5c151d628508e9a845ce`**. That is an exact cryptographic equivalence between two public OPNsense references, not a guess from the user's configured key. DER encoding intentionally hashes differently and is **not** the FreeBSD pkg fingerprints-file reference.

The first [owner-executed isolated catalog and installed ELF qualification](2026-11-01-v0.6.2_24-stage0-owner-target-trust-and-elf-acceptance.md) already established that the **on-device configured** OPNsense fingerprints successfully authenticate a fresh isolated catalog and that **one trusted file** exists. It did **not** expose its fingerprint or compare it to this externally established official key. Do not redo the package catalog, Python/ABI, ELF or 275-line owner report.

## One target-side comparison — safe refusal, no changes

The self-contained `scripts/stage0-verify-opnsense-official-key.py` performs **no network calls, pkg commands, file writes, service/Config/IPFW/kernel changes or package installation**. It independently recomputes SHA-256 of the embedded official release PEM and requires it equal the separately pinned official core fingerprint; then reads only `/usr/local/etc/pkg/fingerprints/OPNsense`:

- Requires root-owned (in actual target mode), non-group/other-writable, non-symlinked trust/revocation directories and fingerprint files.
- Requires **exactly one** trusted file with the pinned official name `pkg.opnsense.org.20260608`. Any missing or additional trusted file, alternate filename, wrong signature format/algorithm, duplicate field, unexpected SHA-256, symlink or unsafe permissions produces `NOT_VERIFIED`. This deliberately strict qualification **does not declare an otherwise valid different key layout intrinsically insecure**.
- Reads all OPNsense revoked fingerprints; rejects if the official release key is revoked or if a revoked fingerprint entry is unparseable, symlinked or unsafe.
- Emits only one bounded `STAGE0_OFFICIAL_KEY={...}` JSON line, with the public reference fingerprint, status and a refusal code if needed. It does not reveal key-store paths beyond standard public configuration or any private content.

**The source-only CI suite has ten isolated positive and negative tests** for official PEM/source mismatch, exact trusted match, tampered/missing/extra keys, unsafe directories/files, symlinks, revoked official key and malformed entries. CI PASS would establish only script correctness, **not** that the owner-installed key is authentic. `stage0_closed=false` and `pkg_hooks_fd9_verified=false` remain explicit.
