## Missing scenario and existing evidence not to repeat

The [first owner target witness](2026-11-01-v0.6.2_20-stage0-owner-opnsense-target-witness.md) already confirmed OPNsense 26.7.8_1 / FreeBSD:15:amd64, installed 0.6.2_1, generic Python owner, the private ELF digest and existence of six base libraries. [Official repository template checks](2026-11-01-v0.6.2_21-stage0-official-repository-trust-source.md) prove a pinned *source* trust configuration, **not** the actual configured catalog or keys. The [real FreeBSD15.1 binary qualification](2026-11-01-v0.6.2_22-stage0-published-private-elf-native-runtime.md) executed the *published package ELF* in a disposable FreeBSD VM, **not** on installed OPNsense. None of those completed probes is requested again.

The new scripts/stage0-target-trust-runtime.py requires the previously observed product/package ABI and installed 0.6.2_1 identity as safety guards; reads the effective **pkg -vv** configuration for the exact OPNsense repository (not a guessed filename), confirms enabled fingerprint signatures and the correct trusted directory, and refuses ambiguous, malformed, symlinked, empty or world-writable trusted fingerprints. It then runs **pkg update -f -r OPNsense** with a temporary, automatically removed PKG_DBDIR and PKG_CACHEDIR. Finally it queries the freshly downloaded catalog for actual provider names, versions, origins and repo identity. This isolated database approach is based on the [official OPNsense firmware connectivity checker at pinned source commit](https://github.com/opnsense/core/blob/ac08367416c1d66dea87df0ef0de24c315b5d5bc/src/opnsense/scripts/firmware/connection.sh).

The script also hashes the *installed* private ELF against SHA-256 e4af7ba05b6ad8dd997aefeae3a9c15a08be2700534d043cd93c7987f97c451f, checks actual **ldd** resolution for six required sonames, executes **-V** for HTTPS/HTTP3 advertisement and tests its installed Chrome profile with **--ech false** exclusively against **https://127.0.0.1:1/**. The connection is deliberately refused; no external TLS/QUIC handshake or browser ClientHello is claimed.

## Security and evidence classification

- This is a **network-capable, ephemeral-catalog-only** check on the owner's test appliance. It creates and cleans private temporary catalog files under /tmp and downloads repository metadata; it performs **no persistent pkg database update, pkg install/upgrade/remove, package hook execution, service restart, Config/IPFW modification, WAN request, or changes to repository files**.
- Raw pkg -vv output (possibly containing mirror URLs), raw repository update output, fingerprint/key contents, private configuration and raw ELF diagnostic output are **not printed**. One summary JSON line contains only public names/versions/origins, base-library paths, proof flags and a bounded failure code.
- Success means the catalog was accepted using the **configured on-device fingerprint trust**, **not** that the configured fingerprint was independently compared with the official OPNsense 26.7 release signing public key. The report explicitly keeps official_trust_anchor_independently_compared=false and stage0_closed=false.
- Failed or unreachable signature catalog, unsupported ABI, changed predecessor, foreign provider, bad ELF, unresolved native library or wrong Chrome CLI is **NOT_VERIFIED** rather than silently accepted. Success does not prove actual TLS ClientHello, network HTTP3/QUIC, installed pkg hook ordering, FD9 safety, Python-loss native Stop/Status, configd PID identity or rollback.
- The owner's /usr/local/etc/pkg/repos/FreeBSD.conf remains **foreign/unproven** with absent backup. It must **never be edited, restored or normalized**; the script selects only the OPNsense signed repository.
- Eight local/offline tests include disabled/wrong/duplicate repository, wrong ABI/path, unsigned catalog refusal, isolated temporary database cleanup, missing libraries and tampered ELF. GitHub CI tests this suite; fixture success is **not an owner appliance test**.
