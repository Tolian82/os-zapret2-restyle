## 30 сентября: TCP, proxy и ошибочный маршрут

1. Простой `nc` к `185.203.117.88:33128` доказал только TCP-connect. Явный HTTP-proxy запрос затем получил CONNECT 200, корректный сертификат `*.telegram.org` и HTTP/2 200 (09:52:47).
2. Старый sing-box SOCKS `127.0.0.1:1080` также вернул HTTPS 200 (10:03:38), но его прежний TCP outbound указывал прямо на parent. Это ещё не было прохождением через Squid.
3. Router-origin `curl https://telegram.org` без proxy завершился timeout. LAN-входные `rdr` не применяются к собственному исходящему сокету роутера. Это выявило пробел локальной политики, а не недоступность parent.
4. Первая проверка прозрачного LAN-пути остановлена route guard: `149.154.167.99` шёл через старый `192.168.1.140`. `curl` не запускался. Пустой WAN capture этого окна не является результатом TLS-теста.
5. После отдельного `/32` через `192.168.1.2` TNAS/container выполнил **без явного proxy** `curl -q -4 --interface 192.168.1.100 --proxy "" --noproxy "*" --resolve telegram.org:443:149.154.167.99 https://telegram.org/`. Получены подлинный сертификат, HTTP/2 200 и `curl_exit=0` в 16:44:22 UTC / 19:44:22 МСК.

Согласованная запись Squid последнего теста:

```text
1790786662.437 565 192.168.1.100 TCP_TUNNEL/200 27410 CONNECT telegram.org:443 - FIRSTUP_PARENT/185.203.117.88 -
```

Одновременно WAN-журнал показал TCP к parent:33128. Таким образом прозрачный LAN HTTPS → Squid → parent **подтверждён**. Маршрут к этому HTTPS-адресу оставлен для дальнейших опытов; это отдельный маршрут от reflector `/32`.

Нельзя объявлять все ранние UDP-опыты недействительными из-за router-origin HTTPS timeout: данный reflector CLI передаёт signaling локально между экземплярами и не подключается к Telegram API через TCP. Для настоящего Telegram-приложения TCP-связность остаётся самостоятельным обязательным условием.

## Что больше не требуется заново устанавливать

- Родительский proxy доступен; TCP CONNECT и полноценный HTTPS через него уже подтверждены.
- Прозрачный LAN HTTPS → Squid → parent подтверждён после исправления **TCP-целевого** маршрута TNAS.
- SOCKS IPv4 TCP/80,443 → Squid3130 → parent подтверждён успешным v2-run; ранний failed-run не является текущим результатом.
- Добавление helper охватывает Telegram IPv4 UDP на всех портах, но его zero-fake применяется только к STUN.
- Попадание UDP в rule19000 не равно `MEDIA_PASS`; текущий reflector генерирует не-STUN Hello.
- Необходимость постоянной конфигурации теперь зафиксирована владельцем. Ещё открыты автоматическая локальная TCP-политика, сохранение ON/маршрутов после reboot, синхронизация alias-снимков, проверка SOCKS UDP и воспроизводимый звонок. Это задачи, не уже выполненные изменения.
