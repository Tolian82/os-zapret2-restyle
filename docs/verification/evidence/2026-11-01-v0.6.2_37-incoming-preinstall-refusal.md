# Stage 0.09 — Incoming PRE_INSTALL nonzero refusal under native OPNsense pkg

**Source only:** v0.6.2_37, pinned parent main c603b5df874675417a8b3cf02e40954b75051d26. **Specification and plan remain editorial v1.3; Stage 0 OPEN / Stage 1 BLOCKED.** Stable published and owner-installed 0.6.2_1 is immutable and untouched.

## Reason and testable question

[Real OPNsense historical installed-package test at _36](2026-11-01-v0.6.2_36-original-unknown-owner-native-refusal.md) proved the original PRE_DEINSTALL exits nonzero for synthetic incomplete owner state, but real native pkg delete returned 0 and removed the package/service anyway. A separate [_27 actual FreeBSD pkg phase scheduler](2026-11-01-v0.6.2_27-stage0-real-freebsd-pkg-phase-scheduler.md) showed forced pkg add -f executes incoming pre-install and does **not** run outgoing pre-deinstall. Therefore the next narrower question is whether native **incoming** pre-install nonzero exit is a true barrier to replacement.

## Bounded execution

- Run only within the pinned disposable GitHub Actions OPNsense 26.7 KVM guest, after the existing read-only product/ABI identity check.
- Create two **distinctly named synthetic** versions of harmless zapret2-stage0-preinstall-refusal-fixture package. It is **not** named os-zapret2-restyle; the real released package is neither downloaded nor installed in this experiment.
- All payloads, trace, pkgdb and cache are inside one new 0700 temporary directory. PKG_DBDIR isolates native package queries; no stock repository, real plugin, IPFW, service, Config, FD9 or owner's appliance is changed.
- Install the synthetic predecessor and require exact old package-db version and file bytes. Force-add the synthetic successor with an incoming pre-install script which writes an observable trace and exits **73**. Capture actual pkg add -f return code, post-command native package-db identity, payload bytes and hook trace **without assuming a refusal succeeded**.
- Report exactly one of **ABORT_PRESERVED_OLD_FIXTURE**, **REPLACED_DESPITE_INCOMING_PRE_INSTALL_REFUSAL**, or **PARTIAL_OR_INCONSISTENT_MUTATION_AFTER_REFUSAL**. The second and third outcomes are explicit safety hazards; a failure to execute refusing hook or unverified baseline prevents an outcome claim.

## Verified native outcome — incoming hook refusal is NOT a pkg barrier

**Exact source-run result:** [disposable OPNsense 26.7 CI #41318536518](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41318536518), tested head `ac0286465a2f53a1a748fa802859de2c7628820e`. Eleven offline positive/negative cases PASS, including actual `/bin/sh` execution of the synthetic hook with exit code 73 and exact text trace. The read-only OPNsense 26.7 identity witness also PASS.

The actual native package manager returned:
- `pkg add -f exit=0` despite exact stderr `pkg: PRE-INSTALL script failed`;
- `hook_trace=["old:pre-install","old:post-install","new:pre-install:refuse","new:post-install"]`, including **the incoming hook that exits 73** and **subsequent POST_INSTALL execution**;
- `installed_after=zapret2-stage0-preinstall-refusal-fixture|0.6.2_37` and `payload_after="new\\n"`;
- `outcome=REPLACED_DESPITE_INCOMING_PRE_INSTALL_REFUSAL`;
- `product_safety_acceptance_passed=false`, `independent_pretransaction_gate_qualified=false`, `stage0_closed=false`.

The earlier native attempt [#41318365486](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41318365486) already showed a replaced fixture and exit 0, but its test-only `printf` trace was malformed. The exact same-scope fix uses `/bin/echo`, verifies the hook through real `/bin/sh` before CI, and now obtains an **unambiguous native chronological trace**. Thus the successful experiment is an **OBSERVED UNSAFE PACKAGE-LIFECYCLE MECHANISM**, not a safety PASS.

## Acceptance boundary and next task

Combining this exact incoming-hook native evidence with [_36's original historical package PRE_DEINSTALL/pkg delete witness](2026-11-01-v0.6.2_36-original-unknown-owner-native-refusal.md), **neither incoming PRE_INSTALL nor outgoing PRE_DEINSTALL exit status is a sufficient replacement/deletion safety barrier for the tested pkg operations**. The approved TЗ/plan v1.3 must retain LH-01, LH-02, LH-06 and LH-07 safeguards, and a **separately enforced ownership and state check before initiating any destructive pkg transaction** must be qualified. Do not advertise standard direct `pkg add -f`/delete as safe for an unknown/foreign/live old runtime.

This **does not test** the historical installed old package inside the fixture, a real native successor, legitimate RUNNING owner, foreign IPFW, actual affected process or configd, Python-loss Stop/Status, independent image SHA, or production owner appliance. The synthetic pkgdb, payload and hook trace are private to a disposable virtual guest; no `0.6.2_37.pkg` is built or published. Stage 0 **OPEN**, Stage 1 **BLOCKED**, TЗ/plan editorial v1.3 unchanged; published stable `0.6.2_1.pkg` immutable and owner's foreign `FreeBSD.conf` preserved.
