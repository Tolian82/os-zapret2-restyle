# Stage 0 — Isolated genuine OPNsense 26.7 guest bootstrap

**Proposed source revision:** `v0.6.2_32` (from `main=d45c2df735e7ad9cb0befa585de0bb378d1e949b`), `VERSION=0.6.2`, source-only; technical specification and plan independently remain editorial **v1.3**. The verified published stable `v0.6.2` / `os-zapret2-restyle-0.6.2_1.pkg` are unchanged.

## New practical target instead of another FreeBSD mock

Public [`vmactions/opnsense-vm`](https://github.com/vmactions/opnsense-vm) supports a real virtual **OPNsense 26.7 amd64** guest in ordinary Linux-hosted GitHub Actions, rather than a plain FreeBSD VM. The project says its [OPNsense builder](https://github.com/anyvm-org/opnsense-builder) starts from an official OPNsense nano disk image and enables SSH through the serial console; the resulting qcow2 is **third-party prepared**, not bit-identical to an official published OPNsense image. This workflow pins the VM action to exact Git commit `abaa977e3dbc77a0d1eeed4d82c8d9914b018235`. Upstream OPNsense's own 26.7 release lists an official nano-amd64 image, but this increment does not independently verify the third-party guest-image digest or builders' provenance.

[`stage0-opnsense-guest.yml`](../../../.github/workflows/stage0-opnsense-guest.yml) is a path-gated PR/explicit-dispatch workflow. It boots one **disposable OPNsense 26.7 VM**, without passing project secrets, with `contents: read`, temporary guest disk, no post-run file copyback, and runs [`stage0-opnsense-guest-readonly.py`](../../../scripts/stage0-opnsense-guest-readonly.py). That verifier **reads only** actual root identity, `uname` OS/amd64, `opnsense-version -a` exactly `26.7`, `pkg config ABI` exactly `FreeBSD:15:amd64`, FreeBSD 15 userland, non-null `kern.vm_guest` and **absence of installed `os-zapret2-restyle`**. It emits a bounded machine-readable `STAGE0_OPNSENSE_GUEST` witness, or refuses.

This **bootstrap** does NOT install `0.6.2_1.pkg`, run any historical `+MANIFEST` hooks, alter configd, IPFW, FreeBSD.conf or service state, exercise FD9, or build a native successor. The action's initial SSH/config.xml preparation is inside the throwaway third-party-built guest only, not an owner appliance. On passing, the isolated 26.7 guest's platform identity is qualified, but the **actual installed predecessor and native lifecycle remain OPEN**. Do not infer that the VM image has been cryptographically authenticated merely from runtime version checks.
