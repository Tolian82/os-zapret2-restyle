# v0.4.1_5 — discovery cleanup finalizer root cause

Status: **ROOT CAUSE CONFIRMED / SOURCE CORRECTIVE REQUIRED**
Date: 2026-08-13
Package under live test: `os-zapret2-restyle-0.4.1_5`

## Trigger

All three owner-live discovery-probe reports (`telegram.org`, `rutracker.org`, `www.youtube.com`) completed their planned samples, retained one search epoch, preserved PASS attribution, and restored the normal Zapret2 lifecycle, but each ended with:

`checks.cleanup_ok=false`

and therefore:

`conclusion=measurement_rejected`.

A direct post-run Telegram cleanup subsequently returned shell status `0`, with no reserved IPFW rules, no `dvtws2` on discovery divert port `9989`, no divert socket on `9989`, and normal Zapret2 RUNNING. That made a persistent-runtime leak unlikely and justified inspecting the finalization interface itself.

## Confirmed source mismatch

The shell worker uses numeric shell state:

```sh
cleanup_ok=0
...
if "${CANDIDATE_ADAPTER}" cleanup "${REFERENCE_JOB}" >/dev/null 2>&1; then cleanup_ok=1; else cleanup_ok=0; fi
...
"${PYTHON_LAUNCHER}" discovery-probe-measure finalize "${OUTPUT}" "${INITIAL_EVIDENCE}" "${FINAL_EVIDENCE}" "${cleanup_ok}"
```

Therefore the finalizer receives literal `1` after successful cleanup and literal `0` after failed cleanup.

The Python CLI decodes the same argument as:

```python
return finalize(Path(args[1]), Path(args[2]), Path(args[3]), args[4].lower() == "true")
```

Consequently:

- shell success: `"1".lower() == "true"` -> `False`;
- shell failure: `"0".lower() == "true"` -> `False`.

The Python finalizer then writes that boolean directly into `checks.cleanup_ok`, and acceptance requires it to be true.

This makes `cleanup_ok=false` deterministic for every `_5` live finalization through the packaged worker, regardless of whether the adapter cleanup actually succeeded.

## Exit-trap detail

The worker also runs cleanup again in its `EXIT/HUP/INT/TERM` trap. However the first explicit finalization sets `finalized=1`; the later trap calls `finalize_report`, which immediately returns without rewriting the already finalized report.

Therefore a later successful trap cleanup cannot repair the persisted `cleanup_ok=false` created by the numeric/string interface mismatch.

## Impact

This defect explains the otherwise contradictory owner-live evidence:

- all three reports reject only on `cleanup_ok=false`;
- the Telegram direct cleanup/residue follow-up is clean;
- the network agreement/timing samples and lifecycle-restoration evidence remain useful collected data;
- no `_5` live report can satisfy `measurement_accepted` until the finalizer interface is corrected.

The defect is confined to the measurement harness finalization contract. It does not change production Stage-60 execution, Model C, candidate semantics, or the production 4-KiB discovery probe.

## Corrective boundary

The next packaged corrective must keep `_5` measurement semantics unchanged and repair only this boolean handoff, with a regression test proving both cleanup-success and cleanup-failure finalization paths.

After installing the corrected package, repeat the discovery measurement against retained compatible reference jobs if still available. A corrected run is required to establish formal lifecycle/cleanup acceptance; the already collected multidomain agreement/timing data must remain preserved as historical evidence rather than discarded.

No production discovery change is authorized by this root-cause finding.
