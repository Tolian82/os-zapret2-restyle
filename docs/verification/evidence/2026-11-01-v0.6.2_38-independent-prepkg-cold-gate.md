# Stage 0.09 — Independent pre-pkg cold owner refusal (read-only, NOT transaction authorization)

**Source only:** `v0.6.2_38`, parent `main=4bddc22d8cdeeec65de9acc0235fed36084d3466`. Native compatibility technical specification and five-stage implementation plan remain editorial **v1.3**. Stage 0 **OPEN**, Stage 1 **BLOCKED**. No `0.6.2_38.pkg` exists; immutable published and owner-installed stable `0.6.2_1.pkg` unchanged.

## Why this gate is needed

[Historical package PRE_DEINSTALL refusal](2026-11-01-v0.6.2_36-original-unknown-owner-native-refusal.md) did not stop an actual `pkg delete` and [new incoming PRE_INSTALL refusal](2026-11-01-v0.6.2_37-incoming-preinstall-refusal.md) did not stop `pkg add -f` in native OPNsense. The two tests prove hook errors are **not reliable package-manager transaction barriers** for those cases. Independently verify a supported old owner before a destructive package operation; never infer safety from `pkg` return code or hook refusal.

## Exact bounded experiment

1. Fresh isolated KVM OPNsense 26.7 / FreeBSD:15:amd64 guest; use existing read-only identity and published-archive SHA256/provenance verification, then install **only** the exact immutable published `os-zapret2-restyle-0.6.2_1.pkg` with its original hooks (previously qualified on disposable OPNsense). The third-party guest disk is not independently image-SHA attested.
2. `scripts/stage0-opnsense-prepkg-readonly.py` checks original installed archive vs native pkgdb, four unchanged hook bodies, installed service bytes/mode and package owner using the previously qualified `stage0-installed-predecessor-readonly.py`. The original installed service's **own** `status` command acquires its historical FreeBSD FD9 using a private temporary guest lock path. Do not nest another external FD9 holder or misrepresent this as an atomic lock spanning `pkg`.
3. A positive **cold observation only** requires exact `status` rc=1 and `zapret is not running`, no shared Apply journal, restart marker, engine/supervisor PID files, pending Extra Resources transaction or detectable named Zapret process. The *narrow cold-only* kernel gate requires absent ipfw/ipdivert kernel modules plus native `ipfw -q list` ENOPROTOOPT/71, not any potentially ambiguous loaded/foreign table layout. Missing evidence refuses. A positive snapshot sets `safe_pkg_transaction_authorized=false` and is **not** a live RUNNING/foreign owner acceptance.
4. In that **same disposable guest**, inject only a known synthetic malformed `/var/db/zapret2/shared-apply/operation.json` using the exact already qualified `_36` fixture helper. Require genuine original installed service Status=2; then call the pre-pkg gate through a **fake operation callback**. It must **refuse before callback invocation**; no real `pkg add/delete/upgrade` is called. Verify original native pkgdb identity, service SHA/mode and hooks unchanged. Remove only the exact test-owned journal (never recursively clean unrelated paths) and confirm original cold STOPPED is restored.
5. Offline contract tests cover correct cold observation, wrong package/old hook provenance, STOPPED/RUNNING/INCOMPLETE/unknown status, journal/symlink/marker/PID/Extra Resources, process census, IPFW modules/ENOPROTOOPT, denial before callback, non-OPNsense refusal and absence of package-mutation calls in source.

## Evidence and limits

**Fast local preflight:** `python -m py_compile` on the two exact prepared scripts and `python test-stage0-opnsense-prepkg-readonly.py -v` — **12 offline tests PASS**. Real disposable OPNsense 26.7 CI result **PENDING exact-head verification** at PR opening. The design deliberately does NOT make production packaging changes, execute a real package transaction after a positive snapshot, assume a lock held between check and action, call Stop/Start/Apply, mutate IPFW, touch the owner appliance, repair foreign `FreeBSD.conf`, or qualify a final native successor. Simulated refusal without real pkg invocation is a bounded **pre-pkg negative gate**, not a complete safety guarantee.

**What remains blocking:** An actually enforced, atomic pre-transaction owner/FD9 guard integrated into each supported package-management entrypoint and preserved through the destructive transaction and its rollback, including legitimate RUNNING owners, foreign IPFW, unknown journals, unrelated direct `pkg` invocations, and the actual final native package SHA. Until those are proven, **no real upgrade/deletion is authorized**, LH-01/LH-02/LH-03/LH-06/LH-07 are not fully accepted, Stage 0 OPEN / Stage 1 BLOCKED. Follow the approved TЗ/plan v1.3; no architecture extension or versioned Python unification in this scope.
