Date: 2026-08-07
Appliance: OPNsense 26.7.1_1, FreeBSD 15.1-RELEASE-p1 stable/26.7
Package: `os-zapret2-restyle-0.3.3_13.pkg`
Target: `rutracker.org`
Job: `job.3mc9c6`

## Live result

Stages 00, 10, 20, and 30 passed. Stage 40 failed with `FAIL — DNS-разрешение обязательного endpoint не выполнено.` Stages 50–85 were skipped. Stage 90 passed and restored the initially RUNNING Zapret2 service completely; stage 99 returned the truthful `PARTIAL` outcome.

This live run therefore verifies the `_13` stage-90 correction: after an error-path run, the normal Zapret2 runtime remained healthy and its generated arguments were restored.

## Stage-40 artifacts

`endpoint-1.a.log` was zero bytes. `baseline.json` recorded:

```json
{"target":"rutracker.org","target_type":"A","dns_a":"FAIL","dns_aaaa":"SKIPPED","endpoints":[{"endpoint":"rutracker.org","status":"FAIL","exit_code":1,"transport":"dns-a","detail":""}],"all_accessible":false}
```

The incorrect `target_type:"A"` is a separate shell-variable namespace defect and is intentionally excluded from corrective `_14`.

## Exact DNS reproduction

Direct resolver query without the Strategy Lab timeout wrapper:

- command: `/usr/bin/drill rutracker.org A`
- result: `rc=0`
- resolver response: `NOERROR`
- addresses: `104.21.32.39`, `172.67.182.196`
- query time: 96 ms

The exact Strategy Lab wrapper behavior:

- command: `/usr/bin/timeout 2 /usr/bin/drill rutracker.org A`
- result: `rc=124`
- elapsed time: 2 seconds
- output size: 0 bytes

Control query through the same non-foreground timeout wrapper:

- command: `/usr/bin/timeout 2 /usr/bin/drill yandex.ru A`
- result: `rc=0`
- query time: 8 ms

FreeBSD foreground timeout control for the blocked target:

- command: `/usr/bin/timeout -f 2 /usr/bin/drill rutracker.org A`
- result: `rc=0`
- output size: 416 bytes
- resolver response: `NOERROR`
- addresses: `104.21.32.39`, `172.67.182.196`
- query time: 30 ms

## Root cause

The resolver and `drill` are healthy. On this FreeBSD appliance, the Strategy Lab DNS probe is incorrectly wrapped by `timeout` without foreground mode. The wrapper returns 124 after two seconds with no output even though the same DNS lookup completes in tens of milliseconds directly. Adding `-f` to the exact same timeout invocation makes the request succeed immediately.

Corrective `_14` is therefore limited to FreeBSD DNS requests: `strategy_lab_dns_request()` uses `timeout -f` on FreeBSD and preserves existing timeout behavior on non-FreeBSD systems.
