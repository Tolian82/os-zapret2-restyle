## Exact reproduced incident

[Trusted-main scheduled watchdog run #41856709938](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41856709938) was **FAIL** while looking at [PR #892](https://github.com/Tolian82/os-zapret2-restyle/pull/892): \`Api.pages('actions/runs/<id>/jobs')\` rejected \`{"total_count":N,"jobs":[...]}\` with \`PAGINATED_GITHUB_RESULT_UNEXPECTED\`. The previous generic pager recognized only bare lists and \`workflow_runs\` envelopes. Thus a *genuine failed-job* classification crashed before posting a dependable notification, and after 30 minutes the code path that measures \`newest_job_progress\` would fail the same way. This is a failure of GH-065 alert **delivery**, not a Zapret2 product failure. [Issue #894](https://github.com/Tolian82/os-zapret2-restyle/issues/894) tracks the bug.

During #892 qualification, 5 jobs with successful \`Complete job\` steps continued to report job status \`in_progress\`, leaving the native and general workflows nonterminal. GitHub subsequently issued all 20 exact-head workflow SUCCESS conclusions without code edits, allowing a guarded squash merge. Separately, GitHub's official status page reported an **Actions/Pages/Webhooks degradation beginning 2026-11-04 16:05 UTC**; correlation is not proof that this specific Actions incident caused the jobs' late status transitions. Never count completed steps alone as a successful workflow.

## _125 bounded fix, test scope and implementation rules

- \`scripts/github_pr_watchdog.py\`: strictly dispatch \`Api.pages\` response shape by *supported endpoint*, without deriving API commands from untrusted PR content: \`actions/runs?\` requires a dict containing \`workflow_runs\` list; \`actions/runs/<positive numeric id>/jobs\` requires a dict containing \`jobs\` list; \`pulls?\`, \`pulls/<id>/files\`, \`issues/<id>/comments\` require direct arrays. Unexpected dict keys, a non-list, an element not an object or unknown endpoint fail closed with explicit error. Original cap **10 pages of 100** stays. The verified production controller uses read-only job summaries to build deduplicated alert comments; it must not auto-merge.
- A \`Complete job\` step reported SUCCESS but parent \`job.status=in_progress\`/**workflow.status=in_progress** is **not** acceptance. \`newest_job_progress\` can now read real GitHub \`jobs\` envelopes and a stale latest step timestamp leads to \`CHECK_STALLED\` advisory only; \`READY_FOR_OWNER_REVIEW\` continues requiring **all exact-head required workflows** terminal SUCCESS.
- \`scripts/test_github_pr_watchdog.py\` expands **20 → 27 test methods**, including a real-shaped jobs envelope, runs and bare-list compatibility, two-page/ten-page bounds, malformed/foreign envelope, unsupported endpoint no-network, successful steps but stuck job still stalled, and end-to-end simulated failed-job details plus deduplicated PR comment creation.
- \`.github/workflows/pr-completion-watchdog.yml\` retains trusted-\`main\` checkout, fixed comment-only token permissions, CI completion trigger, scheduled fallback, and no PR-code checkout or merge endpoint. Its \`push.paths\` now also includes the watcher Python source and tests, so a **merge changing only scripts** triggers trusted-main validation instead of relying exclusively on delayed schedule.
- Before branch publication, an isolated local synthetic implementation of the exact bounded \`pages\` behavior passed **7/7**, with local \`python -m py_compile\` PASS. The complete repository tests **could not be executed locally** because connected GitHub repository files are not mounted into the local execution container and direct public GitHub downloads fail DNS; the precise project Python test suite and the trusted-main runtime must be qualified by GitHub Actions. **New _125 exact-head CI / real GitHub alert delivery PENDING until actually observed.**
