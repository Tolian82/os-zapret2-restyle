# PR completion watchdog — observed 403 after READY and bounded delivery fallback

**Source-only candidate:** `v0.6.2_90`, parent `main=fc6031388d5ff1e8de7c0f1146f1aef356caba64`. This is **GitHub notification infrastructure only**: no product runtime, package hooks, published `.pkg`, OPNsense firmware, owner appliance or native LH-08/AC-11 acceptance changes.

## Incident and exact native GitHub evidence (3 November 2026)

PR [#857](https://github.com/Tolian82/os-zapret2-restyle/pull/857) remained OPEN even though **all 19 required latest-head PR workflows succeeded**, source head `6c5c496e102de9224c542f6034f4f276af690032`. User screenshot displayed `30/30` green individual checks. [Watchdog run #630](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41643467036), job `125942582443`, **did not exit early**: its 12 local offline contracts succeeded, it logged `PR #857: READY_FOR_OWNER_REVIEW`, read existing PR comments and rechecked current PR head. Only **POST `/repos/Tolian82/os-zapret2-restyle/issues/857/comments`** failed HTTP **403**, causing workflow failure. Workflow's actual runner `GITHUB_TOKEN Permissions` were `Actions: read`, `Contents: read`, **`Issues: write`**, `PullRequests: read`. The script caught this exception but erased the response body and accepted permission headers, leaving `RuntimeError: GITHUB_API_REFUSAL_403`. **403 cause is not yet proven**: a pull-request-specific integration permission denial, rate/secondary limit or policy denial all require actual 403 response details. Do not attribute the 403 only to missing `issues:write`.

Earlier [watchdog runs #629–#626](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41642832760) had completed successfully before the final READY notification, and numerous overlapping workflow completion events spawned cancelled queued watchdog checks. The triggering architecture was too noisy: one event for each of 16 workflows, each triggering full PR-state polling. This is not self-recursion, but wastes GitHub Actions capacity and can contribute to API throttling.

Verified remediation: PR #857 was subsequently exact-head squash-merged to `main` at [fc603138](https://github.com/Tolian82/os-zapret2-restyle/commit/fc6031388d5ff1e8de7c0f1146f1aef356caba64), with all 19 PR workflow statuses SUCCESS, main [CI #41645834247](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41645834247) and release classification [#41645834238](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41645834238) SUCCESS, **zero open PRs** and task branch deleted. This completion was performed by the developer with the normal checks, **not** by watchdog.

## Least additional permissions and observable fallback

1. Trusted-main watchdog workflow adds **`pull-requests: write`** alongside existing `issues: write`, `actions: read`, `contents: read`. The [GitHub documentation](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment) states either Issues or Pull requests write should authorize comment creation, but [an independently reported GitHub API behavior](https://github.com/github/rest-api-description/issues/6994) reproduced a PR-timeline 403 with `Issues: write` plus `Pull requests: read` which resolved with PR write added. This is a **plausible mitigation**, not yet proof the exact #630 403 was that issue. Workflow continues to check out **trusted default main only**, no PR-head source, package, merge, label, approval or code-modifying endpoints. The broader token is limited to this privileged notification-only job.
2. The `workflow_run` trigger now watches only **`CI` completion**. The permanent fallback schedule runs every **10 minutes** (`7,17,27,37,47,57`), plus manual dispatch and bounded main push activation. All **applicable per-PR current-head** workflows are still dynamically evaluated, never just CI. This reduces a burst of 16 completion-triggered watcher invocations. GitHub scheduled delivery is best-effort and can be delayed; **there is no guarantee of exactly ten minutes** or a continuously running ChatGPT agent.
3. `classify_http_error` reads only a bounded 4 KiB API error response and derives **fixed labels** (`INTEGRATION_ACCESS_DENIED`, `SECONDARY_RATE_LIMIT`, `PRIMARY_RATE_LIMIT`, `AUTHORIZATION_OR_POLICY`). It reports only allowlisted `X-Accepted-GitHub-Permissions`, numeric `Retry-After` and syntax-checked GitHub request ID; never includes raw server response, token or PR body. A POST 403 remains a **failed job**, with GitHub error annotation and safe GitHub **job summary** containing the PR number, exact head and readiness plus delivery failure. This is an **inspectable fallback, not guaranteed external notification**.
4. On this workflow's **initial merged-main push only**, an explicit, idempotent delivery smoke posts one fixed, marked informational comment to **already merged PR #857** through the **same PR timeline `/issues/857/comments` endpoint** that failed. The smoke is gated by trusted `GITHUB_EVENT_NAME=push`, `GITHUB_REF=refs/heads/main`, `state=closed` and `merged=true`, and deduplicates by a unique marker. A failure leaves a red annotated Action and safe summary; no fictitious success. Repeated future pushes do not post additional comments. **A successful closed-PR smoke verifies this exact write endpoint with the new token on that occasion, but does not verify that a future open PR alert will actually be delivered, nor any real-time monitoring guarantee.**

## Tests and acceptance

Runnable offline tests cover HTTP 403 permission classification and redaction, primary/secondary limit distinction, injection-resistant summaries, POST 403 red/fallback behavior, fixed PR-only write smoke twice/idempotency, on-main-push only, and retained scope-specific CI/current-head classification. The existing tests also reject untrusted PR execution, unknown policy, old SHA or cancelled/skipped runs and repeated comments.
