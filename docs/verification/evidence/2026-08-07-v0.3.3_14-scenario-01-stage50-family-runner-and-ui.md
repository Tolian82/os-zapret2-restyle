## Stage-50 root cause

The worker log contains the exact failure:

```text
/usr/local/opnsense/scripts/OPNsense/Zapret/strategy_lab_family_runner.sh: STRATEGY_LAB_TIMEOUT_BIN: parameter not set
```

`strategy_lab_family_runner.sh` enables `set -eu` and sources only `common.sh`,
`result.sh`, and `family.sh`. `family.sh` uses `${STRATEGY_LAB_TIMEOUT_BIN}` to wrap the
single-candidate runner but, in `_14`, no sourced module defines that variable.

The persisted result exactly matches an abort before the first candidate execution:

```json
{"total":7,"completed":0,"families":[],"accepted":[],"rejected":[],"all_pass":false}
```

This is the exact `completed:0` live state that proves no family candidate completed.

Corrective scope for `_15`: the family module must own a safe default for
`STRATEGY_LAB_TIMEOUT_BIN`, with a regression that invokes the production family runner
under `set -u` while the variable is absent from the caller environment.

## Additional confirmed defects preserved for later correction

These defects are not part of the `_15` stage-50 patch but are now live/source-confirmed
and must remain in the project backlog until corrected and requalified.

### 1. Baseline `target_type` corruption

The final job-level target type remains `domain`, but `baseline.json` records
`target_type:"A"`. DNS helper functions reuse the shell-global `_strategy_lab_type`
variable and overwrite the outer baseline value. This is a report/state correctness bug.

### 2. GUI shows an immediate stale `ERROR` for a newly started job

Immediately after pressing Run, the UI showed the new job id `job.mCqg7Y` together with
`Статус: ОШИБКА`, before the new worker had failed. The Diagnostics JavaScript preserves
previously rendered terminal state while replacing the displayed job id, so a new job can
briefly inherit the previous job's visible status until polling renders fresh state.

### 3. GUI progress remains at 0% while backend state advances

During the same run the UI remained at `Прогресс: 0% — —` until the terminal response,
then jumped to 100%. A one-second watcher of the authoritative `status.json` proved that
the backend actually advanced normally:

- 17:37:33 — stage 00 / 0%;
- 17:37:34 — stage 20 / 18%;
- 17:37:37 — stage 30 / 27%;
- 17:37:39 — stage 40 / 36%;
- 17:37:41 — stage 90 / 91%;
- 17:37:48 — stage 99 / 100%.

Therefore the worker/state engine is not stuck at 0%; the remaining defect is in the GUI
status/polling presentation path.

### 4. DNS answer parser is semantically too permissive

`strategy_lab_dns_answer_present()` currently searches for an `IN A`/`IN AAAA` token
anywhere in raw `drill` output. The same token appears in `QUESTION SECTION`, so that
check does not prove that an answer exists. A later corrective patch must distinguish
successful response status and actual answer records rather than accepting a question
line as evidence of resolution.

### 5. DNS failure diagnostics collapse distinct command failures

The current endpoint DNS helper converts any failed DNS request to a generic return 1,
and the baseline result writes `exit_code:1`. This loses the distinction between timeout,
`drill` execution failure, and successful command output rejected by parsing. A later
corrective patch must preserve the real command result or another structured failure
classification.
