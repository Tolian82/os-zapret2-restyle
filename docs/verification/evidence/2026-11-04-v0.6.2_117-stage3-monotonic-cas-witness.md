## What _116 could not guarantee

A standalone RSA signed latest checkpoint can detect a valid local ledger tail deletion only if the expected latest SHA is rooted in an independently authenticated state outside compromised appliance root. If root can select an older signed snapshot and its old SHA, full rollback succeeds. The missing property is an independent monotonic *latest state*, not another self-signed checksum.

## _117 implemented CI experiment

New scripts/stage3-prepkg-monotonic-witness.py is a CI-only SAME-VM witness store protocol, separate from original _115 approval-ledger and _116 signed-checkpoint verifier. Commands are exactly bootstrap, publish and compare. All commands require actual FreeBSD amd64 root plus the four disposable CI environment opt-ins. All storage is canonical root-private 0700 directories and 0600 nofollow single-linked files on a disposable OPNsense VM. There is NO network client/server, no pkg dispatcher, no production service or hook changes, no binding to the _114 trusted seed.

- bootstrap: Verify existing true detached RSA checkpoint signature and local original _115 ledger; initialize separate witness-store with an UNTRUSTED genesis record. This does not authenticate the signer or a truly independent latest SHA.
- publish: Under independent nonblocking flock of witness.lock, compare-and-swap exact expected previous checkpoint sequence and SHA; refuse stale/racing requests and changed signer. Verify true _116 RSA signed next snapshot against the existing local journal. Require precisely previous sequence + 1. Append next immutable state-<12-digit-generation>.json using O_EXCL, full write and fsync(file), fsync(directory); each record commits SHA256 of its previous record. Strict full-chain scan, single owner, no duplicate JSON keys, contiguous generation and operation sequence, bounded 512 records. A zero-byte partial record after O_EXCL blocks all further operations, never autorepaired.
- compare: NEVER takes caller-selected expected latest SHA. While holding witness flock, read latest checkpoint SHA and pinned public-key SHA from the witness store itself; verify exact supplied signed checkpoint with _116 and original local journal under its own flock. Reject missing/corrupt witness, stale signed checkpoint, local-ahead sequence, local tail deletion, invalid signer or incorrect local head.

This is a protocol simulator, NOT a production external authority: two stores reside on ONE VM and a root attacker can delete/restore both. Also there is no atomic transaction spanning witness publication and local ledger write. Successful compare flags explicitly witness_latest_independently_anchored=false, witness_root_rollback_resistant=false, witness_remote_service_deployed=false, cross_store_atomic_transaction_implemented=false, production_pkg_authorized=false, pkg_invoked=false.

## Negative evidence required

1. Two actual concurrent publish subprocesses with same expected previous tuple: exactly one succeeds, one refuses CAS stale or lock busy.
2. Local ledger sequence N+1 while witness remains N: compare must refuse. After RSA-signed publish from N to N+1, compare succeeds with latest stored SHA.
3. Deleting complete last local spent entry leaves locally valid shortened chain, but unchanged witness latest causes compare to refuse. Restore native ledger to original bytes.
4. Deliberate FULL ROOT ROLLBACK: delete the last witness-state record and last ledger spent record, restore older valid signed snapshot: compare can PASS. This is proof of absent external tamper resistance, not a security success.
