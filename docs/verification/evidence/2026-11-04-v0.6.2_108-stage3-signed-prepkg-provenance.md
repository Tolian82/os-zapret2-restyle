## Scenario and trust decision

The _107 trusted `python3 -I -B -c` program verified an externally supplied standalone Python file by SHA-256 before executing it, but its expected hash was just a caller string. An adversary able to substitute *both* the script and caller-supplied hash could authorize hostile code. _108 replaces this unsigned argument mode with **one signed, read-only provenance mode**, rather than treating a checksum adjacent to the downloaded script or incoming package as trustworthy.

The trusted operator-reviewed `-c` bytes are still a **separate, mandatory trust anchor**: their own distribution/authentication is **not implemented**. The *public key SHA-256* must be pinned via a separately authenticated operator channel before use; it MUST NOT be obtained from the same incoming package, signed claims, downloaded standalone script, or untrusted response. Root ownership and `0600` alone do not confer publisher identity.

Invocation interface (conceptual, for authorized operator-provisioned code only):

```text
python3 -I -B -c '<independently authenticated verifier text>' \
  --signed-provenance <out-of-band SHA256 of public PEM bytes> \
  /root/private/trusted-public.pem /root/private/claims.json \
  /root/private/claims.sig /root/private/native-prepkg-standalone.py \
  inspect-predecessor /root/private/os-zapret2-restyle-0.6.2_108.pkg \
  0.6.2_108 /root/private/os-zapret2-restyle-0.6.2_1.pkg 0.6.2_1
```

The exact **signed JSON bytes** use schema `zapret2-prepkg-provenance-v1`, repository `Tolian82/os-zapret2-restyle`, a 40-hex `source_commit`, `entrypoint_sha256`, `incoming_version`, `incoming_sha256`, `predecessor_version`, and `predecessor_sha256`. Extra, missing, duplicate, malformed, or unsupported fields fail closed. Signed versions are matched to exact package basenames; the signed digest of the entrypoint is verified against the one opened private root-owned inode. Key file, signature, claims, and source must be root-owned single-link `0600` regular files below secure `/root` ancestry with stable inode/size/timestamps. The code compares public PEM bytes against the **independent** pinned key SHA, verifies `openssl dgst -sha256 -verify` using separately captured manifest/signature/key bytes in a fresh `/root` directory, then checks the signed JSON. Only after that does it compile/execute frozen, verified standalone CLI bytes. The standalone CLI verifies both exact archive SHA-256 values and invokes existing read-only original-FD9 predecessor inspection. No command can dispatch `pkg add`, reinstall, upgrade or remove.
