## Exact _121 implementation scope

The previous `_120` localhost TCP service accepted unauthenticated JSON. The new **CI-only** `scripts/stage3-prepkg-remote-witness-ci.py` refuses any non-mTLS request:

- Uses Python standard-library `ssl` with minimum TLS 1.2, required certificate-chain verification and TLS client-certificate verification (`CERT_REQUIRED`). There is **no plaintext fallback**. Listener remains fixed to `127.0.0.1` on a disposable runner and still requires `ZAPRET2_CI_REMOTE_WITNESS_ONLY=1`.
- Beyond a CA chain, the server checks **SHA-256 of exact client certificate DER bytes** against the expected client leaf pin before any JSON processing/SQLite transaction. The client checks the server's chain, `127.0.0.1` IP SubjectAltName, and **SHA-256 of exact server DER leaf** before sending any operation.
- Private keys differ by role: server TLS key, authorized client TLS key and original `_120` RSA status-signature key. All test keys and a test CA are **created solely within the disposable test environment**. No test private key is committed to the repository or a release.
- TLS protects the transport; existing `_119` detached RSA-SHA256 response verification still binds the exact nonce, operation, payload, checkpoint and witness sequence. Existing SQLite `BEGIN IMMEDIATE`, one-use challenge, read-back after reply loss, termination and root rollback counterexample must remain unchanged.

The same test module now has **27 executable cases** (previous 18 plus nine mTLS negative cases): foreign CA, wrong server CA, missing client certificate, plaintext TCP, wrong server SAN, serverAuth certificate offered as clientAuth, a different valid **same-CA client** rejected by the server leaf pin, a different valid **same-CA server with identical SAN** rejected by the client's leaf pin, and missing server leaf pin. Rejected requests must not append operations or challenges.

## What this does NOT prove

This is still an **isolated CI fixture on one runner**, with loopback networking and the test runner controlling the CA, expected fingerprints, RSA signing identity, wall clock and SQLite file. It proves TLS **mechanics and transport refusal**, not that an OPNsense appliance cannot access the off-host database/keys. Same-privilege rollback of the SQLite store remains possible; client identity is unapproved by any owner; there is no deployment, independent authorized operator, out-of-band key authentication, certificate issuance/revocation/rotation, protected off-host monotonic store, availability/SLA, anti-rollback after privileged compromise, authenticated high-watermark policy, real original FD9 package gateway, or cross-store crash-consistent `pkg` operation.
