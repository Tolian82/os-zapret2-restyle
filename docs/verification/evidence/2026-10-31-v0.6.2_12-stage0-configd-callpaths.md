**Status:** static source evidence and CI audit; not installed target-runtime evidence. Specification and plan editorial revisions v1.2 unchanged.

## Direct GUI → PHP → configd → shell/Python trace

- `src/opnsense/service/conf/actions.d/actions_zapret.conf` contains **33** registered configd actions, including native service start/stop/status/Apply, Voice, Strategy Lab and circular launcher, runtime setup, extra resources and live inspectors. Every action is source-mapped to its direct absolute installed `/usr/local/` entrypoint, with its exact registry line, command, invocation type and corresponding tracked Git source/mode.
- Three explicit direct configd Python 3.13 invocation sites are present at source: `voice_inspect`, `extra_resources_preflight`, `extra_resources_inventory`. Other Python paths inside shell/PHP or downstream executables are still captured by the [complete source path/line inventory](2026-10-31-v0.6.2_8-stage0-source-audit.md). Direct shell commands are *not* automatically proof of Python-independent Stop or Status.
- The new `scripts/stage0-configd-callpath-audit.py` checks every configd direct command and tracked source path, records source Git mode and flags directly invoked scripts without `100755`. It scans tracked OPNsense Zapret API PHP controllers for literal `configdRun('zapret ACTION')` and preserves unresolved/dynamic references explicitly rather than falsely attributing them.
- In particular `src/opnsense/scripts/OPNsense/Zapret/zapret_service.sh` currently has **Git mode `100644`** despite direct configd calls; both previously published real packages delivered it as **tar mode `0755`**, via the old builder's staging `chmod`. Stage 2 native packaging MUST preserve mode `0755` for this directly invoked script. The audit emits mode-review warnings without changing production or claiming a current failure.
- Positive/negative real temporary Git index fixture regressions verify mode transitions, explicit Python classification, missing direct source detection, missing action rejection, literal unknown PHP action failure, dynamic PHP caller uncertainty and exact-head refusal. Latest-head CI emits JSON plus human-readable Markdown to the existing source-audit artifact, with an exact commit SHA.

## Lifecycle and acceptance boundaries

- Four published hooks are byte-hashed in [archive baseline](2026-10-31-v0.6.2_9-stage0-published-package-audit.md): pre-install checks previous service and cold state; post-install reloads configd actions and conditionally resumes; pre-deinstall refuses incomplete owner and stops; post-deinstall does no watcher restart. These describe existing source contracts, **not tested actual OPNsense lifecycle**.
- `zapret_service.sh` uses the native owner FD9/lock path and shell backend; currently hardcoded Python 3.13 inside shared transactions. The new scanner only proves direct configd dispatch and Git executable ownership, **not** Python-loss Stop, FD9 lock safety or zero foreign-IPFW side effects.
- Scenario matrix to qualify later: clean install, RUNNING or STOPPED replacement, caller execution bit failure, unsupported product/pkg ABI, missing generic Python/unsupported Python branch, Python-loss Stop/Status, private ELF missing soname, legacy owned backup vs foreign-edited FreeBSD.conf, foreign IPFW process refusal. Acceptance requires qualified OPNsense, not stock FreeBSD VM alone.
- **STOP:** Target package providers, fully qualified ABI, installed old bytes, real private ELF resolution and former FreeBSD.conf ownership remain unresolved. No Stage 1, service mutation, `pkg install`, package build publication or appliance operation in this revision.
