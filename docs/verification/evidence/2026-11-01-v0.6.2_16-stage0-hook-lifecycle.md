# Stage 0.13 — exact-HEAD four manual package hooks / FD9 / process-ownership map

**Date:** 2026-11-01. **Source:** `v0.6.2_16` on current Git head; editorial native OPNsense TЗ/plan v1.2. **Scope:** strictly Git blob/static analysis and isolated temporary Git fixtures, not installed OPNsense or a package replacement.

## Exact source findings and evidence

- `pkg/+PRE_INSTALL` lines 9–19 select old installed service, lifecycle lock `/var/run/zapret2-lifecycle.lock` with FD9, Python 3.13 and cold inspector. Lines 27–58 classify the cold-kernel state using short read-only lockf FD9, exact IPFW ENOPROTOOPT and a JSON inspector; absence of Python refuses this path. Lines 64–88 retry a previously installed status call holding inherited FD9 in narrowly recognized old service cases. Lines 99–138 preserve restart marker for running, stop only when recognized, and refuse incomplete/unknown state. This older-installed-code inspection is **not** a general safe Python-independent Stop.
- `pkg/+PRE_DEINSTALL` lines 13–55 check installed service status, refuse unverified `2`/other codes and Stop only for verified running `0`. This hook itself has **no FD9 retry**; whether the service handles its own FD9 depends on its exact old deployed content. Executable absence causes the status/stop branch to be skipped (line 13), a boundary to test during native replacement.
- `pkg/+POST_DEINSTALL` is a no-op. Existing transitory restart markers are not owned here and the hook does not signal unrelated global daemons.
- `pkg/+POST_INSTALL` lines 24–85 checks existing configd watcher parent and exact child process pattern, signals **only the matched worker** via `SIGTERM`, then waits for a changed worker and successful system status. It registers/configures/templates, then lines 135–163 restores a previously running instance only when a preserved marker exists. Lines 165–173 opportunistically refresh extra-resource inventory using hardcoded `/usr/local/bin/python3.13` if present. This **does not** prove configd PID reuse is excluded on a real system, nor prove target state restores correctly.
- `src/opnsense/scripts/OPNsense/Zapret/zapret_service.sh` is currently Git mode `100644`, whereas existing packaged service is executable because bespoke staging performs `chmod`. The official native packager must ensure required execute permissions at source before installation.

## Automated source and negative contracts

`scripts/stage0-hook-lifecycle-audit.py` uses exact `git rev-parse HEAD`, `git ls-tree` and `git show HEAD:path`, verifies Git blob SHA-1 and records line-numbered occurrences and source modes for all four hooks and service in a machine-readable JSON CI artifact. It always sets `target_pkg_hook_execution_order_tested=false`, `runtime_fd9_signal_process_ownership_tested=false`, `python_loss_native_stop_tested=false`, `foreign_ipfw_cleanup_tested=false`, `signed_target_provider_qualified=false` and `stage0_closed=false`. Its regex classifications are **source observations**, not claims that hook actions are safe on the installed target.

Five isolated Git fixture tests exercise positive source classification, wrong HEAD refusal, deleted hook refusal, ignored uncommitted edits, and Git service mode 0644 versus 0755. The existing package lifecycle regression additionally checks RUNNING/STOPPED restart markers and fake configd signalling, but uses mocked service and cannot establish actual `pkg` ordering or ownership. The new audit and its fixture tests run in existing Stage 0 CI, and the exact-head JSON is retained with the source inventory artifacts.
