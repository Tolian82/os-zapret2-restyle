## Result

Scenario 1 failed.

Stages 00, 10, 20, 30, and 40 passed. Stage 50 failed immediately with:

```text
Temporary candidate runtime failed internally.
```

Stage 90 then reported:

```text
RESTORE_FAILED — Исходное состояние Zapret2 восстановить не удалось.
```

The final service state was STOPPED.

## Live stage-90 timing evidence

A one-second live watcher captured the restoration path.

First restoration attempt:

- 13:31:00 — stage 90 begins and normal runtime rebuild starts;
- 13:31:02 — dvtws2 is running, supervisor not yet present;
- 13:31:07 — service is fully ready, semantic runtime status is RUNNING, supervisor and rule 19000 are present;
- 13:31:07 through 13:31:45 — the restored service remains healthy and RUNNING;
- 13:31:46 — the healthy runtime is stopped and all normal PID files disappear.

Second restoration attempt:

- 13:31:45/46 — second rebuild starts;
- 13:31:52 — service is fully ready again;
- 13:31:52 through 13:32:30 — the restored service remains healthy and RUNNING;
- 13:32:31 — the job terminates `RESTORE_FAILED` and the normal service is stopped again.

The two healthy-runtime lifetimes align exactly with the configured `STRATEGY_LAB_RESTORE_TIMEOUT=45` envelope.

## Root cause

`strategy_lab_timed_service_action()` wrapped `strategy-lab-start` in:

```text
/usr/bin/timeout 45 zapret_service.sh strategy-lab-start
```

without FreeBSD foreground mode.

On FreeBSD, `timeout` without `-f` / `--foreground` becomes a reaper for the command and its descendants and waits for those descendants to terminate. `strategy-lab-start` intentionally creates long-lived `dvtws2` and supervisor daemon descendants. Therefore the service action itself completed and the runtime became fully healthy, but `timeout` continued waiting for the daemon descendants. At 45 seconds it timed out the process tree, killing the successfully restored runtime. The lifecycle retry repeated the same failure a second time.

This is a deterministic FreeBSD lifecycle defect, not a failed dvtws2 startup or supervisor readiness problem.

## Correction boundary

The corrective patch must use `timeout -f` specifically for the daemonizing `strategy-lab-start` action on FreeBSD, so the bounded service-control command is timed while its intentionally long-lived daemon descendants remain outside timeout reaping. Stop actions retain normal timeout semantics.

A regression must emulate FreeBSD and reject a daemonizing lifecycle start that omits foreground mode, while also rejecting accidental foreground-mode use for stop.

Stage 50 is a separate live blocker and is not part of this correction.
