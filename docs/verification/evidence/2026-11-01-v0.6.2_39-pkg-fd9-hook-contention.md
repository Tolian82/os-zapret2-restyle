# Stage 0.09 — Native pkg hooks versus one externally retained FD9

**Source-only** `v0.6.2_39`, pinned parent `main=9666b6ff4d105efd9e3978e404e4a276d2630038`. Approved native TЗ/plan remain independently editorial v1.3. Stage 0 **OPEN**, Stage 1 **BLOCKED**. Published stable `v0.6.2/0.6.2_1.pkg` and owner appliance unchanged. **No `0.6.2_39.pkg` produced.**

## Question arising from proven pkg hazards

The [_36 original PRE_DEINSTALL / genuine pkg delete](2026-11-01-v0.6.2_36-original-unknown-owner-native-refusal.md) and [_37 incoming PRE_INSTALL / forced replacement](2026-11-01-v0.6.2_37-incoming-preinstall-refusal.md) experiments proved `pkg` continued destructive operations despite nonzero hook refusal. The [_38 authentic installed predecessor cold/unknown-owner pre-pkg gate](2026-11-01-v0.6.2_38-independent-prepkg-cold-gate.md) proves isolated **read-only refusal before any package operation**, not an atomic transaction. The next required feasibility question is whether an external original-FD9 lock could remain exclusively held **across actual native pkg** without making its lifecycle hooks fail on attempted re-acquisition.

The official FreeBSD [lockf(1) manual](https://man.freebsd.org/cgi/man.cgi?query=lockf&sektion=1) documents descriptor-based `lockf -s -t 0 9` using BSD flock(2); the manual describes the lock contract, not actual pkg hook scheduling or historical service compatibility.

## Bounded disposable test

- Use verified disposable KVM OPNsense 26.7, FreeBSD:15:amd64, and require the real plugin package **absent**. Build **two synthetic** harmless `zapret2-stage0-fd9-hook-fixture` packages with four explicit tracer hooks each, differing version and one private marker payload. Isolated `PKG_DBDIR` and private package cache and files are contained in a fresh temporary directory. No published Zapret2 archive is downloaded.
- Install old inert fixture, verify its actual pkgdb identity and payload. The parent then acquires an exclusive `flock(2)` on a private lifecycle lock path and proves a second native `/usr/bin/lockf -s -t 0 9` contender cannot acquire it.
- **While the parent keeps the same original lock open and held**, call real `pkg -o REPO_AUTOUPDATE=false add -f` with the new synthetic package. Its incoming `pre-install` and `post-install` hooks each open the **same path on FD9**, use native zero-timeout lockf, and deliberately exit 73 with distinct trace lines when lock acquisition fails. Require the independent contender still cannot acquire FD9 **after the pkg command but before parent release**.
- Record actual command exit, stderr, exact ordered synthetic hook trace, installed pkgdb and marker bytes; classify a replacement despite hook lock refusal separately from preserved/partial outcomes. After releasing the parent lock, prove an independent native contender **can** acquire it. Report `product_safety_acceptance_passed=false` regardless of observed package outcome.

## Evidence status and necessary limits

**Prepared source:** `scripts/stage0-opnsense-pkg-fd9-contention.py`, its offline contract tests, and a dedicated pinned disposable OPNsense workflow. **Native/fast CI PENDING**, not claimed PASS before execution.

This is **not** a production owner gate or an authorized update path: new and old hooks are synthetic, native pkg is only touching the synthetic fixture under a private pkgdb, an externally held lock is not yet integrated into any supported package manager entrypoint, and there is **no** original installed `0.6.2_1` service, true RUNNING/foreign IPFW, genuine upgrade, or native successor. Replacing a synthetic fixture while FD9 is held would establish a significant *hook-level lock mismatch hazard*, not a safely guarded transaction. Even if hooks fail and pkg continues, do not relax LH-01–LH-07. Any actual new package build/installation, real Stop/Start/Apply or production compatibility change belongs to the approved later stages and separate target acceptance.

**Next:** accept only exact-head real OPNsense evidence of FD9 holder, both original-style hook acquisition outcomes, package-manager result and lock release. Then design a production path that owns the transaction and avoids reentrant old/new hook deadlock, with verified RUNNING/foreign negatives before Stage 0 closure.
