## Source-proven next blocker

Fresh review of the exact `_15` candidate runtime found a FreeBSD lifecycle defect in
`strategy_lab_candidate_start()`.

The production code starts the temporary dvtws2 runtime with:

```text
/usr/sbin/daemon -p <child-pidfile> -o <logfile> -f dvtws2 ...
```

and invokes that command synchronously before entering the candidate readiness loop.

FreeBSD `daemon(8)` semantics are explicit: when `--child-pidfile` (`-p`), output, or
other supervision options are used, the target program is run as a spawned child and the
`daemon` monitor waits until that child terminates. Therefore a healthy long-lived dvtws2
candidate prevents the shell from reaching `strategy_lab_candidate_ready()` at all. The
current Linux fixture had hidden the defect because its fake `daemon` spawned dvtws2 and
returned immediately instead of remaining resident like FreeBSD.

This is a deterministic source defect independent of the `_15` timeout-variable fix. A
candidate runtime cannot be accepted as ready while its `daemon(8)` monitor is invoked in
the foreground.

Reference: FreeBSD `daemon(8)` documentation, current 15.x manual: when child-pidfile or
output/supervision options are specified, `daemon` waits for the spawned program to
terminate so it can retain the pidfile lock and supervise cleanup.

## Corrective scope for `_16`

The temporary candidate `daemon(8)` monitor must be launched asynchronously, while the
existing child-pidfile, process identity, divert-port, log-cleanliness, stop, and cleanup
proofs remain authoritative. The regression fixture must model the real FreeBSD resident
supervisor instead of a launcher that returns immediately.

No GUI, DNS parser, target-type, or diagnostic-flattening defect is included in this
runtime patch. Those confirmed defects remain in the backlog.
