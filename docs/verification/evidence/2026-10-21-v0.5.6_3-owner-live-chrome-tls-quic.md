# Owner-live Chrome HTTPS, TLS1.2 and HTTP/3 evidence — v0.5.6_3

**Observed on:** 21 October 2026, owner OPNsense, private curl-impersonate wrapper `/usr/local/libexec/zapret2-restyle/run-curl-impersonate.sh`.
**Scope:** Stage 1 installed Chrome client verification only; no Strategy Lab production baseline/Model C, no IPFW attribution, and no bypass candidate was tested.
**Proof level:** Owner-live (reported console output). Signed FreeBSD 15 package/tag/SHA proof is separately captured in [v0.5.6_3 publication](testing-publications/v0.5.6_3.md).

## Read-only local prerequisite check

```text
CURL_IMPERSONATE_LOCAL_READY profile=chrome150 ca_bundle=/usr/local/etc/ssl/cert.pem network_tls_quic=NOT_TESTED
```

The client used the OPNsense CA PEM through the explicit-CA wrapper. The failed `v0.5.6_2` default-CA `curl(77)` case did not recur.

## Real owner-reported target responses

Commands used the private wrapper with `--ipv4`, `--connect-timeout 7`, `--max-time 12`, no proxy, and a real GET to the intended HTTPS URL. QUIC used `--http3-only` (no TCP fallback). No `-k` or ordinary curl.

| Requested target / policy | Reported IPv4 | Negotiated HTTP | Final status | CA verify result | Exit | Time to TLS/QUIC handshake |
| --- | --- | --- | --- | --- | --- | --- |
| `https://example.com/`, default Chrome HTTPS | `8.47.69.0` | 2 | 200 | 0 | 0 | 0.176215 s |
| `https://github.com/`, default Chrome HTTPS | `140.82.121.4` | 2 | 200 | 0 | 0 | 0.176517 s |
| `https://www.google.com/`, default Chrome HTTPS | `216.239.38.120` | 2 | 200 | 0 | 0 | 0.128696 s |
| `https://www.google.com/generate_204`, explicit QUIC/HTTP3 only | `216.239.38.120` | 3 | 204 | 0 | 0 | 0.057389 s |
| `https://cloudflare-quic.com/`, diagnostic `--ech false` | `8.6.112.0` | 2 | 200 | 0 | 0 | 0.097827 s |

All five reported `IP=` values, authenticated `CODE=`, `HTTP=`, `CERT=0`, and `EXIT=0` are actual observed client output, not simulated branch assertions. The `%{time_appconnect}` observation is time until the TLS/QUIC handshake, **not** proof of page-download latency.

The earlier Cloudflare HTTPS and QUIC checks *with* advertised ECH ended with `curl(28)` after eight seconds, whereas HTTPS with `--ech false` succeeded in ~0.098 s. This is compatible with ECH-related filtering or network/path differences, **not causal proof** of filtering by ECH or the Russian ISP. The Cloudflare-only `--ech false` run is a diagnostic: it does not authorize changing default Chrome behavior or weakening certificate checks. Earlier Cloudflare addresses/transport/mode were not all identical; no controlled A/B causal conclusion is claimed.

## Explicit TLS 1.2-only acceptance — OWNER-LIVE PASS

The owner then ran the same installed private wrapper with:

```text
run-curl-impersonate.sh --ipv4 --tlsv1.2 --tls-max 1.2 --connect-timeout 8 --max-time 15 -v -o /dev/null https://github.com/
```

The reported verbose output explicitly includes:

```text
SSL connection using TLSv1.2 / ECDHE-ECDSA-AES128-GCM-SHA256 / [blank] / UNDEF
ALPN: server accepted h2
subjectAltName: "github.com" matches cert's "github.com"

< HTTP/2 200
IP=140.82.121.3 HTTP=2 CODE=200 CERT=0
```

The client received a complete actual HTTP/2 response and downloaded page data. The explicit `--tls-max 1.2` plus negotiated TLSv1.2 in verbose server evidence excludes an automatic TLS1.3 false positive. The Chrome user-agent and HTTP/2 request headers identify `Chrome/150`. The WAN source tuple is diagnostic client output, not an assertion of Strategy Lab's future IPFW attribution.

**Stage 1 / acceptance matrix V1: OWNER-LIVE PASS**, including a signed FreeBSD15 client package, CA correction, HTTPS/TLS, forced TLS1.2, and real `--http3-only` QUIC. The private binary is not yet integrated into Standard or Model C; those are Stage 2 tasks.

## Accepted scope and pending boundary

**Positive Stage 1 installed evidence:** private Chrome `chrome150` runs on OPNsense; existing trusted CA loads and cert identity validates (`CERT=0`); real HTTP/2 over HTTPS receives multiple 200 responses; real UDP/443 HTTP/3-only request receives authenticated 204. TLS and QUIC reachability are thus confirmed for those requested endpoints. Bundle/source SHA verified separately by publisher.

**Not yet independently observed:** an HTTP/1.1-only target; a bare TLS/QUIC handshake *without* HTTP; fixed-IPv4 Host/SNI and source-port/IPFW attribution; negative baseline → Model C; 3/3 candidate confirmation/replay; Stage 90 restoration for the migrated production path; any bypass of a specific filtered site. These belong to the respective Stage 2–6 acceptance activities, not to the private-client Stage 1 gate.

**Stage 1 is closed.** The next engineering scope is Stage 2 production Standard/Model C Chrome request and reachability evidence integration, not additional client smoke testing. No additional broad Cloudflare/ECH experiments are required.
