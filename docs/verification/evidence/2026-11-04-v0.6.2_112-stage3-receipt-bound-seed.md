## Previous observable gap and this source-only change

_111 created an explicit manual `operator-pins.json` under a root-owned private `0700` directory, but **nothing in the active _109/_110 execution path consumed that receipt**. The initial `-I -B -c` trust seed still accepted arbitrary caller-passed expected verifier SHA and source commit, while the RSA checker separately accepted a public-key SHA. Incoming and old archive digests could be correctly signed but diverge from the user's recorded expectations.

_112 makes **the receipt the mandatory sole source of six SHA-256/commit/version expectations** in the read-only initial seed route. Its strict invocation is:

```text
python3 -I -B -c '<INDEPENDENTLY AUTHENTICATED TRUST SEED SOURCE>' \
  --operator-receipt /root/review/operator-pins.json \
  --verified-verifier /root/review/stage3-prepkg-verified-eval.py \
  --signed-provenance /root/review/approved-public.pem \
  /root/review/claims.json /root/review/claims.sig \
  /root/review/native-prepkg-standalone.py \
  inspect-predecessor /root/review/os-zapret2-restyle-0.6.2_112.pkg \
  0.6.2_112 /root/review/os-zapret2-restyle-0.6.2_1.pkg 0.6.2_1
```

**Illustrative only, not a deployable updater or an authorization to execute it on the owner's appliance.** The source for `python -c` MUST already be independently authenticated. Neither GitHub checkout nor an unsigned human-entered fingerprint alone proves publisher identity.

The initial seed **rejects the historical parameterized command form**. Before interpreting the external verifier, it reads a root-private, single-link `0600` receipt through one opened `O_NOFOLLOW` FD, checks stable inode/size/mtime/ctime/path, strict 4096-byte bound, `0700` parent, exact JSON key set and duplicate rejection, fixed repository and `trust_status=PINS_RECORDED_NOT_AUTHENTICATED`. The eight pins must be well-formed, nonzero, and match requested old/new package names and versions. The seed then SHA-verifies the external verifier's frozen bytes with the **receipt's** `verifier_sha256` before compiling/executing it. It constructs the verifier's arguments itself with the receipt's `source_commit`, `public_key_sha256`, `incoming_sha256` and `predecessor_sha256` — never with caller-supplied digest/commit strings.

The RSA verifier still independently hashes the public PEM, validates actual OpenSSL RSA signature over the strict JSON claims and checks signed `source_commit`. **New:** signed `incoming_sha256` and `predecessor_sha256` must *also* equal both receipt-provided expected archive digests **before any standalone CLI bytes execute**. Then the verified in-memory standalone validates the actual native current and historical archive bytes, holds original FD9 for read-only old-owner inspection and stops without `pkg` mutation.

```text
independently authenticated -c seed (NOT PROVIDED)
    -> strict local manual pin receipt (NOT production-signer authenticated)
    -> receipt SHA of frozen external RSA verifier
    -> receipt expected source commit + pinned public PEM SHA
    -> real RSA-signed claims must match both receipt archive SHA pins
    -> signed standalone source SHA and both real native archives
    -> read-only original FD9 predecessor inspection
    -> STOP: NO UPGRADE / INSTALL / REMOVE / TRANSACTION
```

The receipt's `seed_sha256` is **NOT evidence that the already-running `-c` bytes are independently authenticated**; the expected seed must come from an actually separate, owner-approved review channel *before execution*. No automatic self-provenance or production issuer approval is created here. Root can still edit a root-owned file; the receipt is a transport/binding mechanism, not an immutable cryptographic policy authority.
