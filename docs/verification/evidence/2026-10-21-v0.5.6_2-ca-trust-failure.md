# Stage 1 owner-live CA trust failure — installed v0.5.6_2

**Date:** 21 October 2026.
**Status:** OWNER-LIVE NEGATIVE. The installed private client cannot load its default CA trust anchors; **this is not evidence of provider blocking or target accessibility**.

The owner ran the private curl-impersonate binary with its selected `chrome150` profile against `https://cloudflare-quic.com/`, once using HTTPS/TLS and once using `--http3-only`.

Both attempts reported `SSL Trust Anchors: error adding trust anchors from locations: CAfile: /etc/ssl/cert.pem CApath: /etc/ssl/certs` and `curl: (77)`. The HTTPS output showed outbound ClientHello but no confirmed handshake or HTTP response; the QUIC output attempted two IPv4 addresses and failed before confirmed QUIC. Both reported `IP= HTTP=0 CODE=000 CERT=1`, `TLS_EXIT=77` and `QUIC_EXIT=77` respectively.

The old `check-curl-impersonate.sh` tested the existence of a CA file, not client certificate validation, and misleadingly displayed `CURL_IMPERSONATE_READY`. The bounded `v0.5.6_3` fix introduces explicit `--cacert` selection from existing OPNsense/FreeBSD PEM bundles and a private Chrome launcher; it reports **local** readiness and fails closed when a trusted bundle is unavailable. No `-k`, no CA download, no system curl fallback.

Real TLS and QUIC target tests using the corrected package remain owner-live acceptance requirements before Stage 2. [Canonical handoff](../../START_HERE.md) · [plan](../../architecture/STRATEGY_LAB_BROWSER_HTTP_PLAN.md).
