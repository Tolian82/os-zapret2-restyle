## Why the next boundary must be empirically tested

The original installed `0.6.2_1` has its own FD9 acquisition in service Status/Start/Stop. The incoming source `pkg/+PRE_INSTALL` similarly calls historical Status and sometimes tries another FD9. A proposed external caller holding `/var/run/zapret2-lifecycle.lock` **could conflict with its own child service/hooks opening new descriptors**. A held FD9 is not, by itself, proof that native `pkg` stops when those hooks refuse. The [published FreeBSD 15 lockf(1) manual](https://man.freebsd.org/cgi/man.cgi?query=lockf) specifies `lockf -s -t 0 9` for an immediate independent FD challenge, returning EX_TEMPFAIL/75 when another open file description owns the lock. Earlier [real old service FD9 proof](2026-11-01-v0.6.2_34-installed-old-service-native-fd9.md) qualified its Status locking only against an isolated *temporary* lock file. This test uses the **actual installed default pathname**, without an alternate `LIFECYCLE_LOCK_FILE`.

The [_74 unlocked old Status=2/pkg mutation](2026-11-02-v0.6.2_74-stage2-real-unsafe-owner-native-pkg.md), [_76 genuine locked package refusal](2026-11-03-v0.6.2_76-stage2-real-locked-unsafe-owner.md), [_77 stock OPNsense entrypoint matrix](2026-11-03-v0.6.2_77-stage2-entrypoint-admission-matrix.md), and [_78 native stock configd Unlock bypass](2026-11-03-v0.6.2_78-stage2-stock-configd-unlock-native.md) establish that `pkg lock` and a rejecting incoming hook cannot qualify atomic product admission. This new native test asks a **different, narrower question**: can an **outer genuine FD9 holder and its real pkg descendant** coexist with authentic historical lock-taking hooks, and does native pkg still mutate its installed package despite a hook refusal?

3. Check `/var/run/zapret2-lifecycle.lock` is absent or an original root-owned, regular single-link inode; reject symlink or foreign file. A privileged `/bin/sh` opens it as `9>`, calls real `/usr/bin/lockf -s -t 1 9`, and keeps FD9 open **while calling native `pkg -o REPO_AUTOUPDATE=false add -f`** of the official successor. It does not invoke shell Stop/Apply or modify the four hooks.
4. A separate real process opens the *same* pathname and calls `lockf -s -t 0 9`; require exit **75** while holder is alive, both before native pkg and after the held shell marks entry into the pkg invocation. On a timeout, kill the test process group; do not pretend uncertain ownership is a successful transaction.
5. Record real pkg return code, final installed identity, authentic hook-refusal text when a replacement occurs, Config byte comparison, original installed service hash/record when still present, restart markers and unchanged signed native archive. Print the state **before disposing of the VM**, without deleting foreign IPFW or recovering a possibly half-upgraded guest.
6. Never interpret a green hazard workflow as native no-mutation acceptance. A new installed pkg despite historical hook refusal is an **explicit FAIL of product safety**, even if this diagnostic workflow reports PASS for *observing* that failure. An unchanged old pkgdb does not prove original Config/service/marker identity unless independently observed and matching.

## Measured exact-head native OPNsense 26.7 outcome — unsafe bypass confirmed

**Native PASS as a diagnostic hazard only:** [CI #41565876126](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41565876126), exact source `7b70462f718744708780f8db177e71952e496ad1`. `PASS_REAL_OUTER_FD9_PKG_FEASIBILITY_HAZARD_ONLY` / `OBSERVED_HELD_FD9_NOT_A_NATIVE_PKG_VETO`. Original installed package: `os-zapret2-restyle|0.6.2_1`.

A real shell-held original `/var/run/zapret2-lifecycle.lock` FD9 was independently observed busy **both before and during native pkg entry** (`outer_fd9_contended_before_pkg=true`, `outer_fd9_contended_during_pkg=true`, each independent `lockf -s -t 0 9` fails). Authentic incoming `PRE_INSTALL` **refusal text was observed**. Nevertheless native `pkg add -f` returned **0** and changed actual installed pkgdb identity to `os-zapret2-restyle|0.6.2_79`. Config bytes **changed** (`config_bytes_unchanged=false`); original pkgdb **not preserved**. Restart markers absent after pkg. The installed service bytes still matched the former hash (`original_service_unchanged=true`), **not** proof that the original package survived. No foreign IPFW operation or guessed rollback was performed; the disposable VM was discarded.

**Pinned archive SHA-256:** published old `0.6.2_1.pkg` = `1e21fbcac847529b94fea940241b4da7f86a42d33c129b7003ad04a72f4e5a0f`; genuine official Mk-built source-only successor `0.6.2_79` = `7d599e9cd63cf53e5ee72f209f006dc622ccb4664d420a976a58238bf0e6f07c` (unchanged after observation). **No `_79` package was published or installed on the owner appliance.**

**Precision limit:** the FD9 contention and genuine hook refusal are measured, but no per-hook PID/FD syscall trace identified exactly which internal lock attempt blocked or refused. The justified conclusion is that holding external FD9 alone **does not veto native pkg**, not that a particular recursive lock site was independently traced. In a separate native `_78` witness, stock firmware configd Unlock removed the pkg metadata lock before a forced package replacement. These are independent negative findings. **LH-08/AC-11 BLOCKED** until a supported owner-aware pre-pkg admission is implemented and all no-mutation negatives pass on the same final package SHA.
