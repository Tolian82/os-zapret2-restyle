Owner tested the installed `os-zapret2-restyle-0.5.7_46` GUI. RU/EN switching, F5, and the bottom Strategies Apply passed. The upper upstream-release Apply initially failed with `Zapret2 setup error`; the appended `/var/log/zapret2/setup.log` (historical entries as well as final attempt) ended with `RECOVERY_REQUIRED: previous upstream rollback snapshot exists`. The rollback directory contained only `binaries/` (no `checkpoint`), from 23 October, while the native service was Started, upstream Git was clean, `runtime.release=v1.0.6`.

The owner followed the reviewed, console-driven quarantine procedure while the service was running, preserving the incomplete old rollback corpus at `/var/db/zapret2-restyle/rollback-quarantine.onv082Er/runtime-rollback`. The original path was then absent. This was an **explicit operator action**, not an automatic updater deletion. Snapshot availability on the hypervisor remains unconfirmed.

The owner then requested the upstream switch from `v1.0.6` to `v1.0.5.2` via the upper button. **Native upstream switch succeeded**, as evidenced by the owner-provided post-operation console output:

- `setup.status=ready`
- installed upstream Git exact tag `v1.0.5.2`
- native `zapret_service.sh status` prints `zapret is running`
- no new `runtime-rollback` directory
- final setup.log contains `Runtime installation completed successfully; zapret service remains stopped.` (native wrapper subsequently restores the prior Started state)
- `PASS: managed additional resources are preserved` during the update.

**GUI defect:** the upper Apply remained indefinitely at `Применение…` with temporary service badge `Ошибка`, even though the completed native state became Started `v1.0.5.2` after F5. This is a confirmed owner-live **M3 GUI FAIL**, not an upstream switch failure. Source `_46` only starts its background status polling after observing `busy=1`, so a native-held FD9 status timeout or missed busy pulse can leave the spinner without a timer. The source improvement in the subsequent candidate `_47` starts polling on accepted dispatch, serializes requests, uses bounded uncertain-result handling, correlates terminal completion with actual selected release and original service semantics, and avoids blocking native status inspection while setup is busy.

**Acceptance boundary:** unchanged installed `_46` is still affected. A source CI PASS for `_47` will not close the owner-live GUI row until an owner installs its package and retests the upper Apply without F5. M4 Stage-60 execution, cold reboot and explicit damaged-plugin clean reinstallation remain untested.
