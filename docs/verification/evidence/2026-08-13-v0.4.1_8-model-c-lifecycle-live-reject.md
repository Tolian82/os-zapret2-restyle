## Source diagnosis

The lifecycle instrumenter appends a sample only after a Model-C `_bucket_batch` returns
successfully. Production `stage60_model_c.expand()` intentionally catches
`ModelCInfrastructureError` and replays that batch through Model B, persisting the fallback
batch evidence and its Model-C fallback reason.

A persisted fallback batch can therefore outnumber successful Model-C instrumentation
samples. `_8` raised the generic count mismatch before extracting the persisted
`model_c.fallback_reason` / `warm_error`, and the worker later removed its private session
tree during normal cleanup.

This establishes a measurement-harness diagnostic defect. It also establishes that the
isolated `_8` replay reached a production fallback boundary after passing the earlier
directory-traversal corrective. Because the primary fallback reason was masked, this
observation is **not** evidence of a production Model-C regression and supplies no valid
lifecycle-cost measurement.

## Required corrective

The next packaged measurement corrective must persist exact fallback evidence before
count/sequence validation, leave a rejected but inspectable top-level report, fail fast
after the first incomplete repeat, and keep production Model C/B/A unchanged.
