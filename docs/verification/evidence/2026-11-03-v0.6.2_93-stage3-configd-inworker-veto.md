**Source-only candidate:** `v0.6.2_93`, exact baseline main `4b5be1df05197965e40ac8b3edd0038536388b01`. **At creation: native KVM evidence PENDING; no product-supported installer implemented; LH-08/AC-11 BLOCKED.** All code runs only in a throwaway GitHub OPNsense 26.7 guest (root/FreeBSD 15 amd64/exact source SHA and explicit test-only opt-in). ## New and consequential caller boundary

Previous accepted `_89` genuine native positive old-hook-to-`pkg` used a root process **outside** OPNsense configd; `_91` demonstrated late IPFW/journal no-pkg refusal at the same explicit Python dispatch gate, also **outside** configd. These do not establish that a supported `configctl`/Web → configd caller can perform a safe actual package replacement.

Official OPNsense [configd backend documentation](https://docs.opnsense.org/development/backend/configd.html) describes privileged actions defined under `/usr/local/opnsense/service/conf/actions.d`, activated with `service configd restart` and invoked using `configctl`. This is a real, supported integration surface for custom plugin GUI/CLI actions, but **it is not a veto for stock firmware/Web plugin-manager operations**; prior [_86 stock firmware route audit](2026-11-03-v0.6.2_86-stage2-native-prepkg-route-decision.md) already documented their separate unqualified path.

**Critical self-termination hazard found in the candidate's actual current `pkg/+POST_INSTALL`:** `reload_configd_actions()` reads `/var/run/configd.pid`, finds its current `/usr/local/opnsense/service/configd.py console` child with `pgrep -P`, then sends **SIGTERM to that worker**, waits for a different worker and executes `configctl system status`. Thus a synchronous modifying `pkg` called **inside the same configd worker's action** could terminate the exact worker responsible for keeping that transaction and its caller alive. A passing `_89` standalone process does **not** prove such an in-worker call safe. This must be evaluated **before** attempting mutating `pkg` through configd; no speculative override of stock firmware or original archived hooks is authorized.

New [source-only diagnostic](../../../scripts/stage3-native-configd-inline-veto.py) and [offline negative tests](../../../scripts/test-stage3-native-configd-inline-veto.py) are run from an additional job inside the **already required** [Stage 2 genuine original-hook native pkg workflow](../../../.github/workflows/stage2-native-delegated-fd9-handoff.yml); both existing genuine `_89` positive native pkg and `_91` negative late-owner jobs are **unchanged and must continue to PASS**.

On its own disposable OPNsense 26.7 guest, the new job:

1. Attests root, machine/OS, exact GitHub candidate head, explicit one-use test flag, and published historical `0.6.2_1.pkg` SHA256 `1e21fbcac847529b94fea940241b4da7f86a42d33c129b7003ad04a72f4e5a0f`. Installs the **original old package only as disposable fixture**, verifying original four hooks and current installed provenance. No incoming `_93` package is installed.
2. Snapshots actual original pkgdb, all installed files/modes/ownership, Config, plugin markers, owned processes and IPFW with the existing `_87` read-only owner observer, asserting genuine old STOPPED and cold kernel.
3. Creates exactly one **private test-only** root-owned mode `0600`, `O_EXCL|O_NOFOLLOW` action named `actions_zapret2_stage3_ci.conf`. It accepts **no user parameters**; its command is the fixed checked-out Python diagnostic with exact source SHA and no modifying `pkg`. It is **not part of installed product**.
4. Restarts actual native configd to register the action and runs **real `configctl zapret2_stage3_ci veto`**. The diagnostic proves its parent-process chain contains the actual current configd worker located using **the same pidfile/`pgrep` worker signature as the real POST_INSTALL hook**, proves the real current hook's kill/reload path is present, checks the unchanged old stopped owner, then returns `PASS_REAL_CONFIGD_INWORKER_PKG_REFUSED_BEFORE_MUTATION`. 5. The caller verifies the single expected output, removes **only** its exact original action content/inode and restarts configd, refusing on any cleanup failure or foreign modification. It compares the whole original owner snapshot before/after; no plugin package, Config, process, marker or IPFW mutation may be accepted.

**Positive result**, if real target confirms all these rows, is an **enforced absence of a mutating `pkg` call in this unsafe synchronous configd worker design**, not a product-safe upgrade, not a proof that the OS cannot support a different entrypoint and not acceptance of LH-08/AC-11. The real test must fail if the configd lineage or installed worker-reload path differs from the assumptions; do not simply lower checks to make an unknown process graph green.
