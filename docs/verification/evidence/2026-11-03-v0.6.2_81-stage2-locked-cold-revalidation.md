## Purpose and empirical reason

The real [`_79` hazardous pkg replacement](2026-11-03-v0.6.2_79-stage2-held-fd9-pkg-feasibility.md) proved authentic PRE_INSTALL refusal and externally busy FD9 do **not** veto direct native pkg replacement. The genuine [`_80` inherited-FD9 original Status](2026-11-03-v0.6.2_80-stage2-original-fd9-nested-status.md) did **not complete within seven seconds** under outer FD9. Published old `zapret_service.sh status` opens another descriptor `9>"$LIFECYCLE_LOCK_FILE"` and invokes `lockf`; this is inconsistent with assuming nonrecursive Status handoff, but exact syscall traces remain absent.

This `_81` diagnostic tests a narrower necessary condition: can a disposable native CI shell hold **the original historical FD9 inode** while independently reading verified cold package/process/IPFW/Config state, without calling old Status under the lock? No hook or stock firmware path is changed.

## One-use native sequence

1. Require root, explicit GitHub Actions opt-in, actual virtual OPNsense 26.7/FreeBSD 15 amd64, original immutable SHA-qualified `0.6.2_1.pkg`, actual original four hooks/service and an existing independently verified cold old Status **before acquiring the outer FD9**.
2. The shell opens historical `/var/run/zapret2-lifecycle.lock` once as FD9, uses genuine FreeBSD `lockf -s -t 0 9` and `exec` to the read-only checker. The checker requires `fstat(9)` to match the root-owned, regular, unique historical lock inode and makes a **separate process** fail an exclusive lock attempt with exact exit 75. This demonstrates a held descriptor, not a universal gate against root/stock firmware.
3. **Without invoking the old service Status again**, re-verify immutable original archive, installed pkgdb/manifest/four hooks, original service bytes/mode/ownership, absence of the shared journal, markers, pidfiles and pending Extra Resources, real process census and exact FreeBSD cold `ipfw`/module ENOPROTOOPT signatures. Compare original pkgdb, service and Config bytes within this read-only probe.
4. Negative scenarios: another real process already holding original FD9 must cause refusal **before the checker runs**. A deliberately invalid shared-Apply journal, owned only by the disposable test fixture, must refuse **inside** the genuine held FD9. After fixture cleanup, confirm unchanged original pkgdb/service/Config/markers and restored old cold evidence. No IPFW modification is performed.
5. An installed old `RUNNING` owner or loaded kernel is **not accepted by this cold-only predicate**. Native successor pkg, Web/firmware routes, concurrent Apply/Start/Stop, arbitrary root pkg and interruption at the replacement phase are **NOT tested** here.

**Proof ceiling:** a successful cold revalidation under FD9 is NOT a proven continuous admission-to-pkg interval, native hook nonrecursive handshake, supported Web/firmware interception, old RUNNING ownership, direct-root pkg veto or LH-08/AC-11 closure.

## Safety conclusion and next gate

A possible diagnostic result `PASS_PREPKG_FD9_COLD_REVALIDATION_DIAGNOSTIC_ONLY` means only that *read-only* old STOPPED/cold consistency was examined while an exclusive historical FD9 was held. It **does not authorize pkg**, grant permission to change Config, show a supported Web/firmware admission, prove nonrecursive historic hook calls through pkg or prevent privileged root bypass. A failed cold, busy or unknown test is a proof limitation/refusal, not license to weaken the predicate.

**LH-08/AC-11 remain BLOCKED** until a genuinely enforced, supported pre-pkg entrypoint with a nonrecursive continuous owner contract can deny native replacement **before any mutation**, including the original `_74` orphan IPFW condition, and pass all no-mutation negatives.
