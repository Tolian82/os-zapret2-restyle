# Stage 0.09 — Characterize historical old hook refusal vs native pkg deletion

**Source-only `v0.6.2_36`; parent `main=015e612cf7f71221f27f5ba7e46ee38eb18fb2cb`.** Approved technical specification/plan remain v1.3; Stage 0 OPEN / Stage 1 BLOCKED, stable published `0.6.2_1.pkg` unchanged.

## Actual target and negative witness

On **fresh disposable KVM OPNsense 26.7** (FreeBSD:15:amd64), install and SHA-256-verify exact immutable published `0.6.2_1.pkg` (`1e21fbcac847529b94fea940241b4da7f86a42d33c129b7003ad04a72f4e5a0f`), then attest real installed four unchanged hook bodies, original service SHA256/mode/pkg owner, initial `status=STOPPED`, and absent shared Apply journal/markers. The only injected state is **one synthetic corrupt root-only shared Apply journal `/var/db/zapret2/shared-apply/operation.json`**, deliberately malformed JSON. This is **not** evidence of real foreign IPFW rule ownership or legitimate committed RUNNING state. The OPNsense image is from pinned third-party VM action, not independently SHA-authenticated against official image.

Require actual old installed service `status=2` and `zapret is in an incomplete runtime state`. Invoke the **exact unchanged original installed `PRE_DEINSTALL` body** via `/bin/sh -x` against real old service and private FD9/marker paths. Prove it returns nonzero with `service_status=2`, original incomplete-lifecycle diagnostic, **no Stop** and no restart marker.

Then measure real native `pkg delete -y os-zapret2-restyle` with original installed hooks enabled and no force/script-bypass flags, capture its exit code and original hook diagnostic, query **actual package database and actual service-file presence** afterward. Crucial: **do not assume that a failed hook blocks pkg deletion**. The test records one of two precise outcomes:
- `REMOVED_DESPITE_PRE_DEINSTALL_REFUSAL`: `pkg delete` returned 0, package absent from pkgdb and original service absent. **UNSAFE OLD-PACKAGE LIFECYCLE HAZARD; not safety acceptance.**
- `REFUSED_WITH_PACKAGE_PRESERVED`: `pkg delete` returned nonzero, package and service remain, immutable original archive-vs-installed payload unchanged. **Bounded native refusal evidence** for this particular injected scenario.

Any partial/inconsistent deletion, missing hook diagnostic, changed unrelated journal, restart marker, unverified guest/bytes or failed cleanup is a **refusal**. After measuring, check the injected journal remains unchanged, and remove *only* the exact test-created record/directory and (if newly created) empty runtime root; no recursive cleaning or owner-appliance actions. Recheck cold STOPPED only if the original package still exists. CI success for a completed hazard characterization **must not be represented as an LH-02 product safety PASS**.

The next revision of this same PR instruments actual native `pkg` exit code, hook diagnostic, installed package-record existence, and installed service-file existence **after** the attempted deletion. Real detailed outcome now independently **MEASURED** by CI #41314033536. Nine offline tests cover both possible outcomes and negative safeguards.

Do not rely solely on historical `PRE_DEINSTALL` exit code or assume it can prevent explicit `pkg delete`; LH-01, LH-02, LH-06, LH-07 remain OPEN. Future native replacement must have an independently verified preflight/owner control **before** a destructive `pkg` transaction, with the approved architecture/plan maintained; no scope-creep fix of immutable published predecessor.

[Exact-head real OPNsense 26.7 CI #41314033536](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41314033536) **successfully completed the characterization experiment** with **nine offline tests PASS** and original actual published package installation/provenance PASS. **Unambiguous finding:** native FreeBSD `pkg delete` proceeded to remove the exact original installed `0.6.2_1` package, even while its original PRE_DEINSTALL emitted the lifecycle refusal on the synthetic corrupt common journal. The test was not a real running/foreign-IPFW runtime, so this proves **native deletion ignores the historical refusal as a barrier in this scenario**; it does not prove what happens to a live engine or firewall. The successful *test workflow* means the unsafe behavior was reliably observed, **NOT** that package deletion or product safety passed. Do not use this historical hook alone as a safety gate for any package-management action on an owner appliance.

**Blocking next step:** Before any real successor replacement or non-disposable package removal, design/qualify a separately enforceable pre-transaction owner gate and its native `pkg` integration, including the possibility that `pkg` may proceed after a hook reports failure. This is a safety-critical risk record under binding LH-01/LH-02/LH-06/LH-07; do **not** silently weaken v1.3 safety requirements to accept the historical behavior. Actual native successor acceptance and Stage 0 closure remain OPEN.
