## Direct resolver observation

Immediately after the failed job, the owner ran:

`/usr/bin/drill rutracker.org A`

One captured invocation succeeded with two A answers (`104.21.32.39` and
`172.67.182.196`), query time 33 ms and resolver `127.0.0.1`. Repeated manual invocation
also showed the important intermittent behavior: some queries return immediately while
others take roughly 8–10 seconds before returning valid data.

The Strategy Lab evidence and the direct observation together prove that a hard
2-second Python subprocess deadline can reject a valid local-Unbound resolution on this
OPNsense system.

## Source diagnosis

The `_26` Stage-50 correction did not change `strategy_lab_py/request.py` or
`strategy_lab_py/probe.py`; the Stage-40 parser fix from `_21` remains present.

Current Python request code gives `drill` only 2 seconds. The Python orchestrator also
gives the entire Stage 40 a 5-second operation envelope. Raising only the DNS subprocess
deadline would therefore expose a second premature outer timeout before an observed
8–10-second valid resolver response can complete.

Corrective `_27` must keep the request bounded while widening both limits coherently:

- DNS subprocess: 15 seconds;
- Stage-40 operation envelope: 20 seconds;
- Standard overall job budget: unchanged at 150 seconds.

The correction must preserve the existing distinct `timeout`, `command_error` and
`parser_rejected` classifications and the ANSWER-section-only parser.
