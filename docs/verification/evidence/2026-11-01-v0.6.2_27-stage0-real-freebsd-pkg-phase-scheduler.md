## Verified upstream, bounded test scenario

The [FreeBSD pkg upstream scripts contract](https://github.com/freebsd/pkg/blob/main/features.md) defines `pre-install`, `post-install`, `pre-deinstall`, `post-deinstall` with `PKG_PREFIX`, `PKG_ROOTDIR`, `PKG_UPGRADE` and process-reaper semantics; it supports rootdir-friendly install. This source-level contract is **not proof of exact replacement phase ordering**. The archived [published immutable `v0.6.2_1.pkg`](https://github.com/Tolian82/os-zapret2-restyle/releases/download/v0.6.2/os-zapret2-restyle-0.6.2_1.pkg) at SHA-256 `1e21fbcac847529b94fea940241b4da7f86a42d33c129b7003ad04a72f4e5a0f` is independently downloaded in a disposable FreeBSD 15.1 VM. The new `scripts/stage0-real-pkg-scheduler.py` first refuses any archive digest, predecessor identity, target ABI or four nonempty authoritative hook metadata mismatch. It records SHA-256 and byte counts for every **actual archived package hook** as separate provenance; these hooks **are not invoked by the fixture**.

The script then creates two explicitly named **synthetic fixture packages** (`zapret2-stage0-phase-order-fixture`, versions `0.6.2_1` and `0.6.2_27`), each with **four short trace-only hooks**. No package named `os-zapret2-restyle` is installed or replaced. It calls native `pkg create -M`, `pkg add`, `pkg query` (confirm **old** fixture version installed), then `pkg add -f` and another `pkg query` (confirm **new** fixture version installed). Once the four-phase forced-add behavior is confirmed, it performs a **separate `pkg delete`** to distinguish uninstall-specific hooks. All commands execute inside the disposable VM with an isolated pkg DB and only harmless trace bodies. All fixture-owned files live inside a fresh private `/tmp` directory; `PKG_DBDIR` and `PKG_CACHEDIR` are separate private directories, with `REPO_AUTOUPDATE=false`; no configured repository, production package, OPNsense service, rules or real host user configuration is changed.

The **real `pkg add -f` observed phase sequence** from first native CI run [#41286214143](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41286214143) **differed from the previous six-phase assumption**: only old pre/post-install and new pre/post-install executed; old pre/post-deinstall did **not** execute. The corrected CI runner now **confirmed the old fixture was installed** via `pkg query` before replacement, **confirmed the new fixture** after `pkg add -f`, then invoked **a separate explicit `pkg delete`**. The fully observed combined trace on real FreeBSD15.1 is:

```text
old:pre-install
old:post-install
new:pre-install
new:post-install
new:pre-deinstall   # separate explicit pkg delete, NOT forced replacement
new:post-deinstall  # separate explicit pkg delete, NOT forced replacement
```

Unexpected/missing/duplicate phases, failed old/new installed-version checks or missing explicit delete phases remain `NOT_VERIFIED` with an artifact or CI log containing **observed** and **expected** order. The earlier six-phase force-add assumption is **falsified by actual native pkg observation**, not silently accepted. The corrected expected combined trace distinguishes forced replacement from explicit deletion and **PASSED the real VM run**, without assuming that old deinstall hooks run during forced add. The new runner is rejected outside **root-owned disposable FreeBSD 15.1 amd64**; the fixture package is deliberately named differently so it cannot be confused with actual `os-zapret2-restyle` installation.

**What PASS would establish:** the **real native FreeBSD15.1 pkg scheduler** executes this observed order for *synthetic tracing hook bodies*, while the historical stable `.pkg` bytes and its four embedded hook hashes are separately validated. It would not prove actual historical hooked service execution, old `+PRE_DEINSTALL` inherited FD9, status/stop, configd worker identity, Python-loss path, full OPNsense binary/install dependencies, or a new native OPNsense package. No successor `os-zapret2-restyle-0.6.2_27.pkg` is produced/published or installed. This **cannot close LH-01–LH-07** or Stage 0.09/0.13 acceptance by itself.
