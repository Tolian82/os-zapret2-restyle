## Official source provenance and bounded entrypoint audit

Pinned [OPNsense core stable/26.7 source commit `874c32d7e5e337f19f256066b9689e91e56d5277`](https://github.com/opnsense/core/tree/874c32d7e5e337f19f256066b9689e91e56d5277), plus explicit real installed guest read-only verification in [`scripts/stage0-opnsense-native-pkg-lock.py`](../../../scripts/stage0-opnsense-native-pkg-lock.py). `FirmwareController.php` `installAction`, `removeAction` and `reinstallAction` call `configdpRun("firmware install/remove/reinstall")`; `actions_firmware.conf` routes those to `/usr/local/opnsense/scripts/firmware/launcher.sh`; `launcher.sh` selects the corresponding `install.sh`, `remove.sh` and `reinstall.sh` from `config.sh`'s `BASEDIR`. Its `FLOCK` with `LOCKFILE` serializes cooperating **firmware launcher** tasks; `config.sh` selects `/usr/local/sbin/pkg` for package operations. The installed `install.sh` and `remove.sh` invoke `pkg install -y` and `pkg remove -y`; `reinstall.sh` can invoke `opnsense-revert` rather than an identically shaped `pkg install`. This is a **selected Web API package operation chain**, NOT proof that all firmware update, auto-update, upgrade, dependency, rollback, system service, or direct root pkg entrypoints follow it.

The actual disposable guest verifier compares **semantic route tokens** and records SHA256 hashes of installed `FirmwareController.php`, `actions_firmware.conf`, `launcher.sh`, `config.sh`, `install.sh`, `remove.sh`, and `reinstall.sh`. It does not assume that the third-party CI guest's installed minor patch matches the pinned source commit byte-for-byte. It never invokes Web/configd/firmware for real mutation, alters official source files, or patches global package manager configuration.

## Native pkg lock feasibility experiment

FreeBSD officially documents `pkg lock` as protecting installed packages from reinstall, upgrade and removal, but only for already-installed package identities (see [FreeBSD Handbook](https://docs.freebsd.org/en/books/handbook/ports/#ports-pkg-locking) and [pkg-lock(8)](https://man.freebsd.org/cgi/man.cgi?query=pkg-lock&sektion=8)). This is a separate **pkg database metadata lock**, not the Zapret2 FD9 service lock or the OPNsense firmware launcher progress/serialization lock.

On a verified **disposable OPNsense 26.7 KVM guest** with the actual project package absent, create two harmless private synthetic `zapret2-stage0-fd9-hook-fixture` archives from existing Stage 0 tooling, using only temporary `PKG_DBDIR`, cache and payload. Install old fixture; execute real `pkg lock -y`; require `pkg lock -l` lists the installed fixture. Then measure a direct native `pkg delete -y` followed by `pkg add -f` while the fixture is locked, re-reading actual private pkgdb and file bytes after each. **If a locked operation nevertheless changes package state, report a safety hazard instead of claiming PASS.** If locked operations preserve original, explicitly `pkg unlock -y` then retry synthetic `pkg add -f` and verify new private package identity and payload. No real plugin package is installed, removed or upgraded. A successful experiment only establishes the tested native `pkg` commands' behavior for this private fixture on this OPNsense guest.
