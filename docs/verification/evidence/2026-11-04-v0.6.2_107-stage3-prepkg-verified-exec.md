## Why the previous standalone entrypoint is insufficient

The _106 `scripts/native-prepkg-standalone.py` root copy checks its own diagnostic SHA-256 only **after the Python interpreter has already started executing the copy**. That diagnostic does **not authenticate the code**. Likewise, an attacker-provided expected digest, or a digest copied from the untrusted incoming `.pkg`, cannot anchor a trust decision. A legitimate operator or managed updater must obtain the expected SHA-256 via an **independently authenticated origin** before any target source executes.

## _107 reproducible verification boundary

`scripts/stage3-prepkg-verified-eval.py` is the **audited operator-side Python `-c` program**, **not** code safely authenticated merely by checking it into the repository or executing it by filename. In the disposable CI only, its exact text is taken from the pinned checked-out PR head and passed directly to the trusted system Python interpreter using `python3 -I -B -c <audited-trusted-code> <independently-expected-cli-sha256> </root/secret/cli.py> inspect-predecessor <new.pkg> <new.version> <new.sha256> <old.pkg> <old.version> <old.sha256>`. The word `trusted` here denotes the **CI source checkout assumption**, not a completed production signature, external release channel or protected operator deployment. A separate operator must establish the trustworthiness of the `-c` bytes **and** the expected SHA using an independent, approved channel; fetching both from the same untrusted package is forbidden.

The `-c` code refuses all commands other than exactly one `inspect-predecessor`. It requires FreeBSD amd64 root, an absolute normalized CLI path strictly below `/root`, root-owned non-world-writable directory ancestors, a root-owned single-link regular `0600` source `<=256 KiB`, non-symlink opened FD with stable inode/size/mtime/ctime, and an independently provided lowercase 64-character SHA-256 expectation. It reads the file **exactly once** through that checked FD, checks the digest with `hmac.compare_digest`, freezes verified bytes, then compiles and executes *that memory buffer*, never re-opening the path to execute a possibly replaced script. `-I -B` avoids user-site, current-directory import injection and bytecode writes. Any failure returns **78** before source code executes. An accepted digest emits `ZAPRET2_PREPKG_VERIFY_EXEC=VERIFIED_SHA256:` on stderr, before the standalone CLI continues into its existing read-only old-owner inspection.

## Outstanding mandatory boundaries

An independently authenticated operator distribution/provisioning **does not yet exist**; the `-c` code and the expected script hash both currently depend on the CI exact-head trust assumption. The operator must review and source them independently before running anything outside CI. Source-backed `-c` verification is not a global OS-enforced execution policy; a privileged administrator can still run the untrusted file by filename or call direct `pkg add -f`. There is **no enforced/registered stock OPNsense Web/firmware/plugin-managed updater entrypoint** and no protection for arbitrary privileged root pkg. This stage also does **not** qualify full old RUNNING/foreign IPFW/PID/Config process ownership, serial admission-to-pkg original FD9, interruption, rollback or historical hook cooperation. Old cold screening must never be treated as an authorization to install.
