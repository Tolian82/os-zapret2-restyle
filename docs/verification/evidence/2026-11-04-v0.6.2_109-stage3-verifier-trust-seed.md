## Observable gap and test scenario

In _108, the signed provenance verifier (`scripts/stage3-prepkg-verified-eval.py`) was *itself* supplied as already trusted Python `-I -B -c` text from exact-head CI checkout. It authenticated a public key through an externally pinned SHA, then authenticated a signed JSON manifest, then checked and executed the standalone predecessor CLI. A downloaded/tampered **verifier** could therefore execute before those checks if an operator incorrectly executed it by filename or supplied its bytes to `-c` without independent authentication.

_109 adds a narrow `scripts/stage3-prepkg-trust-seed.py` reviewed **seed for `python3 -I -B -c`**, one step before the _108 verifier. It is the **first executed Python text** in the envisioned operator workflow, not a file to run as `python3 downloaded-seed.py`. The seed itself still MUST be reviewed/authenticated through a channel independent of incoming files and packages. Its caller-supplied expected verifier SHA-256 must independently originate from that trusted channel; a hash delivered alongside the verifier or inside an incoming `.pkg` has NO trust value.

The seed permits only `--verified-verifier EXPECTED_VERIFIER_SHA256 /root/.../stage3-prepkg-verified-eval.py --signed-provenance ... inspect-predecessor` with exact argument count, FreeBSD amd64 and root. It validates the exact private normalized source path and all root-owned non-world-writable ancestor directories, refuses symlinks, requires a root-owned single-link regular `0600` verifier `<=256 KiB`, checks inode/size/ctime/mtime stability and the *independently pinned* SHA-256 through its one opened FD, then compiles and executes **only frozen verified memory bytes**. It does not call `pkg`, import external project modules, open a second source path, or dispatch any mutating command. The verified _108 code then separately verifies the pinned public-key digest, actual RSA signature, signed metadata, standalone CLI digest and two native archive hashes before read-only original-FD9 inspection.

### Full test-only trust chain

```text
operator-reviewed -c seed + externally expected verifier SHA (NOT distributed)
  -> frozen SHA-verified signed-provenance verifier
  -> independently pinned public-key SHA + verified signed claims
  -> SHA-verified standalone CLI frozen in memory
  -> SHA-qualified native incoming/old archive modules
  -> read-only original FD9 old predecessor inspection
  -> STOP: no upgrade/reinstall/remove/pkg dispatch
```

The CI runner may use only source from its exact checkout for the seed and verifier hash and generates a throwaway test-only RSA signer; these are **CI trust assumptions, not operator or publisher authenticity**. The real production signing key, authenticated seed text delivery, independent verifier SHA provisioning and supported OPNsense firmware/Web/managed pre-pkg gateway remain **NOT IMPLEMENTED**.
