## Narrow purpose

Prior `_118` had only locally stored unsigned STATUS; `_119` verified a caller-supplied signed response but did not demonstrate a **separately running process** owning persistent operation state and a private status signing key. This `_120` change adds CI-only `scripts/stage3-prepkg-remote-witness-ci.py` and `scripts/test-stage3-prepkg-remote-witness-ci.py`.

The witness process owns a separate SQLite file and an ephemeral CI RSA private key. It only binds `127.0.0.1` on the disposable runner, is not installed or started as an OPNsense service and requires `ZAPRET2_CI_REMOTE_WITNESS_ONLY=1`. No host/port is loaded from an appliance configuration and there is no general external network exposure or production transport.

The wire protocol accepts strict bounded JSON requests identifying `RESERVE`, `CONSUME`, `ABORT`, or `STATUS`, exact 64-hex operation/payload/checkpoint digests, positive checkpoint sequence and request challenge. Unknown keys, malformed JSON and duplicate request keys are rejected. Each accepted challenge is uniquely inserted into SQLite in the **same `BEGIN IMMEDIATE` transaction** that checks/changes the operation state. SQLite `synchronous=FULL` commits before the reply is signed. A repeated challenge is refused, even for read-only STATUS or idempotent re-read. Operation IDs are immutable; concurrent different operations cannot reserve the same active checkpoint, nor can another operation spend a consumed checkpoint. Identical idempotent `CONSUME` never increments the operation counter. A terminal `ABORTED` may free the test checkpoint for another operation (historical entries remain), but cannot be consumed later.

The response uses the **existing** `_119` raw RSA-SHA256 verifier unchanged, including exact expected signer PEM digest, operation/payload/checkpoint binding, challenge, witness sequence and signed validity interval. The `drop_after_commit` flag is a CI-only fault injection simulating the network response disappearing **after SQLite commit**, with a separately challenged signed STATUS read-back after server restart.

## Security and product acceptance boundary

This service is NOT an independent deployed off-host witness. It has **no client authentication**: another local CI process could reserve/consume/abort. The ephemeral key, public-key hash, SQLite database and simulated clock are all controlled by the disposable runner; root can roll back the database and recover spent challenges. Signed `CONSUMED` is a *test status*, never proof that original FD9 remained owned or `pkg` was invoked safely. No TLS/mTLS, production operator key, owner-approved release/nonce, off-host append-only storage, attested latest sequence or cross-store atomic package transaction has been implemented.

**Therefore `ci_independent_remote_witness_deployed=false`, `production_pkg_authorized=false`, `pkg_invoked=false`, `supported_entrypoint_implemented=false`, `lh08_ac11_accepted=false`.** Published stable `v0.6.2` / `0.6.2_1.pkg`, production four hooks and owner OPNsense remain untouched.

**Next true acceptance gate:** independently administered external witness, authenticated caller rights and signer/key, monotonic anti-rollback storage and authenticated transport; then reconcile lost-reply/split-store crash under continuous original FD9 through the supported native `pkg` gateway with _74 no-mutation negatives. **LH-08/AC-11 BLOCKED.**
