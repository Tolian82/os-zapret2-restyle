## _125 GitHub jobs pagination and incident recovery (Issue #894)

[Detailed _125 evidence](evidence/2026-11-04-v0.6.2_125-watchdog-paginated-jobs-and-actions-stall.md). In [scheduled run #41856709938](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/41856709938), `Api.pages` rejected the documented GitHub REST `{"jobs":[...]}` response and crashed with `PAGINATED_GITHUB_RESULT_UNEXPECTED`. The affected run was red and cannot be counted as successful comment delivery. `_125` now dispatches a bounded GitHub list parser based on the requested endpoint: `jobs` for actual Actions jobs, `workflow_runs` for workflow runs, and direct lists for PRs/files/comments. Unsupported or malformed responses fail closed, never READY.

Importantly, successful final **step** status does not mean a completed **job or workflow**. While #892 had several successful `Complete job` steps and workflows remained `in_progress`, watchdog must report `CI_IN_PROGRESS` or `CHECK_STALLED` after the existing 30-minute timeout, but never `READY_FOR_OWNER_REVIEW` until every required exact-head workflow completes SUCCESS. #892 ultimately achieved **20/20** and merged, without a skip. The watcher now also triggers on **trusted main pushes to its Python files** (plus the workflow YAML), so the fix can be exercised after merge rather than waiting solely on a delayed schedule.

**Deployment and actual PR-timeline write ACCEPTED, with limits:** [Issue #894](https://github.com/Tolian82/os-zapret2-restyle/issues/894) is closed based on the real [#897 comment](https://github.com/Tolian82/os-zapret2-restyle/pull/897#issuecomment-6638756282) on the right open-PR head, and subsequent [#948 READY](https://github.com/Tolian82/os-zapret2-restyle/pull/948#issuecomment-6703929386) / [#949 CHECK_FAILED](https://github.com/Tolian82/os-zapret2-restyle/pull/949#issuecomment-6704094405) reinforce continuing notification capability. Offline unit tests and zero-open-PR scans remain **insufficient alone**. GitHub email/push/reading of the comment is not proven, schedule is best effort, the watcher cannot wake an inactive ChatGPT session, and **the developer remains accountable for every verified merge** under GH-064. The watcher does not auto-merge, build packages, or execute untrusted PR code.

## Trigger, trust and data sources

- `.github/workflows/pr-completion-watchdog.yml` runs on completion of the common PR **`CI`** workflow (`workflow_run`), on an **hourly** fallback schedule (`7 * * * *`, GH-070), via manual `workflow_dispatch`, and on trusted `main` pushes when **the workflow YAML, `scripts/github_pr_watchdog.py` or `scripts/test_github_pr_watchdog.py`** changes. One `CI` completion trigger avoids a storm of 16 separate completion-triggered watchdog jobs. Specialized workflows are STILL dynamically checked per exact head; if they finish after CI the schedule discovers READY/FAILED later (GitHub scheduling can be delayed, no hard 10-minute SLA).
- The privileged watcher **checks out only trusted default branch main**; it never fetches, checks out, sources or executes PR branch code. The GitHub workflow supplies a minimally scoped token: `contents: read`, `actions: read`, `pull-requests: write`, `issues: write`. The expanded PR comment permission is isolated to the trusted-main notification job, in response to an observed PR timeline HTTP 403 with effective `Issues: write`, `PullRequests: read`. It never calls merge, touches protected branch settings, packages software or reaches any appliance.
- `scripts/github_pr_watchdog.py` reads only owner-managed OPEN PRs targeting `main`, their current head SHA, changed-file paths, GitHub workflow run statuses, available job/step summaries and previous GitHub Issue comments. Expected workflow names are derived from the checked-in trusted default-branch `.github/workflows/*.yml` PR path filters, not a constant 16. Unsupported or inconsistent trigger policies fail closed (no READY).
- Classify `CI_IN_PROGRESS`, `CHECK_FAILED`, `CHECK_STALLED` (no job/step progress for ~30 minutes, advisory only), `STALE_BASE` and `READY_FOR_OWNER_REVIEW`. Only **completed successful latest current-head runs for every expected workflow** count. Cancelled, skipped, missing, wrong SHA, unsuccessful or pending checks are never green.
- Actionable states attempt to create a PR issue comment with a unique marker and current SHA/status. A failed POST still causes a **red job**; an API response is classified into a fixed category with syntax-checked GitHub request ID and allowed permission hints, never raw response or token. An independent, trust-bounded **GitHub Actions job summary** records PR URL/current SHA/READY or FAILED plus comment delivery outcome even on an HTTP 403. A job summary is an inspectable fallback **not** a user-push notification. GitHub run-failure notifications also depend on the user's GitHub notification settings. Existing identical head/state comments suppress repeats, including repeated scheduled invocations. Failure messages may include failed run/job/step URL **but never raw job logs or untrusted PR title/body**. The comment warns that it is not a merge/review substitute.

## Setup, smoke and operational acceptance

1. Verify the workflow exists on the *actual main* branch following an exact-head, fully qualified merge. A workflow file sitting only in a PR is NOT an installed monitor.
2. Verify the controlled GitHub Actions run triggered by the merge push to `main` for the watcher file, including a green offline negative regression suite and read-only scan outcome. Confirm subsequent events or scheduled executions before relying on unattended monitoring. GitHub scheduled runs can be delayed or disabled by platform settings.
3. The actual failing run #630 granted `Issues: write` and still rejected `POST /issues/857/comments` with HTTP 403. The workflow now requests **both** `issues: write` and `pull-requests: write`, while retaining trusted-main-only code execution and no PR modification API. Verify these actual effective rights in the job header. GitHub's API error category distinguishes integration permission refusal and primary/secondary throttling; if it still fails, report the recorded safe request-id to the owner rather than guessing. External email/app delivery cannot be guaranteed. A no-PR smoke proves that the watcher ran, **not** that an owner received a comment; a real actionable PR notification must be witnessed separately.
4. The historical **one-time, deduplicated merged-main write smoke** (already accepted; **not** an action to repeat on every new documentation PR) targeted the **already-merged PR #857** using the exact `/issues/857/comments` POST endpoint that failed. It checked `state=closed` and `merged=true`, used a unique marker and never reopened or merged the PR. [The original #857 comment](https://github.com/Tolian82/os-zapret2-restyle/pull/857#issuecomment-6605845176) and [real open #897, #948 and #949 notifications](https://github.com/Tolian82/os-zapret2-restyle/issues/894) are **historical observed evidence**. Future permission regressions still require a red Actions run with sanitized error and summary; no guarantee of owner email/push notification.
5. Operational source tests: `python3 scripts/test_github_pr_watchdog.py -v`. They exercise valid/invalid scoped workflow triggers, count-independent required sets, green/red/missing/old-head/cancelled/skipped/stalled/merge-conflict/draft states, duplicate suppression, owner-only scope and refusal to run untrusted code.
6. No always-on ChatGPT agent is launched by this workflow. GitHub notifications prompt **manual owner/developer follow-up**, not autonomous remediation or merge. Review/version/branch protection and package lifecycle safety gates still apply.

**Boundaries:** no installed product package, pkg hooks, native runtime, WAN, owner device, published stable release or LH-08/AC-11 acceptance is modified by this automation. [Issue #850](https://github.com/Tolian82/os-zapret2-restyle/issues/850) is closed after initial trusted-main activation; **real comment API writes and live open-PR `READY` alert have since been observed**, as linked above. Do not infer email/push delivery from comment creation. Continue checking post-upgrade token permissions, scheduler health, and true PR-head readiness; report delivery failures as red, never silently.
