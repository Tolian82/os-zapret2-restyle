## Текущая граница

**`_63–_65`: safe operator-only cancellation of UNEXECUTED legacy STOP intent.** `shared-apply-legacy-cancel ID` runs under original FD9 and Config inode flock and rechecks previous Config/runtime file bytes against the durable snapshot, marker bytes/mode, exact old 3-process argv/epochs and legacy IPFW/table/managed addresses, plus candidate seal and full immutable recovery plan. Only an unchanged still-live old owner can move the *same* shared journal from `legacy-prepared` to `restored`; no engine, firewall, Config or marker mutation occurs. If anything differs, no terminal transition is permitted. Boot never cancels automatically. This is not a live cutover or rollback after STOP: **do not run `legacy-arm` on a production router pending real FreeBSD acceptance.**

**`_59–_61`: предохранитель перед реальной legacy-миграцией записан в ЕДИНЫЙ durable Apply journal.** Новый операторский маршрут `shared-apply-legacy-arm <id>` под исходным FD9 повторно сверяет sealed Voice ON-кандидат, оригинальный Config preflight, полный прежний runtime/IPFW/argv и ранее запечатанный `legacy-backup` со всеми пятью ресурсами. Затем существующий `shared_apply_operation.py` сохраняет atomic/fsynced запись `phase=prepared` с тем же ID и SHA-256 отпечатком старого predecessor + reverse-plan. В командном inspect эта фаза видна как `legacy-prepared`. **Это только durable STOP intent, не сам STOP.** Обычный `shared-apply-record activating`, boot recover-prepared и дальнейшие общие переходы для неё **запрещены**, пока не написан специальный проверяемый исполнитель. Поэтому операторское arm временно блокирует обычный start/reconfigure при последующем запуске — не применять на производственном устройстве до окончания миграции. Второй WAL, отдельный Config writer и новый runtime не создавались; GUI/ТЗ не менялись. Следующая работа — доказуемый живой cutover с восстановлением по этим ресурсам, FreeBSD power-cut и STUN/CALL приёмка.

Вызов реального live cutover всё ещё не разрешён; owner-live FreeBSD/Telegram call не выполнен.

**`_57` — полноценное сохранение старого пятикомпонентного PoC без его остановки.** Операторская команда `shared-apply-legacy-capture <ID>` под штатным FD9 сначала выполняет `_56` candidate-bound read-only qualification, затем вызывает **существующий** root+Config-flock backup/restore-plan capture. Предыдущий Config, runtime, old Telegram marker, exact IPFW/table и зафиксированные kernel process/security evidence сохраняются атомарно и синхронизируются в **`/var/db/zapret2/shared-work/<ID>/legacy-backup`**; обратный план immutable, без дополнительного WAL и без запуска старого rollback executor. Затем повторная qualification должна совпасть буквально, иначе команда отказывает с сохранением свидетельств для ручной проверки. Ранее созданные следы никогда не перезаписываются. Snapshot не равен разрешению миграции: **`legacy-handoff-authorized=0`**, работающий old PoC и native Config не меняются. Далее — строго единый reversible executor с dry-run/real OPNsense acceptance, без второго backend.

**`_56` — рабочий FD9-маршрут legacy-аудита и привязка к конкретному Voice-кандидату.** Найден и исправлен дефект `_54–_55`: `shared-apply-legacy-audit` был в `service_dispatch`, но не во внешнем списке `service_with_lifecycle_lock`; поэтому реальный CLI обходил оригинальный FD9 и строгий инспектор отказывал. Теперь и `shared-apply-legacy-audit`, и новый read-only `shared-apply-legacy-qualify <32-hex-id>` проходят **тот же штатный FD9**. Qualify проверяет оба sealed/fresh Config состояния, Voice ON, полный общий runtime candidate, установленный dvtws2 и точное legacy IPFW/kernel/argv-свидетельство из `_55`, не мутируя ничего. Печатает candidate ID и старые IPFW/IPSET fingerprints; одновременно выдаёт **`legacy-handoff-authorized=0`**. Это не переход и не rollback работающего PoC: физическое переключение всё ещё требует единого восстановимого executor и FreeBSD owner-live.

**`_55`: точная read-only сверка legacy IPFW/argv без нового исполнителя.** Операторский общий `shared-apply-legacy-audit` под прежним FD9 теперь после базового наблюдения вызывает **существующий** `voice_native_legacy_live_preflight.py inspect`. Он закрепляет Config оригинальным flock, старые marker/runtime state и managed IPv4, сверяет реальные FreeBSD kernel argv и image трёх процессов, а также полный старый IPFW rule interval/table в двух независимых выборках. Код требует ожидаемый ответ и повторно сверяет общие PID после получения свидетельства. Только при успехе возвращает `legacy-exact-ipfw-argv-observed=1`, но по-прежнему **`legacy-handoff-authorized=0`**: читать и установить соответствие — не значит безопасно остановить работающий PoC или восстановить старые правила после ошибки. Нет нового WAL/движка/публичной кнопки.

**`_54`: read-only live legacy audit.** В общем `apply_runtime.sh` добавлено наблюдение одного работающего старого runtime: обязательные legacy-файлы, отсутствие общего `voice-plan.json`, PID dvtws2 и supervisor, независимый census engine и штатная проверка old IPFW. Команда `shared-apply-legacy-audit` выполняется под исходным FD9 без записи Config/WAL и без изменения процессов/IPFW; даже положительный результат выдаёт `legacy-handoff-authorized=0`. Старый IPFW check не доказывает точный ownership и не разрешает live cutover. Далее — доказуемый rollback legacy/kernel и FreeBSD owner-live.

**`_53` — восстановление подтверждённого разрыва атомарной установки при `activating`.** В новых общих Apply три служебных пути `.stage.<id>`, `.old.<id>` и `runtime-v2-<id>` привязаны к тому же durable ID, который уже записан в едином journal под FD9. Ранее использовались PID/дата, поэтому остатки старых операций **не** считаются доказуемыми и не восстанавливаются автоматически. При отсутствии active runtime, точной новой staged-копии и ровно одной прежней parked/backup-копии, совпадающих с обоими sealed release, а также прежнем native Config и пустых процессах/IPFW, штатный `atomic_install_tree` возвращает предыдущий release из sealed source. Остатки stage и previous park/backup сохраняются для анализа; никакой сканирующей/угадывающей очистки нет. После повторной сверки `finish-activating` переводит единую запись в `restored`. Неизвестные, старые PID-пути, обе previous-копии, чужие деревья и live-состояния остаются blocked. Это проверяемая кодовая симуляция, не квалификация реального отключения питания FreeBSD.

**`_52` — холодное восстановление полностью установленного нового runtime из прерванной `activating`.** Запись single common journal может остаться в `activating`, даже если atomic rename уже завершён. Boot под тем же FD9 сначала отдельно проверяет прежнее дерево (прежний `_49` pristine-case); если оно не совпало, проверяет строго совпадающий с sealed candidate новый installed runtime. Только если оба bundle целы, предыдущая native Config не изменялась, все процессы dvtws2/supervisor отсутствуют (включая full census), а scoped IPFW пуст, применяется существующий cold rollback `_50` к предыдущему sealed release. Повторная проверка обязательна до перехода того же журнала `activating → restored`; следующий штатный boot обслуживает предыдущего common owner. При частично перенесённых, исчезнувших или чужих деревьях, чужом IPFW, изменившемся Config или живом процессе **ничего автоматически не стирается**. Проверки CI — только simulation, FreeBSD owner-live ещё не доказан.

**`_51` — защита промежуточных деревьев атомарного Apply.** В `atomic_install_tree` устранено удаление заранее существующих `.stage.$$` и `.old.$$`: после прерывания или повторного использования PID они могут содержать единственную копию прежнего runtime. Теперь выполняется отказ до копирования и переноса дерева. Дополнительно проверяется отсутствие целевого `name-date-PID` backup, чтобы `mv` не вложил текущий release в чужую директорию. Regression проверяет сохранность трёх занятых путей и действующего runtime штатной производственной функцией, в существующих Linux/FreeBSD CI. Это предотвращение потери доказательств, **не** готовый redo/recovery частичного `activating`.

**`_50` — холодный откат прерванной фазы `activated` к предыдущему общему владельцу.** Новая ветка восстановления под оригинальным FD9 проверяет оба sealed release, предыдущий штатный saved Config, пустой IPFW и отсутствие `dvtws2`/supervisor (включая полный census). Если установленный runtime полностью совпадает с новым кандидатом, существующий `atomic_install_tree` восстанавливает прежний release и сохраняет неудачный кандидат в обычном backup. Если прежний release уже восстановлен, действие идемпотентно. Перед записью `restored` выполняются повторная сверка файлов, Config и процессов. Неизвестное, частично изменённое, живое состояние, потеря предыдущего владельца, конфликт Config и ошибка атомарного переноса остаются заблокированными. Это ограниченный cold-case, не универсальный power-cut recovery; реального FreeBSD owner-live пока нет.

**`_49` — ограниченное восстановление «чистого» прерывания `activating`.** Если предыдущий владелец — уже сохранённый общий release, после сбоя FD9-процедура сверяет sealed bundle обеих операций, полный установленный runtime, сохранённую native Config, отсутствие зарегистрированных и потерянных процессов dvtws2, пустой owned IPFW. Только при полном совпадении `activating → restored` сохраняет прежнего committed owner; обычный boot затем может запустить именно его. Любой частично изменённый runtime, legacy без sealed predecessor, `activated`, постсохранённая неоднозначность или чужой IPFW остаются **заблокированы**, без автоматической очистки. История Draft PR до неизменяемого коммита `a7682c46` (`v0.5.2_47`) закреплена как legacy-период: заголовки этой прежней ветки не переписываются; с первого `_48` действует строгая проверка каждой новой версии/названия. Любое изменение исторического SHA делает прежнюю границу неприменимой. Linux CI проверяет сценарий, реальный FreeBSD power-cut/звонок не подтверждён.
