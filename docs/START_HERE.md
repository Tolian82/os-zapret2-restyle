## Подтверждённый отказ `_11` и исправление `_12`

18.10.2026 владелец выполнил один Telegram ON Apply: GUI прошёл стадию candidate, но отказался до переключения runtime с `preflight-rejected=runtime-build`. Read-only журнал сборки подтвердил `4|8|blobs|failed|...|telegram.args: required --filter-udp is missing`; `stage-error.log` повторил `ERROR: telegram.args: required --filter-udp is missing`. Не проверять снова общую службу/PID, WAN, FD9: этап отказа известен.

Причина обнаружена в преобразовании модели OPNsense в detached XML: `Zapret.xml` задаёт Telegram STUN `args` по умолчанию (`--filter-udp=*`...), поэтому GUI показывает и валидирует профиль, но старый `config.xml` может не содержать физического `<args>`. При включении только флага `enabled` прежний `VoiceCandidateXml` записывал только changed fields, оставляя default `args` за пределами XML; Python-компилятор читает этот XML и ожидаемо отказывает. В `_12` при Voice Apply для **каждого включённого** профиля явно материализуются его уже проверенные `args` и IPSET в detached XML даже без пользовательского изменения этих полей. Запись вне Voice whitelist и изменение активного Config на подготовке запрещены, режим all-OFF/no-change остаётся прежним. PHP-регрессии покрывают отсутствующий и пустой `<args>`, отсутствующий IPSET и root worker request.

**Единственное следующее действие:** проверить exact-head CI Voice/Project/FreeBSD15 `_15`, опубликовать тестовый pkg и дать владельцу команды `fetch`, `pkg add -f`, `pkg info -x`. На установленном `_15` выполнить ОДИН Telegram ON Apply с действующими «Стратегиями», затем независимо подтвердить сохранённый Config, общий runtime/IPFW и реальный звонок. Новых диагностик WAN/FD9/сборки 8/8 не требуется. Если Apply откажет до начала транзакции, GUI теперь укажет точную стадию (`bundle-verify`, `config-preflight` либо `runtime-preflight`), вместо неопределённого результата.

Никакие `candidate.xml`, `plan.json`, внутренние файлы транзакции или пользовательские секреты туда не копируются. Движок получает аргументы, переписанные только на эту временную копию; после проверки она удаляется в успехе, ошибке и исключении. Регрессия моделирует `nobody` на закрытом staging, отказывает в symlink/escape, проверяет очистку.

В `_14` общий IPFW адаптер получает строго проверенный manifest предыдущих обычных «Стратегий» из root-owned `runtime-v2/dvtws.args`, `tcp-ports.txt`, `udp-ports.txt` и физического WAN текущего native кандидата. Отдельная read-only проверка сравнивает действительные старые правила и отсутствие чужих таблиц; любое несовпадение отвергается **до** записи журнала. После успешной проверки используется прежний FD9, одна durable транзакция, существующие atomic runtime/Config/IPFW этапы и rollback штатного адаптера. Старый Telegram PoC не используется и второй движок не запускается.

Код проверяется в PR #361. Тесты охватывают первую передачу владения, rollback до Config и отказы для чужих правил/подменённого runtime. До установки `_14` успех сохранения Telegram, IPFW/STUN и звонка **не подтверждён**.

## Дефект `_14` в реальной CLI-ветке первого перехода, исправление `_15`

После публикации `_14` владелец снова получил в GUI «Результат применения неизвестен» и статус «Voice не подтверждён». Ревизия кода установила конкретный блокирующий дефект: `backend/voice_ipfw_adapter.py::main()` проверяет `if not legacy` в ветке `verify-legacy`, но переменная `legacy` **не объявлена**; выше вычисляется `prior_legacy`. Таким образом первая попытка передачи владения от обычных «Стратегий» падает с `NameError` ещё до durable `prepared`. Ранее unit-тесты использовали только вспомогательный алгоритм и не вызывали настоящий CLI — CI не обнаружил ошибку. Причина подтверждена анализом кода, но точный live журнал `_14` владелец не предоставлял.

`_15` исправляет имя переменной и добавляет тест, выполняющий настоящую CLI-ветку `main()` с контролируемыми FD9/root/IPFW двойниками. Дополнительно префлайт до durable журнала возвращает строго ограниченный этап отказа в GUI (`bundle-verify`/`config-preflight`/`runtime-preflight`), чтобы новые причины не маскировались сообщением о неизвестном результате. После начала транзакции неопределённые ошибки продолжают требовать проверки состояния. **Нет подтверждения установленного `_15`, saved Telegram ON, IPFW или работающего звонка.**
