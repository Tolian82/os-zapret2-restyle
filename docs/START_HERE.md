## Наблюдение установленного 0.5.3_4

17.10.2026 владелец подтвердил установку `0.5.3_4` на OPNsense 26.7.7. `setup_status` сообщает `service=started` и `v1.0.5.2`; GUI корректно показывает «Запущена · Voice не подтверждён». `configctl zapret voice_lifecycle_inspect` теперь успешно отвечает `state=voice-saved-off-common-apply-available`, `saved_voice_on=false`, все пять сохранённых профилей OFF. Отдельный `voice_inspect` сообщает `state=uninitialized`: Voice/IPFW ещё не подтверждён. На скриншоте Telegram выбран ON в форме, однако backend сообщает saved OFF, поэтому успешного сохранения/применения нет.

Новый блокер: Voice GUI показывает на WAN обобщённую ошибку проверки, внизу «Результат применения неизвестен». Аудит `VoiceController::applyAction()` обнаружил ложную неопределённость: `catch (Throwable)` помечает `requires_review=true` даже ДО dispatch `zapret shared_apply`. В `_5` ошибки до границы FD9 классифицируются как безопасный отказ `applied=false`, `requires_review=false`, с фиксированным кодом стадии и записью типа исключения в PHP error_log без входных данных, а post-dispatch остаётся неизвестным результатом и блокирует повторный Apply. Конкретная первопричина ошибки подготовки XML/модели на устройстве ещё **не доказана**. Есть PHP-регрессия для Throwable в guard до dispatch и для dropdown+ON модели. [CI #39042954730](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/39042954730) (Voice/Project/FreeBSD15 pkg) успешен; исправление включено в `main` [d91c8cb](https://github.com/Tolian82/os-zapret2-restyle/commit/d91c8cb9ff957ef71545cb8d8bcca26638101f77), [проверочный пакет `_5`](https://github.com/Tolian82/os-zapret2-restyle/releases/download/v0.5.3_5/os-zapret2-restyle-0.5.3_5.pkg) опубликован, SHA-256 `3c4ca5acf76e22f0d0fc16c823849bc363030f137e36d1bea8c2bc2e1613b7da` подтверждён. Установка `_5` ещё не наблюдалась.

## Блокер после первого live Apply на установленной _6

17.10.2026 владелец показал неуспешный `shared-apply-run voice` (exit 69) на OPNsense 26.7.7, saved Voice всё OFF, runtime Voice uninitialized; `/var/db/zapret2` отсутствует. Отдельные пробы: `CLI_MODEL_OK`, Python native-gate `NATIVE_GATE_RC=0`, но настоящий PHP FD9 check вызывает **Fatal Error: undefined `posix_geteuid()`** в `shared_apply_lock.php:14`, rc 255. Это доказанный blocker до PHP-attestation, но не доказательство успешности более поздних фаз Apply. OPNsense 26.7 использует PHP 8.5 и не включает расширение POSIX в обязательный список. `v0.5.3_7` добавляет в пакет `php85-posix` (`sysutils/php85-posix`), единый fail-closed euid helper и FreeBSD pkg regression; только этот дефект, без изменений сервиса/IPFW/GUI. Пакет [опубликован](https://github.com/Tolian82/os-zapret2-restyle/releases/download/v0.5.3_7/os-zapret2-restyle-0.5.3_7.pkg) из `e402d89`, SHA-256 `38f656a4e295f7451b1dd192737dba41d8e2f4405929fa81aa3b324a49158913`, [Voice/Project/FreeBSD15 CI #39053386699](https://github.com/Tolian82/os-zapret2-restyle/actions/runs/39053386699) PASS. Установка и повторный root PHP FD9 test ещё не проверены.

## Дополненное доказательство (17.10.2026)

Установленная _6: PHP posix_geteuid() отсутствует, FD9 PHP проверка завершается Fatal Error (rc255), конфигурация Voice не сохранена и configd Apply rc69. _7 ошибочно добавлял php85-posix (из FreeBSD ports). Владелец подтвердил, что пакет не найден в штатных репозиториях OPNsense. _7 как исправление использовать нельзя.

_8 исправляет именно зависимость: больше не требует php85-posix и использует базовый /usr/bin/id -u через PHP proc_open(argv) без shell, EUID проверяется строго и fail-closed; исходный FD9/inode/flock остаётся. FreeBSD pkg CI запрещает наличие php85-posix в манифесте; тест php -n проверяет отсутствие POSIX.

## Новый live-блокер и конкретное исправление `_9`

На установленной `_8` PHP FD9 (`EUID=0`, `PHP_FD9_OK`), native gate (`GATE_RC=0`) и PHP saved-model (`PHP_MODEL_RC=0`) успешно проверены. Два GUI Apply вошли в `configd shared-apply-run voice`, но завершились кодом 69; под FD9 `shared_apply_operation.py inspect` вернул `none`, `/var/db/zapret2` отсутствует, общий движок продолжает работать. `telegram-envelope enable` отказал для *сохранённой OFF-конфигурации* и не является причиной отказа несохранённой GUI-формы.

В `_9` исправлена доказанная потеря результата подготовительной стадии: вместо безусловной неопределённости для всех nonzero `configd`, root-worker сообщает только доверенную `preflight-rejected=<stage>` до runtime/Config/IPFW. Контроллер отвечает `applied=false`, `requires_review=false`, переводит стадию в RU; post-dispatch ошибки без такого подтверждения остаются неопределёнными. Ни WAN, ни runtime, ни STUN семантика не меняются. **Причина исходного отказа `_8` ещё не доказана**.

## Опубликованная `_9` и выявленный `candidate` blocker

Владелец установил `_9` на OPNsense 26.7.7 и нажал Telegram ON Apply: GUI показал **«Подготовка Voice остановлена до переключения службы (стадия: candidate). Настройки не применены»**. Сохранённые профили остаются OFF, Voice `uninitialized`, общий Zapret2 продолжает работать. Это точное свидетельство pre-runtime отказа; гипотеза «WAN не проходит» не подтверждена отдельно.

18.10 владелец одобрил архитектурное упрощение: **удалить Voice WAN selector и брать только WAN со страницы «Стратегии»**. [Issue #350](https://github.com/Tolian82/os-zapret2-restyle/issues/350). `_10` изменяет нативную форму, PHP-кандидат/whitelist, совместимый CLI-путь и Python-компилятор; старое `voice.waninterface` в Config читается инертно и не изменяет Strategies. ТЗ согласовано с решением владельца; пять STUN/IPSET профилей, общий backend и его транзакция сохраняются. Ошибка `candidate` может остаться после этого упрощения, поэтому успех Apply не объявлен.
